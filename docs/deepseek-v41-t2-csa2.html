TL;DR：大模型推理时，每个历史 token 的 Key/Value（合称 KV）都要留在显存里供后续 token「查阅」，上下文越长这部分显存越大。DeepSeek-V4.1-Flash 的答案是 CSA2（Compressed Sparse Attention 2）：把 KV 压缩从「序列维」（V4 的 CSA：每 m 个 token 压成 1 条 entry）进一步扩展到「层维」——相邻若干层共享同一份 main KV、indexer K 甚至 Top-K 索引，层与层之间按 Full / Reindex / Reuse 三种模式静态分工。再配上层级稀疏索引器（Hierarchical Sparse Indexer）：解码器第一层全量打分后选出一个候选池，后面的索引器只在池内「复试」，把每个查询的打分开销从「随上下文线性增长」压成「常数」。两项设计加上 FP4 量化，把全局 KV cache 压到 890 字节/token，约为 DeepSeek-V4-Flash 的 1/4、DeepSeek-V1 的 1/437——而模型性能反而更强。本讲就是要把这两招和配套的训练策略（§3.1.2）掰开揉碎讲清楚。

1. 铺路：KV cache 为什么会「越聊越大」

1.1 Attention 的记账方式

先补三块基础知识（懂的同学可以直接跳到 1.3）。

Token（词元）：模型处理文字的最小单位，可能是一个字、半个词或一个标点。模型读入一串 token，预测下一个 token。

Attention（注意力）：生成每个新 token 时，模型要让「当前的查询（Query，简称 Q）」去和「之前所有 token 的钥匙（Key，简称 K）」比对相关度，再按相关度加权取回「内容（Value，简称 V）」。打个比方：你在图书馆找资料——Q 是你手里的问题清单，K 是每本书书脊上的标签，V 是书里的内容。问题要和标签逐一比对，才能决定重点翻哪几本书。

KV cache（KV 缓存）：比对用的 K 和书的内容 V，在每个注意力层、每个历史 token 上都要留一份，否则每生成一个字都得把整篇文章重新算一遍。这份「留在显存里的历史 K/V」就是 KV cache。它的体量公式很朴素：

\[ \text{KV cache 字节数} \;=\; \text{层数} \times \text{序列长度} \times \text{每层每 token 的 KV 字节数} \]

三个因子都是乘法关系：模型层数固定，于是 KV cache 随上下文长度线性膨胀——100 万 token 的上下文，就意味着 100 万份历史 K/V 堆在显存里。full attention（每个 token 都能看全部历史）的代价由此而来：显存放不下（HBM 容量）、搬不动（读写带宽）、算不完（打分计算量随长度平方增长）。

1.2 V4 世代的解法：压 entry 大小 → 压序列长度

V4.1 论文在 §2.3 开头给了一张很好的「地图」：KV cache 的开销可以沿三个乘法维度去压——

压缩维度思路代表方法
entry 大小（每 token 每 深度存多少字节）让多个注意力头共用一份 KV，或把 KV 投影到一个低维 latentGQA、MLA
序列维（多少 token 存一条）每 m 个 token 压缩成 1 条 entryDeepSeek-V4 的 CSA / HCA
层维（多少层各存一份）让一部分层复用别的层的缓存与检索结果IndexCache、YOIO、HySparse 等前人工作

表 1｜论文 §2.3 归纳的三个 KV 压缩维度。前两维是 V3→V4 世代的主战场，第三维是 V4.1（本讲）的新战场。

V4 世代做了什么？V4 采用「全局注意力分支 + 滑窗注意力（SWA）」的混合结构（论文 §1 回顾）：全局分支负责「看全部历史」，它的 KV 叫全局 KV，由两部分组成——main KV（真正参与注意力计算的主体）和 indexer K（给索引器用的检索钥匙）；SWA 只看最近一个窗口（如最近 128 个 token）的原始 token，窗口固定，所以 SWA 的 KV 存储量不随上下文增长。上下文足够长时，全局 KV 主导了运行时 KV cache 的体量，这就是 V4.1 要集中火力的靶子。

全局分支内部，V4 用 CSA（压缩稀疏注意力）解决「存」和「算」两件事（详见背景报告）：

  • 存：序列维压缩。每 m 个 token 经「可学习门控池化」压成 1 条 512 维的 main KV entry，entry 数从 N 变成 N/m；
  • 算：稀疏检索。一个轻量的 Lightning Indexer 用 indexer Q 和 indexer K 给每条 entry 打相关度分，每个查询只挑出得分最高的 Top-K 条 entry 参与真正的注意力计算——「先检索、后精读」，像搜索引擎先筛出前几页结果再逐条打开。

这条路线把「算」的成本大幅压低了（V4.1 论文 §1 承认：prior advances in sparse attention 已显著降低长序列计算成本），但论文紧接着指出新瓶颈：持久化存储（persistent KV cache）和数据搬运。全局 KV 仍要挤在 HBM 里、复制到 SSD 上做前缀复用，I/O 和互联带宽限制了缓存的迁移与加载——「存」成了压垮部署成本的大头。V4.1 的目标因此非常聚焦：把全局 KV 的字节数再往下压一个量级。

本节对 GQA/MLA/CSA/SWA 的白话展开，部分借用了 V4 论文与已有背景报告的结论（如 CSA 的门控池化压缩、Lightning Indexer 的先检索后精读），V4.1 论文正文只做了简要回顾；逐项技术细节请以背景报告为准。

1.3 前人在「层维」上走到了哪一步

论文 §2.3 还盘点了一层维压缩的已有尝试，并点出它们的不足（以下均为论文转述）：IndexCache 跨层复用 Top-K 索引、削减索引器计算，但「index reuse alone saves no main KV storage」——只省计算、不省存储；YOIO 全网只算一次稀疏路由、所有层共享，但「network-wide routing sharing limits performance」——共享得太狠、模型性能受损；HySparse 让稀疏层复用稠密层的 KV，但混合设计仍保留 full attention 层。论文的判词是：没有任何一种已有方法同时覆盖三个乘法维度。CSA2 的野心正是把三维一次性用满。

2. CSA2 总览：一份 KV，三种分工

2.1 CSA2 是什么

CSA2（Compressed Sparse Attention 2）是 V4 的 CSA 的第二代。它保留了 CSA 的骨架（论文 §2.3 原文概括）：

「Similar to CSA, CSA2 includes a lightweight indexer that scores the main KV entries using indexer Q and indexer K and selects the Top-K entries for each query. Each Q attends to the selected entries together with the layer-local sliding-window KV (SWA KV).」

（译：与 CSA 相同，CSA2 也含一个轻量索引器：用 indexer Q 给 main KV entry 打分（打分依据是 indexer Q 与 indexer K 的匹配），为每个查询选出 Top-K 条 entry；每个查询在「被选中的 entry + 本层滑窗 KV」上做注意力。）

在这个骨架上，CSA2 新增两件武器：跨层复用（§3，共享 main KV、indexer K、Top-K 索引）和层级稀疏索引器（§4，先粗后细的漏斗式检索）。同时把 CSA 的压缩器和索引器做了简化（§7 详述）。

2.2 三种模式：Full / Reindex / Reuse

每个 CSA2 层在部署前就被静态指定三种模式之一（论文 §2.3.1）。三种模式都做同样的事——用「本层的查询 Q + 被选中的 main KV entry + 本层滑窗 KV」算出注意力输出；区别只在三样东西从哪来：main KV、indexer K、Top-K 索引。

模式main KVindexer KTop-K 索引一句话人设
Full自己算自己算（从自己的 main KV 投影）自己全量打分选出「大厨」：从原料做到上菜
Reindex复用前面最近的 Full 层复用同一份用自己的 indexer Q 给复用的 indexer K 重新打分，选出新的 Top-K「复读生」：书是别人的，笔记自己做
Reuse复用前面最近的 Full 层—（不打分）复用前面最近的「出索引层」（Full 或 Reindex）的 Top-K「蹭读生」：书和笔记都用别人的

表 2｜CSA2 三种模式的分工（据论文 §2.3.1 与图 4 整理）。三种模式下，每层都保留自己的 main Q 与 SWA KV——局部、逐层的东西从不共享，共享的只有「全局 KV 与全局索引」这些层间高度冗余的部分。

图 1｜CSA2 三种模式的数据流（对应论文图 4）。绿色 = 本层现算；黄色 = 从最近的 Full 层复用 main KV 与 indexer K；红色 = 从最近的出索引层（Full 或 Reindex）复用 Top-K 索引。注意三点：① 三种模式都现算自己的 main Q 和 SWA KV；② Reuse 模式完全没有 indexer——这是「复用索引省计算」的落点；③ Reindex 模式是「共享但不僵化」的关键：KV 共享了，但每层仍能凭自己的 indexer Q 选出不同的 Top-K。

2.3 为什么「共享」在直觉上是成立的

不同层的注意力真的会看同一批历史 token 吗？经验上是：多层 Transformer 的注意力分布高度重叠——「这段话在讲什么」这个问题，第 10 层和第 14 层关心的答案位置往往差不多。V4.1 论文引用的三个前人工作（IndexCache / YOIO / HySparse）都验证了层间冗余真实存在，只是各自只敢共享一部分（索引或 KV）。CSA2 的赌注是：全局 KV 在层间冗余度足够高，可以用「静态分组 + 三模式分工」把冗余几乎榨干，同时用 Reindex 模式保留层间选择的差异度，用训练策略兜住精度。从 §6 的评测结果看，这个赌注赢了。

「层间注意力分布重叠」是本文为帮助理解补充的直觉解释；论文没有直接给出层间注意力重叠度的测量，只以前人工作效果作为间接证据。

3. 招式一：跨层 KV 与索引复用——共享的结构怎么组织

3.1 全模型的模式编排

V4.1-Flash 共 40 层 Transformer，被 CED 架构切成 20 层因果编码器（causal encoder）和 20 层解码器（decoder）（CED 本身是第 1 讲的主题：解码器的全局 KV 不是从各层隐状态算的，而是直接从编码器第 L/2 层的最终隐状态 \(H^{L/2}\) 投影出来，从而省掉一半 prefill 计算）。CSA2 只用在编码器后 18 层和解码器全部 20 层，压缩率不同：

部分注意力压缩率 m分组方式（论文 §4.2.1）
编码器第 1–2 层纯 SWA—不参与 CSA2
编码器第 3–20 层（18 层）CSA2，m=22（每 2 token 压 1 条 entry）3 组 × 6 层：每组第 1 层 Full，其余 5 层 Reuse
解码器全部 20 层CSA2，m=1（即 main KV 不压缩的特殊情形）15 组 × 4 层：第 1 组第 1 层 Full、其余 3 层 Reuse；第 2–5 组每组第 1 层 Reindex、其余 3 层 Reuse

图 2｜40 层的模式编排（据论文图 3 与 §4.2.1 绘制）。绿色 = Full（产 KV）、蓝色 = Reindex（借 KV、池内重选索引）、黄色 = Reuse（借 KV、借索引）、灰色 = 纯 SWA。所有 Reuse 层合计占总层数的 30/38 ≈ 79%。

3.2 共享的「源」：Full 层怎么产 KV

与 CED 结合时（论文 §2.3.1 末段），解码器中唯一那个 Full Mode 层的 main KV 并非从本层隐状态计算，而是从编码器最后一层（第 L/2 层）的隐状态 \(H^{L/2}\) 用逐层独立的投影矩阵投影得到（论文式 1）：

\[ C^{l} = H^{L/2}\, W^{KV}_{l}, \qquad Z^{l} = H^{L/2}\, W^{Z}_{l}, \qquad l > L/2 \]

逐符号解释（记号照录论文式 1）：

  • \(H^{L/2} \in \mathbb{R}^{N \times d}\)：编码器第 L/2 层（本模型即第 20 层）输出的隐状态，N 为序列长度、d=5120 为隐藏维——它承载了整段输入「消化完毕」的语义；
  • \(W^{KV}_{l}, W^{Z}_{l}\)：第 l 层专属的两组投影权重，把同一个 \(H^{L/2}\) 分别变成该层的 KV 载体 \(C^{l}\) 与「压缩权重」 \(Z^{l}\)（CED 论述部分称 C 为 KV entries、Z 为对应压缩权重）；
  • 关键含义：各层看的是同一份「原料」\(H^{L/2}\)，只是各自的「切法」（投影矩阵）不同。这就是跨层共享在数学上顺理成章的原因——解码器所有层的全局 KV 本来就出自同一个源头，让部分层连投影都省掉、直接借用别层的投影结果，只是把这个冗余推到极致。

编码器的 3 个 Full 层则照常从各自隐状态计算 main KV，并「由 main KV entry 经投影得到 indexer K」（论文 §2.3：CSA2 obtains indexer K by projecting main KV entries）——这一点与 V4 的 CSA 不同（CSA 的 indexer K 有独立的压缩路径），§7 详述。

3.3 复用链条与「省」的落点

把三种模式串成一句话：Full 层花全价生产 KV 和索引 → Reindex 层蹭 KV 但自己精挑索引 → Reuse 层连挑都懒得挑，直接用上游挑好的。论文明确区分了两种节省的落点（§2.3.1）：

  • 共享 main KV 与 indexer K → 省「存储」（"Sharing main KV and indexer K reduces cache storage"）：38 层的全局 KV 从 38 份减到 4 份；
  • 复用 Top-K 索引 → 省「计算」（"reusing Top-K indices avoids additional indexer computation"）：30 个 Reuse 层完全不跑索引器。

且两者解耦（"cache sharing and index reuse decoupled"）：一个层可以只借 KV、不借索引（Reindex），也可以两者都借（Reuse）。「解耦」是 CSA2 相对 YOIO（全网共享一路由、性能受损）的关键改良——想保留层间差异的层组用 Reindex，确认冗余的层组才用 Reuse。

此外论文 §3.2 给了一个部署侧的硬数字：纯 Reuse 层推理时只需 15 个 kernel（prefill）/ 11 个 kernel（decode）——索引器、压缩器全被裁掉之后，层的执行流程极其精简，kernel 融合后硬件可以全流水跑满。

4. 招式二：Hierarchical Sparse Indexer——先粗后细的检索漏斗

4.1 问题：剩下的索引器仍在全量打分

跨层索引复用砍掉了 30 个 Reuse 层的索引计算，但剩下 8 个出索引层（4 Full + 4 Reindex）里，每个索引器仍要「对全部因果可见上下文打分」。论文 §2.3.2 的原话：「For extremely long contexts, this cost remains a major computational bottleneck.」——100 万 token 的上下文，解码的每个新 token 都要对 100 万条 entry 打分 4 次（1 个 Full + 4 个 Reindex，Full 只在解码器算一次全量），这本身就是一笔可观的算力。

4.2 漏斗：三层筛子

论文的观察非常巧妙（§2.3.2）：「in the decoder, information from shallower indexers can naturally be used to restrict the candidates considered by deeper indexers without adding any extra state」——浅层索引器反正已经把全上下文打过分了，它的打分结果天然可以告诉深层索引器「值得看的地方在哪」，不需要额外维护任何状态。于是设计出三级漏斗（只在解码器使用）：

层级谁来做做什么规模
① 全量打分解码器第 1 个 Full 层的索引器对全部因果可见的 main KV 位置打分；先给自己选出 Top-512；再做分块初筛：把位置按 8 个一组分块，每块取块内最大索引分作为块分，选得分最高的 2,048 个块O(N)
② 建候选池同上（一次性的副产品）把被选块覆盖的所有位置收集成共享候选池：2,048 块 × 8 位置 = ≤16,384 个候选位置固定 ≤16,384
③ 池内精选后续 4 个 Reindex 层的索引器只对候选池内的位置打分，各自选出自己的 Top-512O(16,384) = 常数

表 4｜层级稀疏索引器的三级漏斗（论文 §2.3.2 与 §4.2.1 配置）。注意：候选池是所有出索引层共享的搜索域，但各层最终的 Top-512 选择可以不同。

用记号整理（论文以文字描述此流程，公式为本文按论文语义整理的记号）：对查询 t，设索引器对位置 i 的打分为 \(I_{t,i}\)，位置按每 8 个划入块 \(\mathcal{B}_j\)，则——

\[ b_j = \max_{i \in \mathcal{B}_j} I_{t,i} \qquad\text{（块分 = 块内最大索引分）} \]
\[ \mathcal{P} = \bigcup_{j \in \mathrm{TopK}_{2048}(\{b_j\})} \mathcal{B}_j, \qquad |\mathcal{P}| \le 2{,}048 \times 8 = 16{,}384 \qquad\text{（共享候选池）} \]
\[ \mathcal{S}^{l}_{t} = \mathrm{TopK}_{512}\big(\{\, I^{l}_{t,i} \;:\; i \in \mathcal{P} \,\}\big) \qquad\text{（Reindex 层 } l \text{ 池内选 Top-512）} \]

逐符号解释：\(I_{t,i}\) 是 indexer Q（每查询 32 个头、每头 128 维）与 indexer K 匹配产生的相关度分；\(b_j\) 是第 j 块的得分——取块内最大值而非平均值，意味着只要块里有一个强相关位置，整块就会被保送进候选池，宁可错收、不可漏收；\(\mathcal{P}\) 是候选池；\(\mathcal{S}^{l}_{t}\) 是第 l 层为查询 t 选出的 Top-512 entry 集合。

图 3｜层级稀疏索引器的检索漏斗（对应论文图 5 与 §2.3.2）。绿色方块是被选中的位置、蓝色矩形是按块分选中的块（论文图 5 的配色约定）。注意两个「不忘本」的设计：第一级 Full 层仍然扫全量（保证 recall 的源头）；候选池大小固定后，深层索引器的成本从 O(N) 变为 O(1)。

4.3 三个容易忽略的细节

  • 只在解码器用。论文明确 "used only in the decoder of CED to reduce this repeated scoring during decode"——它优化的是解码阶段逐 token 反复打分的开销；prefill 阶段全量打分只发生一次，本身不是瓶颈。
  • 训练感知、且在 post-training 引入。"The mechanism is training-aware and introduced in post-training: the candidate restriction is applied identically during training and inference"——训练时深层索引器就在同一个 16,384 的池子里学习选择，推理时才不会「考试题型变了」。若训练全量、推理限池，分布突变会伤精度；「训练即所见」是这类硬约束设计的标准姿势。
  • 零额外状态。候选池由第一级打分的副产品（块分）直接导出，不需要为它缓存任何东西——这也是标题里 "without adding any extra state" 的分量：省计算但不反弹存储。
「块分取 max 而非均值 ⇒ 宁可错收不可漏收」是本文对块级最大值池化的动机解读，论文未明说选 max 的理由；但「候选池大于最终 Top-K 集合」（论文原文 "a candidate pool larger than the final Top-K set"）确实体现了留冗余保召回的意图。

5. 训练怎么配合：Attention Sharing Training（§3.1.2）

5.1 共享会不会伤精度？

先给结论层面的证据（均为论文陈述）：

  • 预训练完全绕开 dense attention：「Sparse attention is trained from scratch at a sequence length of 64K, without any dense attention warmup stages」（§1）——稀疏注意力从零直接学，不需要「先稠密后稀疏」的过渡课程，且 45T token 训练「no instability」（§4.2.2）；
  • FP4 主 KV 缓存的 QAT 只带来 marginal 性能损失（§1：with only marginal performance degradation）；
  • 最终效果不降反升：V4.1-Flash 整体性能优于 V4-Flash（§1、§6），BPB 评测全面领先（论文图 6）；
  • 但论文诚实保留了边界：§6 承认「Potential selection errors in CSA2 … may still cause capability degradation in untested boundary cases」——CSA2 的选择错误在未覆盖的极端用例下可能造成能力退化，团队将持续扩充压力测试。这是「共享有代价」最直接的论文表述。

所以问题不是「共享不伤精度」，而是「用什么工程手段把共享的精度风险按住」。§3.1.2 给的答案是三件套——但它们的出发点其实不是精度，而是分布式训练的可行性：共享 KV 的层可能被切到不同的 pipeline stage（流水线并行是把 40 层切给多台 GPU 的标准做法），而传统训练框架假设「每层的模块只归自己的 stage 管」，跨 stage 共享参数根本没法直接跑。三件套分别是：

机制解决的问题怎么解决（论文原文转述）
Shadow indexers
（影子索引器）		共享的索引器参数被多个 stage 的层引用，但模块不能跨 stage 复用在每个参与 stage 放一个轻量可执行副本，同时保留唯一逻辑属主：属主负责参数优化与 checkpoint；副本靠「参数同步 + 梯度聚合」与属主保持一致。流水线调度器因此无需把共享层当特殊单元对待
Pipeline payload extensions
（流水线载荷扩展）		共享 KV 的生产层和消费层跨流水线边界时，中间表示与稀疏路由信息传不过去把这些状态并入现有的点对点通信路径，并按上下文并行（context parallelism）一致的方式切分——不额外复制数据，且保持对应梯度可回传
Micro-batch-level shared-state management
（微批次级共享状态管理）		多个微批次并发时，共享状态的生存期怎么管（何时可释放、重算时找谁要）统一跟踪前向、激活重算、反向传播中的共享状态，留到最后一个消费者用完才释放；同一套运行时抽象还管理 stage 布局与生产-消费关系，使注意力实现不依赖物理流水线布局

表 5｜Attention Sharing Training 三件套（论文 §3.1.2）。论文总结：配合对优化器、checkpoint、warm-up、计算图追踪的轻量适配，CSA2 可以「透明地」跑在既有分布式训练接口与流水线调度上。

5.2 训练侧的完整拼图

把散落在论文各处的训练相关决策拼到一起，可以看清「共享 KV 的模型是怎么被驯服的」：

  • 预训练：64K 序列长度从零直接训稀疏注意力（无 dense warmup），34T token 处扩到 1M（§4.2.2）。此时模型学的就是「在 Top-512 稀疏选择上做注意力」；
  • 后训练：层级稀疏索引器的候选池约束在 post-training 引入，且训练/推理完全一致（§2.3.2）；主 KV 的 FP4 量化感知训练（QAT）也在 post-training 加入（§2.4.4）；SWA Bounded Replay 的近似行为同样在后训练中模拟以做 train-aware adaptation（§3.2.2）。后训练承担了所有「推理近似行为」的适配教学；
  • 梯度语义：共享参数只有一个属主做优化（shadow indexer 机制），梯度经聚合回到属主——数学上等价于「一份参数、多处使用」的标准共享，不会出现多处各自更新导致的参数漂移。
「后训练承担所有推理近似行为的适配」是本文对论文散落信息的归纳性表述（原文分别陈述了 HSI、FP4 QAT、SWA Bounded Replay 三项在后训练引入，未使用这一总括说法）；「梯度聚合等价于标准参数共享」亦是基于 §3.1.2 文字的合理解读。

6.3 招式二的账：省的是算力

层级稀疏索引器不省字节、省算力。论文的表述是：对固定的候选池大小，「每个后续索引器每查询打分的头数（位置数）从随上下文线性变为常数」（"changes the per-query cost of deeper indexers from linear in context length to constant"）。以 1M 上下文为例（推断演算）：不设池时每个 Reindex 索引器每查询要打 100 万分；设池后只打 ≤16,384 分——4 个 Reindex 层合计少打约 400 万次分/查询。加上 30 个 Reuse 层完全不跑索引器（招式一的另一面）与 Reuse 层仅 15/11 个 kernel 的极简执行流，解码阶段每个 token 的注意力相关计算被压到与上下文长度近乎无关——这正是论文图 2 展示的「上下文从 4K 扩到 1M（256 倍），单 token Decode FLOPs 只增加 1/4」的重要贡献来源之一。

「4 个 Reindex 层合计少打约 400 万次分」与「Decode FLOPs 恒定的贡献来源」均为本文演算/归因，前者由论文配置数字直接推得，后者论文未做逐项归因。

7.2 代价与取舍

  • 精度面：复用意味着「层间选择不自由」。论文的兜底是三层的：Reindex 保留层间差异、训练-推理一致的候选池约束、FP4 QAT；最终评测全面占优。但 §6 明确承认 CSA2 潜在的选择错误是「尚未完全刻画的鲁棒性边界」，特别是稀疏检索 over 长上下文的极端情形是后续压力测试重点。
  • 实现复杂度面：静态模式编排本身简单（部署前定死），但训练系统要为跨 stage 共享补齐 shadow indexer、流水线载荷扩展、微批次共享状态管理三件套（§3.1.2）——这是不小的工程投入；推理侧反而变简单（Reuse 层 15/11 个 kernel）。
  • 灵活性面：模式是静态指定的，不随输入动态调整。论文没有给出「动态路由会不会更好」的讨论——这是设计空间的明确取舍：用灵活性换确定性与 kernel 融合友好性（推断）。
  • 候选池与 Top-K 的固定开销：16,384 池 + 512 Top-K 在短上下文时是纯开销（全量本来也不大），所以论文把层级索引器只放在解码器、且用「池大小固定」来控制上限——短上下文时第一级全量打分本身很便宜（推断）。

8. 本讲小结与自测

8.1 小结

  • 问题：稀疏注意力已把长上下文的「算」压下来后，全局 KV 的「存」与「搬」成为部署瓶颈（§1）；KV 压缩存在 entry 大小 / 序列 / 层三个乘法维度，前人无一同时覆盖（§2.3）。
  • 招式一（§2.3.1）：38 个 CSA2 层按 Full / Reindex / Reuse 三模式静态分工，全局 KV（main KV + indexer K）只存 4 份、Top-K 索引组内复用，且「缓存共享」与「索引复用」解耦；每层保留自己的 main Q 与 SWA KV。
  • 招式二（§2.3.2）：解码器层级稀疏索引器——第一级 Full 层全量打分（自用 Top-512 + 块分 max 池化选 2,048 块），导出 ≤16,384 位置的共享候选池，后续 Reindex 层池内选各自 Top-512；深层索引器每查询打分成本从 O(N) 降为 O(1)，且零额外缓存状态、训练感知。
  • 训练配合（§3.1.2）：shadow indexers / 流水线载荷扩展 / 微批次共享状态管理三件套让跨 stage 共享在分布式训练下透明运行；预训练从零直训稀疏（64K、无 dense warmup），后训练引入候选池约束与 FP4 QAT 并保持训练-推理一致。
  • 账本：890 B/token 全局 KV（≈V4-Flash 的 1/4、V1 的 1/437）≈ 跨层共享（约 11.6×，推断）× FP4 量化（约 1.9×，推断）的结果；层级索引器另省索引算力；持久 KV 靠「不再存 SWA KV + 全局 KV 减到 1/4」两个乘法因子降到 1/8（第 4 讲展开）。
  • 取舍：精度靠「Reindex 保留差异 + 一致性训练 + QAT」兜住，评测反超 V4-Flash；代价是训练系统工程量与静态编排的灵活性损失，论文 §6 诚实标注了极端边界下的鲁棒性待验证。

8.2 自测清单

Q1：CSA2 的三种模式分别复用什么、现算什么？

答：三种模式都现算本层的 main Q 与 SWA KV。Full 层现算 main KV、indexer K（由自己的 main KV 投影）并全量打分产出 Top-K；Reindex 层复用前面最近 Full 层的 main KV 与 indexer K，但用自己的 indexer Q 重新打分、选出新的 Top-K；Reuse 层把 main KV 和最近出索引层（Full 或 Reindex）的 Top-K 索引都借来，完全不跑索引器。（§2.3.1、表 2、图 1）

Q2：跨层共享省的是「存储」还是「计算」？索引复用呢？

答：共享 main KV 与 indexer K 省的是存储（全局 KV 从 38 份减到 4 份）；复用 Top-K 索引省的是计算（30 个 Reuse 层不做任何索引打分）。两者在 CSA2 中是解耦的——Reindex 模式就是「借 KV 但不借索引」的中间态。（§2.3.1）

Q3：层级稀疏索引器的漏斗有几级？每级保留多少？为什么块分取 max？

答：三级：① 解码器第 1 个 Full 层对全部因果可见位置打分（O(N)），自用 Top-512，并按 8 位置/块取块内最大分为块分、选出 2,048 块；② 被选块覆盖的位置并集构成 ≤16,384 个候选位置的共享候选池；③ 后续 4 个 Reindex 层只在池内打分、各选自己的 Top-512。块分取 max 意味着块内只要有一个强相关位置整块入选——偏向保召回（此动机解读为推断，候选池大于 Top-K 集合为论文原文）。（§2.3.2、§4.2.1、图 3）

Q4：层级稀疏索引器为什么不增加存储负担？它优化的是哪个阶段的成本？

答：候选池由第一级打分的副产品（块分排序）直接导出，"without adding any extra state"——不需要为池缓存任何数据。它优化的是解码（decode）阶段的成本：解码时每个新 token 的查询都要让各出索引层重新打分，池化把这从「随上下文线性」变成「常数」；且只用于解码器。（§2.3.2）

Q5：Attention Sharing Training 三件套各自解决什么问题？

答：① Shadow indexers：共享索引器被切到多个 pipeline stage 时，在各 stage 放可执行副本、唯一逻辑属主管优化与 checkpoint，靠参数同步+梯度聚合保持一致；② Pipeline payload extensions：共享 KV 的生产/消费层跨流水线边界时，把中间表示与稀疏路由信息并入现有 P2P 通信、按上下文并行一致切分；③ Micro-batch 共享状态管理：跟踪并发微批次的共享状态生存期，留到最后一个消费者用完才释放。（§3.1.2、表 5）

Q6：890 B/token 里，跨层共享和 FP4 各贡献多少？（哪些是论文事实、哪些是推断？）

答：事实：总量 890 B/token、为 V4-Flash 的约 1/4、FP4 相对 FP8 几乎减半、全局 KV 共 4 份（3 编码器 Full + 1 解码器 Full 层各产一份）、编码器 m=2 / 解码器 m=1。推断：按 512 维 latent FP4 ≈288 B/条、indexer K 128 维 FP4 ≈72 B/条推算，main KV 共 720 B + indexer K 共 180 B ≈ 900 B，与 890 B 吻合到 1%；由此反推跨层共享（相对无共享 FP8 基线）贡献约 11.6×、FP4 约 1.9×（图 4）。论文未给出逐项分解。
