前置：第 0 讲（FFN、参数量 vs 计算量、softmax/sigmoid、top-k）

本讲不涉及 DeepSeek 特有设计——先把 MoE 的通用原理与通病讲透，第 2 讲起再看 DeepSeek 如何逐个击破。

本讲目标：① 搞清稠密模型「容量-算力绑死」的困境；② 掌握 MoE 三件套（专家 / 门控 / top-k 稀疏激活），用 3 个专家的小例子完整手算一遍前向传播；③ 理解组合空间 \(\binom{N}{K}\) 为什么是「自由度」；④ 直面 MoE 的第一个大麻烦——负载不均，以及教科书解法「辅助均衡损失」的原理与副作用；⑤ 认清贯穿 DeepSeek 五代的核心矛盾：均衡要雨露均沾，能力要术业专攻。

1. 稠密模型的困境：想变聪明，就得变贵

第 0 讲说过，稠密模型里参数量 = 每 token 计算量，两者绑死。这带来一条残酷的取舍链：

  • 模型的「知识」基本存在 FFN 的权重里。想让模型知道更多事（医学、法律、代码、十几种语言……），就得加大 FFN、堆参数。
  • 但稠密模型每生成一个字，所有参数都要参与一遍乘加。参数翻倍 = 推理成本翻倍、训练成本大约也翻倍。
  • 结果是：一份 70 亿参数的稠密模型，绝大部分算力花在「对这个 token 其实没多大用处」的参数上——算一道数学题时，烹饪知识也在空转。
换个说法稠密模型像一家「每来一位客人，全体厨师都各做一道菜端上去」的餐厅——浪费显而易见。自然的改进：客人点什么菜，指派对口的厨师去做。这就是 MoE。

2. MoE 三件套：专家、门控、稀疏激活

MoE（Mixture of Experts，混合专家）层把原来的一个大 FFN 换成三样东西：

  1. \(N\) 个专家（expert）：\(N\) 个结构完全相同、权重各自独立的小 FFN 并排放着。每个专家都是一个完整的小加工车间（第 0 讲的 SwiGLU 三件套），只是彼此不知道对方的存在。
  2. 门控 / 路由器（gate / router）：一个可学习的小矩阵 \(W_g\)（形状 \(d \times N\)）。每个 token 的状态向量乘上它，得到 \(N\) 个分数——「这个 token 与每个专家的相关度」。
  3. top-\(K\) 稀疏激活：分数只用来选人。挑分数最高的 \(K\) 个专家（比如 384 个里挑 6 个），其余 \(N-K\) 个完全不参与计算；被选中的专家输出按分数（归一化后）加权求和，作为这一层的输出。

图 1-1｜MoE 层结构。门控给出打分（蓝色），top-2 做硬选择（橙色），只有绿色专家真正计算，输出加权相加。DeepSeek-V4 的真实配置是 384 个路由专家选 6 个——图缩小到 4 选 2 便于看清。

3. 完整手算一个最小例子（3 个专家，top-2）

把第 0 讲的零件组装起来，走一遍完整前向传播。设定：\(N=3\) 个专家，\(K=2\)，某个 token 的状态 \(x\) 已经算出门控分数。专家本身的输出我们直接给定（不然手算几千次乘法）。

3.1 第一步：门控打分

\(x\) 乘上门控矩阵，得到 3 个原始分数 \(z = [2.0,\ 1.0,\ 0.1]\)。用第 0 讲算好的 softmax：

\[ s = \mathrm{softmax}(z) = [0.659,\ 0.242,\ 0.099] \]

3.2 第二步：top-2 选择

分数最高的是 E1（0.659），其次是 E2（0.242）。E3（0.099）落选，输出视为 0。softmax 本身已归一化（总和为 1），所以权重可以直接用：\(g_1 = 0.659\)，\(g_2 = 0.242\)。

为什么是「加权混合」而不是「全权交给第一名」？三个理由：① 第二名的意见也有价值，硬丢弃信息浪费；② 加权是连续运算，分数本身可以接受梯度训练——门控靠「调分数」学习，全靠 top-k 硬选择就无梯度可学（第 0 讲的「梯度失明」）；③ 混合相当于按需「定制」了一个专属 FFN：这个 token 的加工方式 = 0.659 份 E1 + 0.242 份 E2。

3.3 第三步：专家计算与加权求和

假设这个 token 是「红烧肉的做法」，两个被选中专家的输出恰好是：E1 输出 \(+1.0\)（美食特征强烈激活），E2 输出 \(-0.5\)。最终输出：

\[ y = 0.659 \times 1.0 + 0.242 \times (-0.5) = 0.659 - 0.121 = 0.538 \]

这就是一个 token 在一个 MoE 层的全部经历。换成真实的 V4：384 个专家选 6 个、61 层每层都来一遍——但每一层的工序都和上面三步完全相同。

3.4 算一笔账：参数省在哪、算力省在哪

口径稠密 FFN（相当于 1 个大专家）MoE（3 个小专家，top-2）
参数量（总容量）3 份3 份（3 个专家并存）

最后一行是 MoE 真正的威力所在：同样的参数库存，稠密模型只有「一种加工方式」，而 3 选 2 的 MoE 有 3 种不同的有效 FFN（E1+E2、E1+E3、E2+E3），随 token 挑选。专家越多、组合越多，模型表达不同 token 的能力就越细。

4. 组合空间：MoE 的「自由度」从哪来

把组合数算清楚。从 \(N\) 个专家里选 \(K\) 个的组合数是 \(\binom{N}{K} = \frac{N!}{K!(N-K)!}\)：

N（专家数）K（激活数）组合数 \(\binom{N}{K}\)直观数量级

64674,974,368DeepSeek-V1 16B 的配置
3846\(\approx 3.9\times10^{13}\)DeepSeek-V4-Pro 的配置

同样激活 2 个专家，「64 选 2」比「16 选 2」的组合数多 17 倍。而如果把大专家切成小专家（同样的激活参数量下从 16 选 2 变成 64 选 8），组合数会从 120 暴涨到 \(\binom{64}{8} \approx 44\) 亿——这个「切小专家」正是 DeepSeek 第 2 讲的主角（细粒度专家）。

直觉组合数 = 模型能搭配出的「专家团队方案」总数。方案越多，不同类型的 token 越能找到量身定制的团队；但每个专家也分得更薄，训练更难照顾到每一个人——一切 MoE 设计的拉扯都围绕这里。

5. 麻烦来了：负载不均（load imbalance）

5.1 现象

理想世界里，\(N\) 个专家平分所有 token，每人接待 \(K/N\) 的流量。现实里训练早期常常长成这样：

图 1-2｜负载不均的两个受害者：速度（被最挤的专家拖慢）与容量（闲置专家学不到东西，总参数虚高）。

5.2 为什么会这样：赢者通吃的正反馈

训练刚开始，专家权重随机，打分差距不大。但任何一点微小的随机优势都会自我强化：

  1. 某专家 E3 分数偶然略高 → 更多 token 被分给它 → 它在「服务这些 token」中更新权重，越练越顺手；
  2. 越顺手 → 门控给它的分数越高 → token 更往它挤；
  3. 正反馈循环。同时冷门专家接不到活，得不到梯度，越来越「笨」，分数越来越低。

第 0 讲讲过 softmax 的「指数放大差距」脾气——它让这个循环加速。放到「组合空间」的视角：负载不均意味着 3900 万种团队方案里，模型实际反复使用的那几种寥寥无几——组合自由度被大量浪费。

5.3 教科书解法：辅助均衡损失（auxiliary balance loss）

Switch Transformer / GShard 时代的标准解法：在语言建模损失之外，额外加一项惩罚，谁偏心就罚谁：

\[ \mathcal{L}_{aux} = \alpha \cdot N \sum_{i=1}^{N} f_i \cdot P_i \]

两个量都按 batch 统计：

  • \(f_i\)：专家 \(i\) 的实际接待占比（它接到的 token 数 ÷ 总 token 数），衡量「分给它的活多不多」；
  • \(P_i\)：专家 \(i\) 的平均门控分数（softmax 后的概率平均值），衡量「门控有多想选它」。

手算验证它的均衡效果。设 2 个专家、α=1、N=2，两种情形：

情形\(f\)\(P\)\(\mathcal{L}_{aux} = 2\sum f_i P_i\)
严重偏心：80% token 挤 E1，且门控分数也偏向 E1[0.8, 0.2][0.8, 0.2]\(2(0.8{\times}0.8 + 0.2{\times}0.2) = 2 \times 0.68 = \mathbf{1.36}\)
完美均匀[0.5, 0.5][0.5, 0.5]\(2(0.25 + 0.25) = \mathbf{1.0}\)（最小值）

数学上可以证明：\(f\) 与 \(P\) 都均匀时乘积和最小——所以「压低这项损失」就是「逼着负载变均匀」。

5.4 代价：在主目标里掺沙子

问题在于这项损失直接参与反向传播。它的梯度会去改写门控分数：「E1 太挤了，把所有 token 对 E1 的分数调低」——哪怕这个 token 真正需要的正是 E1。它奖励的不是「选得对」，而是「选得匀」。

于是出现一对根本冲突：

  • 语言建模损失（主目标）希望：专家特化——每个专家把某一类 token 做到极致，热门专家就该热；
  • 均衡损失希望：雨露均沾——大家都别太挤。

两者在梯度里直接打架，最终模型是「会做题」和「守纪律」的妥协产物。妥协多少取决于权重 α：调大了伤模型质量，调小了均衡不住。这就是 DeepSeek 在第 2 讲要拆的第一颗雷——他们最终找到的办法堪称优雅：把「均衡」从损失函数里拿出来，挪进那个梯度看不见的角落（回忆第 0 讲：top-k 选择是梯度失明的）。

7. 核心矛盾总结：均衡 vs 特化

把本讲浓缩成一张表——这张表就是整个 DeepSeek MoE 演进史的「剧情大纲」：

均衡（工程友好）负载均匀：没有专家挤爆、没有专家闲置奖励选冷门、惩罚选热门
特化（质量所在）术业专攻：热门专家就该热，冷门专家忍痛让贤完全按 token 的需要来选，别掺纪律条款

8. 自查清单

  1. MoE 层的三件套是什么？各自可学习吗？（专家 FFN 可学习；门控矩阵可学习；top-k 是固定工序，无参数）
  2. 为什么输出是「加权混合」而不是只取第一名？（信息利用 + 可导性 + 每 token 定制有效 FFN）
  3. 负载不均的两类受害者分别是谁？（过载专家拖慢系统；闲置专家学不到东西、白占显存）
  4. 辅助均衡损失为什么会伤模型？（它的梯度直接改写门控分数，强迫 token 去次优专家，与特化冲突）
