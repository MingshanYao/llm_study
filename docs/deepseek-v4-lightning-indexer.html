TL;DR：Lightning Indexer（闪电索引器）是 DeepSeek 稀疏注意力（DSA）体系里独立于主注意力的可学习打分模块：用少量小维度索引头（64 头 × 128 维）对全部候选算一个标量索引分 \(I_{t,s} = \sum_h w^I_{t,h}\cdot\mathrm{ReLU}(q^I_{t,h}\cdot K_s)\)，再 top-k 选出稀疏注意力的参与集合。它存在的根本原因：top-k 不可微、主注意力分数既贵又逐头分歧，无法直接当排序信号用。V3.2 中它在 token 粒度上选 top-k=2048 个 token；V4 中索引器自己的 KV 也经过同一套压缩器压成 128 维 entry（\(K^{\mathrm{I,Comp}}\in\mathbb{R}^{\frac{n}{m}\times c_I}\)），选择粒度变成「压缩 entry」，候选数与索引缓存都 ÷4。索引器 QK 路径做了 FP4 量化感知训练、索引分数存 BF16，使 top-k 选择提速 2×、召回 99.7%。1M 上下文解码时，indexer 打分是 CSA 层注意力侧的主要 FLOPs 来源——它的每一点精简都直接兑现为端到端效率。

1. 为什么需要独立的 Lightning Indexer

稀疏注意力要做的事很朴素：对每个 query token，从全部历史候选里挑出少数几个参与真正的注意力计算。难点在于「挑」本身——这个挑选信号从哪来？直接用主注意力的分数做 top-k 行不行？论文与源码给出的答案是：不行，需要一个独立、轻量、可训练的索引器，理由有四条。

1.1 top-k 不可微，选择必须有自己的训练通路

top-k 是离散操作，没有梯度。如果稀疏模式由主注意力的分数隐式决定，模型没有任何直接监督信号告诉它「该选哪些 entry」。V3.2 的解法是把「打分」变成显式模块并配上专门的对齐目标：稠密 warm-up 阶段冻结除 indexer 外的全部参数，把主注意力各头分数求和、L1 归一化成目标分布 \(p_{t,:}\)，用 KL 散度把 indexer 输出对齐上去（V3.2 论文 §2.1.1，p.4，式 3）：

\[ \mathcal{L}^{\mathrm{I}} = \sum_t D_{\mathrm{KL}}\!\left(p_{t,:}\,\|\,\mathrm{Softmax}(I_{t,:})\right) \]

稀疏训练阶段再把这个 KL 限制在被选中的集合 \(S_t\) 内（式 4），并且把 indexer 的输入从计算图上 detach——indexer 只从 \(\mathcal{L}^{\mathrm{I}}\) 学习，主模型只从语言建模损失学习，两条优化通路互不干扰。

1.2 top-k 要求全量扫描，扫描者必须便宜

要选出 top-k，就必须对全部候选打分。如果用主注意力来打分，等于先做一遍完整的 \(O(L^2)\) 注意力再稀疏化，稀疏化就失去了意义。所以打分者必须比主注意力便宜得多：indexer 只有 64 个头、每头 128 维（主注意力 V4-Pro 是 128 头 × 512 维），V3.2 论文直言「indexer 仍具有 \(O(L^2)\) 复杂度，但其计算量远小于 MLA」（§2.3，p.5）——便宜，正是它能承担「全量扫描」这一职责的前提。

1.3 主注意力分数是逐头的，top-k 需要单一标量序

核心注意力中每个 query head 有自己的分数分布；而为了 kernel 效率，同一 token 的所有 query 头必须共享同一批 KV entry（V3.2 论文 §2.1：「each key-value entry must be shared across multiple queries for computational efficiency」）。这意味着 top-k 集合必须是唯一的——需要把多头意见汇成一个标量分。indexer 的设计恰好就是这个汇合器：\(w^I_{t,h}\) 是由当前 query token 动态生成的逐头权重（V4 式 15），对 64 个索引头的 ReLU 分数加权求和得到单一 \(I_{t,s}\)（式 16）。它不是「主注意力分数的平均」，而是一个参数独立、专门为排序训练的轻量多头打分器。

1.4 精度–开销解耦：打分可以牺牲精度，注意力不能

ReLU 的选用论文说得直白：「We choose ReLU as the activation function for throughput consideration」（V3.2 论文 p.3）——ReLU 计算与硬件实现都极简，且打分是原始 logit（不做 softmax），单调性保序，直接可 top-k。更重要的是，indexer 小而独立，可以单独压到极低精度而不伤主注意力：V3.2 说它「can be implemented in FP8」（p.3），V4 更进一步把 QK 路径做 FP4、索引分数存 BF16（§2.3.4、§5.2.1）。打分错一点的代价只是选错 entry（损失一点召回），而参与计算的注意力内容始终保持高精度——「粗筛可以糙，精算必须准」。

还有一条论文未明说的隐含原因：解码阶段稀疏 kernel 只读被选中的 entry，主注意力分数对未被选中的候选根本算不出来（先有选择、后有分数的鸡生蛋问题），所以全局排序信号只能来自一个能廉价访问全量候选的旁路模块。这是对 §1.2 的工程化补充理解。

2. V3.2 → V4：从 token 粒度到 entry 粒度

Lightning Indexer 首次提出于 DeepSeek-V3.2 的 DSA。两代的打分公式同构——逐头内积、ReLU、逐头权重加权求和——变的是索引 key 的粒度：

\[ \text{V3.2（式 1）}:\ I_{t,s} = \sum_{j=1}^{H^I} w^I_{t,j}\cdot \mathrm{ReLU}\!\left(q^I_{t,j}\cdot k^I_s\right),\quad k^I_s\in\mathbb{R}^{d_I}\ \text{逐 token 一条} \]
\[ \text{V4（式 15–16）}:\ I_{t,s} = \sum_{h=1}^{n^I_h} w^I_{t,h}\cdot \mathrm{ReLU}\!\left(q^I_{t,h}\cdot K^{\mathrm{I,Comp}}_s\right),\quad K^{\mathrm{I,Comp}}\in\mathbb{R}^{\frac{n}{m}\times c_I}\ \text{逐压缩 entry 一条} \]

V4 论文（§2.3.1，p.10）只加了一句话：「CSA 用与 \(C^{\mathrm{Comp}}\) 相同的压缩操作得到压缩索引 key \(K^{\mathrm{I,Comp}}\in\mathbb{R}^{\frac{n}{m}\times c_I}\)，其中 \(c_I\) 是索引头维度」。变化全在这句话里：

维度V3.2（DSA，token 粒度）V4（CSA，entry 粒度）
候选单元单 token 的 MLA latent \(c_s\)压缩 entry（每 m=4 个 token 压 1 条）
索引 key\(k^I_s\in\mathbb{R}^{d_I}\)，逐 token 缓存\(K^{\mathrm{I,Comp}}\in\mathbb{R}^{\frac{n}{4}\times 128}\)，逐 entry 缓存（\(c_I=128\)）

索引 KV 缓存每 token 1 条 \(d_I\) 维每 4 token 1 条 128 维 → 条数 −75%

图 1｜两代索引器的粒度对比（对照 V3.2 论文式 1 与 V4 论文式 13–17）。核心差异在最左一格：V4 先把索引 key 本身压到 1/m（m=4），后续每一环——打分量、排序量、缓存条数——都跟着 ÷4；且「选择单元」与「注意力单元」合一，选中即可用。

2.1 为什么 entry 粒度更省

  • 打分候选数 ÷4：打分是对全部候选的扫描，候选从 L 个 token 变成 n/4 个 entry，打分 FLOPs 与 top-k 排序开销同比例下降；
  • 索引缓存条数 ÷4：索引 key 与主 KV 用同一压缩节奏（每 4 token 1 条），缓存条数直接减为 1/4，且索引头维度只有 128（主 entry 是 512）；
  • 选择单元 = 注意力单元：V3.2 选出 token 后，主注意力还要读这些 token 的 latent 向量；V4 中被选中的 entry 本身就是主注意力的 K=V（SKV-MQA），选择结果即取即用，没有第二跳检索；
  • 覆盖面反而更大：k=1024 条 entry 每条代表 4 个 token 的信息，等效覆盖约 4096 token，比 V3.2 的 2048 token 覆盖更大，而排序的候选规模（n/4）与选中数（1024）都不吃亏。论文也点明「相对 V3.2 选择了更小的 top-k 以提升短中文本效率」（§2.3.4，p.13）。

3. 结构走查：一次打分的数据流（V4-Pro 数）

以 DeepSeek-V4-Pro 为例（\(d=7168\)、\(n^I_h=64\)、\(c_I=128\)、\(d_c=1536\)、top-k=1024，论文 §4.2.1 p.25，与 config.json 一致）。对 query token \(t\)：

\[ c^Q_t = h_t\cdot W^{DQ} \in \mathbb{R}^{1536} \quad (13) \qquad [q^I_{t,1};\dots;q^I_{t,64}] = q^I_t = c^Q_t\cdot W^{IUQ} \in \mathbb{R}^{64\times128} \quad (14) \]
\[ [w^I_{t,1};\dots;w^I_{t,64}] = w^I_t = h_t\cdot W^{w} \in \mathbb{R}^{64} \quad (15) \qquad I_{t,s} = \sum_{h=1}^{64} w^I_{t,h}\cdot \mathrm{ReLU}\!\left(q^I_{t,h}\cdot K^{\mathrm{I,Comp}}_s\right) \quad (16) \]
\[ C^{\mathrm{SprsComp}}_t = \left\{ C^{\mathrm{Comp}}_s \ \middle|\ I_{t,s}\in \mathrm{Top\text{-}k}(I_{t,:}) \right\} \quad (17) \]

三个值得注意的设计点：

  • 索引 query 走低秩：先降到 \(d_c=1536\) 再升到 \(64\times128=8192\) 维。参数量 \(7168\times1536 + 1536\times8192 \approx 13.6\,\mathrm{M}\)，若直接升维 \(7168\times8192\approx 58.7\,\mathrm{M}\)，省 4 倍以上；
  • latent \(c^Q_t\) 一份两用：论文 p.11 明确「the latent query vector \(c^Q_t\) is shared with that used for the indexer queries」——主注意力的 query 升维（式 18）与索引 query 升维（式 14）从同一个 latent 出发，一次降维、两处受益。代码里就是同一个 qr 张量先后喂给两条 wq_b（见 §6.3）；
  • 逐头权重 \(w^I_t\) 不走低秩：只有 64 维，直接 \(h_t\cdot W^w\)（\(W^w\in\mathbb{R}^{7168\times64}\)）一条独立投影。它承担 §1.3 说的「多头 → 标量」汇合，必须逐 token 动态生成——相关性模式随 query 内容变化，静态权重退化成固定平均。

3.1 索引器的因果性与位置编码

  • 因果掩码：式 16 只对「前序压缩块」\(s < \mathrm{Floor}(t/m)\) 打分（论文 p.10）。代码在 prefill 时用 mask 把未来 entry 的分数置 −inf（model.py:424–426），与公式一致；
  • 部分 RoPE：索引 query 与索引 key 都只对最后 64 维（rope_head_dim）施加 RoPE（model.py:413 与压缩器内部），与主 KV 同款位置编码方案，保证索引分对相对位置敏感；
  • Hadamard 旋转 ≠ RoPE：索引器的压缩器以 rotate=True 构造，池化完成后对整条 128 维 entry 做 rotate_activation（随机 Hadamard 旋转，model.py:247–252，注释写明目的是「spread information across dims before FP8 quant」）再做 FP4 量化——这是为低精度量化服务的能量摊平，与位置编码无关，两件事共用「旋转」一词但语义完全不同。

4. 索引器的 KV cache：独立布局与体积

索引器给 KV cache 引入了一套维度与主注意力不同的额外条目（论文 §3.5.1，p.21–22；图 6 的缓存布局里 CSA Indexer KV 与 CSA Main KV、HCA KV 同块分段共存）。布局与分块对齐的细节本站已有专文：deepseek-v4-kvcache.html §2、§4（Indexer 段「一次压缩、两份产出」「写入节奏」「解码四步旅程」三个特写），此处只补代码视角：

  • 独立缓冲：Indexer 类有自己的 kv_cache，形状 (max_batch_size, max_seq_len//4, 128)（model.py:399）——每个 CSA 层一份，每 4 个原始 token 占 1 个槽位、每槽 128 维；
  • 与主缓存的关系：主注意力的 Attention.kv_cache 是「SWA 段 + 压缩段」合一的 512 维缓冲（model.py:474、491）；索引器缓冲与之平行、互不混用。以元素量计，索引缓存是主压缩缓存的 \(128/512 = 1/4\)；
  • score_state 不是索引缓存：score_state（连同 kv_state）注册在压缩器 Compressor 类上（model.py:303–304），装的是还没攒满压缩窗口的在途 token 的门控分数与 KV（padding 为 −inf），大小与上下文长度无关，属于「状态缓冲」，与随序列线性增长的索引 entry 缓存是两类东西。索引器的压缩器是独立实例，自然也有一套自己的 kv_state/score_state（在 model.py:408–410 惰性绑定到 Indexer.kv_cache 上写入）。
每条索引 entry 的字节数取决于存储精度：论文口径下 QK 激活按 FP4 缓存加载（§5.2.1），则约 128×0.5=64 B/条；参考实现当前用 BF16 存（model.py:419 注释原文「kv could also use fp8 format, though current implementation uses bf16」），则约 256 B/条。主 entry（512 维，RoPE 64 维 BF16 + 其余 FP8）约 576 B/条。逐条目字节的推算口径详见 kvcache 报告 §6。

5. 训练与推理代价

5.1 训练：V3.2 的门控损失，V4 的暖启安排

V3.2（写明了损失）：两阶段。①稠密暖启：冻结除 indexer 外的全部参数，以「主注意力各头分数求和 + L1 归一化」为目标分布，KL 损失（式 3）只训 indexer——学习率 \(10^{-3}\)，仅 1000 步（每步 16 条 128K 序列，共 2.1B token）；②稀疏训练：引入 top-k=2048 后，KL 损失只在被选集合 \(S_t\) 内计算（式 4），indexer 输入 detach、与主模型分别优化，训 15000 步共 943.7B token（V3.2 论文 §2.1.1，p.4）。

V4（只写安排，未写损失）：预训练先用稠密注意力训 1T token，在序列长度 64K 处引入稀疏；「引入稀疏时，先安排一个短暂阶段 warm up CSA 的 lightning indexer，随后全程以稀疏注意力训练」（§4.2.2，p.24）。论文没有写明 V4 的 indexer 暖启用什么损失，也未提 KL/gating 损失是否沿用——见 §7 边界条目。

V4 的量化感知训练（QAT，§5.2.1，p.33）：后训练阶段对两处做 MXFP4 量化感知训练——MoE 专家权重，以及 CSA 索引器的 QK 路径（QK 激活的缓存、加载、乘法全在 FP4 下）；同时把索引分数 \(I_{:,:}\) 从 FP32 量化到 BF16。后一项优化使 top-k 选择器提速 2×，KV entry 召回率保持 99.7%。RL/推理 rollout 阶段直接用原生 FP4 权重，保证与线上部署行为一致。

5.2 开销的账：indexer 花了多少，省了多少

indexer 的额外开销在三处：①两条投影（低秩 query + 64 维权重，一次性的小矩阵乘）；②索引 entry 的压缩与缓存（每 4 token 一条 128 维）；③逐 query 对全部候选的打分（这是主体）。它换来的：主注意力从对 \(L\) 个候选的稠密计算降为对 \(k\) 条 entry 的稀疏计算。

以 V4-Pro、1M 上下文、CSA 层解码一步为口径核算（论文未给出该拆分，此为推断核算）：

项目规模每 token FLOPs（×2 乘加口径）需读取的量
indexer 打分（式 16）候选 n/4 = 250,000 条 × 64 头 × 128 维≈ 4.1 GFLOP（FP4 下执行）全部索引 entry：250K × 128 维
主注意力（式 18–19）top-k = 1024 条 × 128 头 × 512 维（QK+AV）≈ 0.27 GFLOP仅被选中的 1024 条 entry

表 2｜1M 上下文解码一步的单层拆分（推断核算，非论文数字）。indexer 打分的 FLOPs 约为主注意力的 15 倍、但只有稠密注意力的约 1/16——它是稀疏化后注意力侧的主要剩余开销。

由表 2 可得一个论文未明说但数据支持的结论：在 1M 上下文的解码阶段，indexer 打分是 CSA 层注意力侧 FLOPs 的主导项。这解释了论文三项优化的着力点——entry 粒度（候选 ÷4）、QK 路径 FP4（QK 是打分的主体，矩阵乘可由 FP4 tensor core 加速）、索引分数 BF16（top-k 选择器 2× 提速）——每一项都直接压这根最粗的杆。同时「99.7% 召回」说明 FP4 打分的排序质量损失很小。Prefill 侧同理：V3.2 已承认 indexer 是 \(O(L^2)\) 剩余项，V4 用压缩把常数再除以 4。

6. 官方代码走读（inference/model.py，commit b5968e9）

6.1 Indexer 类：结构定义

class Indexer(torch.nn.Module):
    """Selects top-k compressed KV positions for sparse attention via learned scoring.
    Has its own Compressor (with Hadamard rotation) to build compressed KV for scoring."""

    def __init__(self, args: ModelArgs, compress_ratio: int = 4):
        super().__init__()
        self.dim = args.dim
        self.n_heads = args.index_n_heads            # 64
        self.head_dim = args.index_head_dim          # 128
        self.index_topk = args.index_topk            # 1024
        self.q_lora_rank = args.q_lora_rank          # 1536
        self.wq_b = ColumnParallelLinear(self.q_lora_rank, self.n_heads * self.head_dim)
        self.weights_proj = ColumnParallelLinear(self.dim, self.n_heads, dtype=torch.bfloat16)
        self.softmax_scale = self.head_dim ** -0.5
        self.compress_ratio = compress_ratio

        self.compressor = Compressor(args, compress_ratio, self.head_dim, True)
        self.register_buffer("kv_cache", torch.zeros(args.max_batch_size,
            args.max_seq_len // compress_ratio, self.head_dim), persistent=False)

6.2 打分与 top-k：式 15–17 的逐行对应

    def forward(self, x: torch.Tensor, qr: torch.Tensor, start_pos: int, offset: int):
        ...
        q = self.wq_b(qr)                                  # 式 14：q^I = c^Q_t · W^IUQ
        q = q.unflatten(-1, (self.n_local_heads, self.head_dim))
        apply_rotary_emb(q[..., -rd:], freqs_cis)          # 部分 RoPE：最后 64 维
        q = rotate_activation(q)                           # Hadamard 旋转（摊平离群值）
        # use fp4 simulation for q and kv in indexer
        fp4_act_quant(q, fp4_block_size, True)             # QK 路径 FP4（QAT 一致性）
        self.compressor(x, start_pos)                      # 压出索引 entry 并写入 kv_cache
        weights = self.weights_proj(x) * (self.softmax_scale * self.n_heads ** -0.5)
        # We performed QAT here, kv could also use fp8 format, though current implementation uses bf16
        index_score = torch.einsum("bshd,btd->bsht", q, self.kv_cache[:bsz, :end_pos // ratio])
        index_score = (index_score.relu_() * weights.unsqueeze(-1)).sum(dim=2)   # 式 16
        if world_size > 1:
            dist.all_reduce(index_score)
        if start_pos == 0:
            mask = torch.arange(seqlen // ratio).repeat(seqlen, 1) >= \
                   torch.arange(1, seqlen + 1).unsqueeze(1) // ratio   # s < Floor(t/m)
            index_score += torch.where(mask, float("-inf"), 0)
        topk_idxs = index_score.topk(min(self.index_topk, end_pos // ratio), dim=-1)[1]
        if start_pos == 0:
            mask = topk_idxs >= torch.arange(1, seqlen + 1).unsqueeze(1) // ratio
            topk_idxs = torch.where(mask, -1, topk_idxs + offset)
        else:
            topk_idxs += offset                            # 指回主缓存中压缩段的位置
        return topk_idxs

摘自 inference/model.py:402-433。逐段对应：einsum("bshd,btd->bsht") 一次算出 [seq, entry, head] 的三维权内积，relu_() 原地 ReLU，再乘逐头权重 weights 沿头维求和——正是式 16 的 \(\sum_h w^I_{t,h}\cdot\mathrm{ReLU}(q^I_{t,h}\cdot K_s)\)；权重乘上 \(1/(\sqrt{128}\cdot\sqrt{64})\) 的固定尺度稳定分数幅值；prefill 掩码实现式 16 的「\(s<\mathrm{Floor}(t/m)\)」因果条件；topk 即式 17。offset 是因为主注意力的 kv_cache 前段装着 SWA 窗、压缩段在后，索引值需平移到全缓存坐标（decode 时 offset=win=128）。q 与索引 entry 各自做过 Hadamard 旋转后，内积数学上仍等于原空间内积（正交变换不变性），旋转只为量化友好——这也是「rotate=True 不影响打分语义」的原因（推断，基于 Hadamard 变换正交性）。

7. 事实与推断的边界

  • 论文/源码证实：式 13–17 及「\(c^Q_t\) 由主注意力与 indexer 共享」「\(K^{\mathrm{I,Comp}}\) 用与 \(C^{\mathrm{Comp}}\) 相同的压缩操作」均出自 paper/deepseek_v4.pdf §2.3.1（p.10–11）；\(n^I_h=64\)、\(c_I=128\)、top-k=512/1024、m=4 出自 §4.2.1（p.24–25）并与 config.json 逐项核对；V3.2 的打分公式、ReLU 的 throughput 理由、FP8 可行性、KL 门控损失与两阶段训练数字（1000 步 / 2.1B token / 2048 / 943.7B token）出自 paper/deepseek_v32.pdf §2.1（p.3–4）；indexer FP4、索引分数 BF16、top-k 提速 2× 与 99.7% 召回出自 §2.3.4（p.13）与 §5.2.1（p.33）；「1M 上下文 V4-Pro 为 V3.2 的 27% FLOPs、10% KV cache」出自 §1（p.2）与图 1 说明。代码行为（独立压缩器 rotate=True、kv_cache 形状、因果掩码、offset 平移、latent 经 q_norm 后共享）逐行核对自 /tmp/paper-research/v4-pro/inference/model.py（commit b5968e9）。
  • 推断（已标注）：① §5.2 表 2 的 FLOPs/读取量核算与「1M 解码时 indexer 打分主导 CSA 层注意力 FLOPs」的结论；② 索引 entry 每条字节数（FP4 64 B / BF16 256 B 口径）；③ 「Hadamard 旋转后内积不变、不影响打分语义」；④ 「解码时主注意力分数对未选中候选不可算，故必须旁路打分」的工程化补充（§1 推断框）。
