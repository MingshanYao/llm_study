1. 补课：KV cache，显存账本里的大胃王

模型生成文字是一个 token 一个 token 蹦的。生成第 \(t\) 个 token 时，注意力要「回看」全部历史——如果每一步都把历史的 K、V 重新算一遍，等于做着天文数字的重复劳动。于是推理引擎把每层每步的 K、V 存下来复用，这份存档就是 KV cache。

代价是它随对话长度线性增长。以 Llama-3-70B 级架构（80 层 × 8 个 KV 头 × 128 维、FP16）为例，每个 token 要存：

\[ 2 \,(\text{K,V}) \times 80 \times 8 \times 128 \times 2\,\text{字节} \approx 0.33\,\text{MB/token} \]

一个 100K 长上下文就是约 33 GB——和 FP16 的 70B 权重同一量级。批量服务 N 个并发请求，就是 N 份 KV cache 并存。这就是长上下文时代「KV 是显存大头」的原因：

图 5-1｜显存账本第二课。柱高按实际 GB 等比。另一条路是改架构本身：DeepSeek 系列的 MLA 把 KV 压缩成低秩潜向量，从源头减量——详见本站《DeepSeek-V4 KV Cache 组织解读》。量化 KV 与 MLA 是同一个问题的两条路。

2. KV 量化的两个特殊难点

KV 本质也是「网络中间的数值」，理论上第 1 讲的工具直接适用。但 KV 有两个自己的脾气：

难点一：key 的 outlier 长在「通道」上

KIVI（Liu 等，2024）发现：key 矩阵的巨大幅值集中在少数固定通道（head_dim 方向的个别维度）上，而不是个别 token 上——这是第 3 讲「离群通道」现象在 KV 里的重演。对策也同款：**换切法**。key 沿通道分组量化（per-channel，把 outlier 关进自己的组），value 则老老实实按 token 量化即可。这一「非对称策略」让 KV 压到 2-bit 仍然可用，且无需微调。

难点二：attention sink——开头的 token 是「泄压阀」

StreamingLLM（2023）发现一个有趣现象：softmax 注意力总和中，最初的几个 token 几乎永远被分走可观份额——不管它们内容是什么。机理是 softmax 必须把概率分给某些位置，开头 token 成了「泄压阀」（attention sink）。对量化的含义：这几个 token 的 K/V 幅值大、又被全场依赖，粗暴量化会出大事。

图 5-2｜KV 量化的两个难点与对策。注意与第 3 讲的呼应：依然是「离群值 + 混合精度保底」的配方——领域知识是通用的，只是换了位置。

方案粒度与对策位宽备注
KIVI（2024）key per-channel + value per-token；开头 + 最近窗口 FP162-bit免微调即插即用，HuggingFace 有集成
KV Quant（2024）per-group 通道量化 + sink token 高精度 + 前几层保持稠密4-bit面向超长上下文（百万 token 级）
MLA 架构（DeepSeek）不改精度，改架构：KV 存成低秩潜向量—与量化正交，可叠加；见本站 KV cache 专文

3. 量化 kernel：W4A16 的速度从哪来

第 0 讲埋的账现在算清。模型 decode（逐 token 生成）时，每一步都要把全部权重从显存搬进计算单元——搬的时间远超算的时间（memory-bound）。权重量化到 4-bit 后：

  • 搬运量变成 1/4 → decode 速度在带宽受限时接近 4 倍（batch 小、单请求时最明显）；
  • 计算时用「边搬边解包反量化」（dequant-on-the-fly）：INT4 权重在进入计算单元前的最后一刻才展开成 FP16——从显存到运算器的路上始终保持 4-bit；
  • Marlin（2024）把这条路走到接近理论极限：精心重排的权重布局 + 位级解包 + 流水线，batch 16~64 时对 FP16 基线提速约 3.9 倍；vLLM 的 Machete 是 Hopper 架构上的同类 W4A16 kernel。

图 5-3｜两条数据通路对照。batch 小时瓶颈在搬运（W4 大赢）；batch 大时瓶颈转向计算——那就需要 INT8/FP8 tensor core 亲自上阵（W8A8/FP8，吞吐 2×）。

4. QServe：W4A8KV4 的组合拳

服务场景的最优解要两头兼顾：权重要 4-bit（省搬运、塞得下），激活要 8-bit（算得快），KV 也要 4-bit（并发翻倍）。QServe（Lin 等，2024）就是这个组合：W4A8KV4。它的技术亮点是把 W4A8 的矩阵乘法重构为「大部分乘法在 4-bit 单元、少量在 8-bit 单元」的渐进式量化计算，让低精度硬件单元物尽其用——在 L40S 级 GPU 上吞吐比 Marlin W4A16 还能再提高约 3 倍量级（论文最高 3.47×）。

系统观点QServe 的教训值得记一辈子：量化格式的设计必须与硬件算力单元、kernel 实现、集群拓扑共同设计。W4A8 在纸面上不一定赢 W4A16，但把「格式 × kernel × 硬件」作为一个系统看，它赢了。这就是「量化工程师」和「量化研究员」的分水岭。

5. 文件格式与框架生态

5.1 llama.cpp 与 GGUF k-quants：本机玩家的世界

llama.cpp 的 GGUF 格式发明了一套自己的量化家族（名字里 Q 后面跟位宽）：

  • k-quants（Q4_K_M 等）：把「每 32 个数一组共享 scale」再套一层「super-block 共享二级 scale」——正是第 1 讲粒度思想的极致压缩；Q4_K_M 里 M 是混合精度变体（敏感层用更高位宽）。
  • i-quants（IQ2/IQ3/IQ4_XS 等）：用 importance matrix（imatrix，用校准数据统计「哪些权重对输出影响大」）+ 类矢量量化的编码，把 2~3-bit 做到可用——第 4 讲思想的本机化。

一条实用的经验选格式时先问三个问题：① 我的瓶颈是显存容量（塞不下）、搬运带宽（decode 慢）还是算力（batch 大跑不快）？② 目标硬件支持哪些低比特单元（有没有 FP8/FP4 tensor core）？③ 模型作者官方发布了哪种格式？三个答案的交集，就是你的默认选择。

6. 自查清单

  1. KV cache 是什么、为什么随上下文线性增长？（答：每层每步的 K/V 存档供注意力复用；每 token 固定 KB~MB 级增量，乘上下文长度和并发数）
  2. KIVI 的非对称策略是什么、为什么有效？（答：key 沿通道量化、value 按 token 量化——key 的 outlier 在通道维，沿通道分组把 outlier 关进自己组）
  3. attention sink 是什么现象？（答：softmax 泄压阀——开头 token 恒定吃掉注意力份额，其 K/V 幅值大且被全场依赖，需保留高精度）
  4. W4A16 在什么条件下接近 4 倍提速？（答：decode 阶段 memory-bound、batch 小；靠 dequant-on-the-fly 保持 4-bit 搬运）
  5. Marlin/Machete 在优化什么？（答：W4A16 kernel 的权重布局、解包与流水线，让反量化融合几乎零成本）
  6. QServe 的 W4A8KV4 各对应哪个瓶颈？（答：W4 省搬运与显存、A8 用 INT8 算力提吞吐、KV4 翻倍并发）
  7. GGUF 的 Q4_K 和 IQ 系列各自的思路？（答：k-quants 是多级共享 scale 的粒度压缩；i-quants 用 importance matrix + 类 VQ 编码）
  8. 选量化配置的三个问题？（答：瓶颈是什么、硬件支持什么、作者发布了什么）
