第一部分 · PyTorch 如何支持一个算子

1.1 一次 torch.mm(a, b) 的完整旅程

一切从一次最普通的矩阵乘法开始。你在 Python 里写下 torch.mm(a, b)（a、b 是 CUDA 张量），到 CUDA kernel 真正执行，中间要经过四站：

  1. Python API 层：torch.mm 只是 C++ 绑定函数的薄壳——调用从 Python 一进来就进入 C++，Python 侧没有任何逻辑。
  2. Dispatcher：这是 PyTorch 的算子调度中枢。每个 op 在 dispatcher 里有一条记录，由两部分组成：一份 schema（op 名字 + 参数类型签名），和一张 dispatch key → kernel 的映射表。调用发生时，dispatcher 根据输入张量的设备/dtype/是否需要求导等信息算出一个 DispatchKeySet（再叠加线程局部的一组 include/exclude key），然后用它去查映射表、选出这次调用要执行的 kernel。
  3. 横切 key 的 kernel 先跑：DispatchKeySet 里通常除了 backend key（CUDA）还有横切 key（AutogradCUDA、AutocastCUDA 等）。官方 dispatcher 教程的说法是："we first execute the Autograd kernel, and then we redispatch to the backend kernel"——autograd kernel 记录完 grad_fn 之后，把调用重新分发（redispatch）给下一层的 backend kernel。
  4. Backend kernel：key 为 CUDA 的 mm kernel，内部调 cuBLAS GEMM，数据落到显存。

图 1：一次 torch.mm(a, b) 的四站旅程（对应 PyTorch 官方 dispatcher 教程的论述），右侧标出 vLLM 在各层的介入点及其对应本文章节。dispatcher 这层存在的意义：让 autograd、autocast、后端实现等关注点去中心化地各自注册，而不需要在一个大 if-else 里互相纠缠。

有了这张图，"新增/扩展一个算子"的所有官方途径，都可以精确地定位成一个问题：你要往 dispatcher 的哪一层挂钩子？下面按从轻到重的顺序讲六条。

1.2 途径 a：纯 Python 组合现有算子

为什么需要它：其实不算"扩展"——90% 的模型层就是这么写的。它不往 dispatcher 加任何东西，只是把已有 op 串起来；好处是 autograd、shape 推导、编译器支持全部白送（每个成员 op 都是 ATen 的一等公民）。

class SwiGLU(nn.Module):
    def forward(self, x):
        a, b = x.chunk(2, dim=-1)
        return F.silu(a) * b      # 三次 dispatcher 调用，autograd 自动生效

背后机制：每一次 F.silu(a)、* 都是一次完整的图 1 旅程（Python → dispatcher → CUDA kernel）。eager 模式下，这意味着每个成员 op 一次 kernel launch：kernel 太小则 launch 开销占比高，且无法把"读一遍显存做两件事"的融合写出来。torch.compile/Inductor 能事后把这些逐元素 op 融合回少数几个 kernel，但那是编译路径的补救，不是 eager 的能力。

图 2：同一语义的两种支持方式对比（机制示意，非实测数字）。左上：纯 Python 组合在 eager 下逐 op launch；下方：vLLM 用 C++ 预编译的单个融合 kernel 覆盖同一语义。SiluAndMul 同时保留两条路径，正是 vLLM 全部算子框架的原型。

在 vLLM 里对应谁：每个 CustomOp 的 forward_native（§2.1）就是这条途径——它是兜底、是单测基准，也是 Inductor 融合的原料。而"局限"（融合做不了、多 launch）正是其余五条途径存在的全部理由。

1.3 途径 b：torch.autograd.Function——自定义 backward 的正道

为什么需要它：当你要的数学在前向可以借现有 op 拼出来、但导数不好自动推（或你想要更省显存的手写导数）时，用 autograd.Function 显式声明前向/反向。

class MyExp2(torch.autograd.Function):
    @staticmethod
    def forward(ctx, x):
        ctx.save_for_backward(x)
        return x.exp2()                    # 前向在 no-grad 下执行，不记图
    @staticmethod
    def backward(ctx, g):
        (x,) = ctx.saved_tensors
        return g * x.exp2() * 2.0          # 自己写导数

def my_exp2(x):
    return MyExp2.apply(x)                 # 必须走 .apply() 才接上 autograd

背后机制：forward 运行时 autograd 被关闭，只执行你写的逻辑；.apply() 会在图里挂一个自定义 grad_fn，反向时调你的 backward。它不产生新的 dispatcher op——本质是"在 autograd 层插入一段自定义代码"，而不是"给 dispatcher 加 kernel"。

在 vLLM 里对应谁：几乎没有。vLLM 主线是推理（不建反向图），这条途径在训练框架（以及 vLLM 里极少数带训练语义的组件）才有用武之地。它在此列出，是为了与 §1.5 的 register_autograd 区分：后者把 backward 公式注册到 dispatcher 的 Autograd key 上，是 custom op 体系内的对应物。

1.4 途径 c：torch.utils.cpp_extension 与 torch.ops.load_library——把仓外 C++/CUDA kernel 挂进 torch

为什么需要它：当性能要求超出 Python 组合的能力（要融合、要手写 warp 级逻辑、要调 CUTLASS），就必须写 C++/CUDA。问题变成：怎么让 torch"认识"这个 kernel？答案分两步：C++ 侧向 dispatcher 注册，Python 侧让代码被加载。

加载的两条路：

  • JIT 编译：torch.utils.cpp_extension.load(name, sources=[...]) 在首次调用时用 Ninja 现场编译并缓存（缓存目录可用 TORCH_EXTENSIONS_DIR 指定）；load_inline 更进一步，直接从字符串源码编译。适合开发期与"随包携带源码"的库。
  • 预编译 .so：torch.ops.load_library(path) 加载已经编译好的动态库，"The library being loaded may run global initialization code to register custom operators with the PyTorch JIT runtime"（torch/_ops.py 中 load_library 的 docstring）——注册发生在库的加载时刻。正式发布的库（flash-attn 这类）走这条路或等价的 import 时注册。

C++ 侧怎么注册：用两个宏，恰好对应 §1.1 说的 op 记录的两半：

// C++：向 dispatcher 注册 schema 与 backend kernel（与官方 dispatcher 教程一致）
TORCH_LIBRARY(my_ns, m) {
  m.def("fused_gate(Tensor x) -> Tensor");          // schema
}
TORCH_LIBRARY_IMPL(my_ns, CUDA, m) {
  m.impl("fused_gate", &fused_gate_cuda);           // key=CUDA 的 kernel
}

之后 Python 侧 torch.ops.my_ns.fused_gate(x) 就是一次普通的 dispatcher 调用——与 torch.mm 完全同权。

在 vLLM 里对应谁：vLLM 的 torch.ops._C.*（如 silu_and_mul、rotary_embedding，见 vllm/_custom_ops.py 的调用处）就是 CMake 构建出的扩展模块在加载/导入时注册进 dispatcher 的；attention backend 依赖的 flashmla、deep_gemm、flashinfer 等外部库（§2.3/§2.5）也是同一模式的现成产品。§2.6 的插件体系则把"谁有资格加载这些库"也工程化了。

1.5 途径 d：torch.library 注册 custom op——最关键的一节

为什么需要它：C++ 算子（途径 c）天然在 dispatcher 里。但大量 kernel 是纯 Python 写的（或 Python 编排多个底层调用），它们默认只是普通函数——torch.compile 的 dynamo 会试图把它内联展开，遇到不支持的东西就 graph break；Inductor 也无从得知你的输入输出形状契约。把函数注册成 custom op，等于在 dispatcher 里给它建立正式的 op 记录（图 1 第二站），从而获得三个能力：

  1. 对 dynamo 是不透明节点：trace 到这里就停，不会展开内部实现——这既是保护（Inductor 不会重排危险 kernel），也是图切分的锚点（vLLM 的 piecewise compilation 就靠它，§2.2）。
  2. 对 Inductor 可做 shape/dtype 推导：这靠 fake kernel（下一小节单独讲）。
  3. 对 autograd 可在 op 层注册：register_autograd 把 backward 公式挂到 Autograd key 上（途径 b 的 custom op 版）。

1.5.1 两种写法

底层写法（vLLM 采用的就是这个，因为它绕开通用封装的开销）：

lib = torch.library.Library("mylib", "FRAGMENT")            # 命名空间的"碎片"库
lib.define("rms(Tensor x) -> Tensor")                        # ① schema 进 dispatcher
lib.impl("rms", my_rmsnorm_cuda, "CUDA")                     # ② 注册 key=CUDA 的 kernel
lib._register_fake("rms", my_rmsnorm_fake)                   # ③ 注册 fake/meta kernel

def my_rmsnorm_fake(x):
    return torch.empty_like(x)    # 只算 shape/dtype/device，不算数据

新一代写法（torch/_library/custom_ops.py 实现，文档措辞："Wraps a function into custom operator"）：

@torch.library.custom_op("mylib::rms2", mutates_args=[])
def rms2(x: torch.Tensor) -> torch.Tensor:
    return my_rmsnorm_cuda(x)

@rms2.register_fake
def _(x):
    return torch.empty_like(x)

@rms2.register_autograd
def my_backward(ctx, g):                # backward 公式挂在 Autograd key 上
    return g * scale

CustomOpDef 上还提供 register_kernel（"Register an implementation for a device type"——同一 op 注册多个 backend 实现）与 opcheck（检查注册正确性）。mutates_args 必须如实声明哪些参数被就地修改：functionalization 依赖它做别名/顺序分析，漏报会导致 Inductor 错误重排就地写。

1.5.2 fake kernel 是什么，为什么没有它 compile 就没法工作

torch.compile 的 tracing 阶段从不执行真实 kernel——张量被替换成 FakeTensor（实现于 torch/_subclasses/fake_tensor.py），上面只有 shape/dtype/device 这些元信息。FakeTensorMode 的目的就是"enable shape inference for torch.compile without actual computation"。fake kernel 就是你为 op 写的 meta 实现：给定输入的 FakeTensor，只做形状运算、返回输出 FakeTensor。没有它，Inductor 拿不到输出的形状契约，图推不下去（或退化成动态 shape）。ATen 的每个原生 op 自带 meta 实现，所以平时感觉不到它的存在；custom op 必须自己补上这一环。

图 3：custom op 的注册三件套与三个消费者（对应 PyTorch 官方 python custom ops 教程）。vLLM 的 direct_register_custom_op（§2.2）就是对这套底层 API 的直通封装。

在 vLLM 里对应谁：这是第二部分的主角——direct_register_custom_op（§2.2）逐字对应本节的三行注册代码；vLLM 强制给 attention 相关 kernel 配 fake impl，正是因为没有 fake kernel 就没有 piecewise compilation。

1.6 途径 e：Triton kernel 与 triton_op

为什么需要它：不是人人都想写 CUDA C++。Triton 让你用 Python 写 kernel、运行时 JIT 编译（@triton.jit 装饰的函数首次被调用时才编译，还有 @triton.autotune 枚举块形状），开发体验接近"带 GPU 常量的 Python"。代价是：一个裸的 Triton kernel launch 对 dynamo 来说是不可追踪的外部调用——官方 recipe 明说用户自定义 Triton kernel "do not automatically support all PyTorch subsystems"，直接混进被编译的函数里会 graph break。

@triton.jit
def sin_kernel(x_ptr, out_ptr, n, BLOCK: tl.constexpr): ...

# 裸调用：能跑，但对 torch.compile 是黑盒/断点
sin_kernel[(triton.cdiv(n, 1024),)](x, out, n, BLOCK=1024)

# 正道：triton_op 包住"含 Triton kernel 的函数"，wrap_triton 包住"kernel 调用本身"
@torch.library.triton_op("mylib::mysin", mutates_args={})
def mysin(x: torch.Tensor) -> torch.Tensor:
    out = torch.empty_like(x)
    n = x.numel()
    wrap_triton(sin_kernel[(triton.cdiv(n, 1024),)])(x, out, n, BLOCK=1024)
    return out

背后机制（torch/_library/triton.py）：triton_op "makes the implementation visible to these subsystems"——与 custom_op 的不透明相反，它允许 trace 进函数体，而 wrap_triton "Allows capture of a triton kernel into a graph via make_fx or non-strict torch.export"，把 kernel launch 本身捕获成图节点。于是一个 Triton kernel 在编译图里既可见（可被 Inductor 调度）又不必展开其内部实现。官方教程的原句："Use torch.library.triton_op to wrap a function that may invoke one or more Triton kernels"，"Use torch.library.wrap_triton to wrap the calls to the Triton kernel"。

在 vLLM 里对应谁：vLLM 大量热路径 kernel 是 @triton.jit 直用（§2.5），其中要参与 warmup/编译治理的那部分（如 DSv4 的融合 RMSNorm）以 VllmTritonJitKernel 基类管理编译键与预热；与 triton_op 精确对应的工程化则是把 Python 编排 + Triton kernel 整体注册成 custom op 的做法（§2.2 的 sparse_attn_indexer 内部正是 deep_gemm/top-k 等 kernel 的 Python 编排）。

1.7 途径 f：torch.compile / Inductor——让 PyTorch 替你生成 kernel

为什么需要它：前五条途径都是"人写 kernel"，这一条反过来：PyTorch 替你生成并融合 kernel。dynamo 把 Python 代码 trace 成图，Inductor 分析图、生成 Triton kernel，把相邻的逐元素/归约 op 融合，省 launch、省显存往返。

@torch.compile
def block(x):
    y = rms2(x)          # 不透明 custom op：图在这里停，成为子图边界
    return F.gelu(y)     # gelu 等交给 Inductor 生成/融合 kernel

背后机制：对算子作者而言，关键是两个互动规则——

  • custom op 是融合的墙，也是切图的锚：Inductor 不会穿透不透明 op 融合其内部，但可以把 op 前后的普通 op 段各自编译成高效子图。这正是 vLLM piecewise compilation 的原理：把 attention 主算子注册成 custom op，图就按它切成"可整体捕获的纯张量段 + attention 环节"（§2.2）。
  • graph break 是主线的断裂：dynamo 遇到不支持的语言构造（数据依赖的 host 分支、.item() 等）就放弃这一段。vLLM 对"必须读 host 信息"的代码不是回避 break，而是主动利用它——用装饰器在 CUDA graph 捕获时把指定函数断成 eager 区域（§2.2 末尾）。

在 vLLM 里对应谁：vLLM 的整个 CompilationConfig / piecewise 模式（第 4 讲详述）就是对本节两条规则的全局编排；CustomOp 的 custom_ops 开关（§2.1）则是"这一个层，走我的 C++ kernel 还是留给 Inductor 融合"的逐层协商。

第二部分 · vLLM 在这些机制上支持算子的六条途径

这一部分每条途径都回答同一个问题：它建立在第一部分的哪个 PyTorch 机制上 + vLLM 加了什么。每节末尾有一个三行小结框（PyTorch 机制 → vLLM 的工程化 → 你什么时候需要它）。所有行号属 vLLM main@fa75d34（2026-10-16 抓取）。

2.1 CustomOp 层框架——按平台分发的 nn.Module

建立在机制 a 上：子类用纯 PyTorch 写一个 forward_native（兜底/测试/编译原料三合一），再为有专属 kernel 的平台补 forward_cuda 等分支。vLLM 加的东西：不走 dispatcher，而是在 Python 侧做一次性的构造期分发——基类 CustomOp（vllm/model_executor/custom_op.py:102）在 __init__ 里把 self._forward_method 绑定到平台对应实现，此后每次 forward() 是一条已解析的方法引用，运行期零分支：

# vllm/model_executor/custom_op.py:172-199（有删节）
def dispatch_forward(self, compile_native: bool):
    compilation_config = get_cached_compilation_config()
    enabled = self._enforce_enable or self.enabled()   # 受 CompilationConfig.custom_ops 控制
    if not enabled:
        # 被禁用时退回 native 实现，并可对该段单独 torch.compile
        return self.maybe_compile(self.forward_native, enable=compile_native)
    if current_platform.is_rocm():
        return self.forward_hip        # 默认实现就是转发到 forward_cuda
    elif current_platform.is_cpu():
        return self.forward_cpu        # 默认实现是 forward_native
    elif current_platform.is_tpu():
        return self.forward_tpu
    elif current_platform.is_xpu():
        return self.forward_xpu
    elif current_platform.is_out_of_tree():
        return self.forward_oot
    else:
        return self.forward_cuda

三个配套设计：

  • 缺省回退链（custom_op.py:144-169）：forward_hip → forward_cuda，forward_cpu/xpu/tpu/oot → forward_native。子类只覆盖真正有专属 kernel 的平台，其余自动落到 PyTorch 原生实现——这就是 forward_native 永远必须存在的原因。
  • 与编译器协商：enabled()（custom_op.py:269）读 CompilationConfig.custom_ops（"+op"/"-op"/"all"/"none"；Inductor 后端默认 none，eager 默认 all）。被禁用的 op 回到 forward_native 交给 Inductor 做图内融合；maybe_compile（custom_op.py:207）还能把这段 native 代码单独编译——用于"外层被包成不透明 custom op、内层还想编译"的嵌套场景。
  • 注册表 + 仓外替换：@CustomOp.register("名字") 把类放进 op_registry（custom_op.py:21）；register_oot（custom_op.py:335）让仓外代码按类名整体替换仓内实现——__new__（custom_op.py:107）在实例化时检查 op_registry_oot，命中则直接换类。这是"改 kernel 不 fork vLLM"的第一条正道（与 §2.6 插件衔接）。

标准层都是这条路的产物，教科书样例是 SiluAndMul（图 2 已画；源码 vllm/model_executor/layers/activation.py:116-152）：forward_cuda 走预编译 C++ 算子 torch.ops._C.silu_and_mul，forward_native 一行 F.silu(x[..., :d]) * x[..., d:]。同族还有 RMSNorm（layernorm.py:37，其 native 路径已升级为调用 vLLM IR op，实现可按 provider 优先级热插拔）、RotaryEmbedding（rotary_embedding/base.py:14，构造经 get_rope 工厂按 rope_type 选子类）。

小结 · CustomOp 层框架

PyTorch 机制：途径 a——纯 Python 组合出 native 实现，C++ kernel 经途径 c 的 torch.ops._C.* 进 dispatcher。

vLLM 的工程化：在 Python 侧（而非 dispatcher）做构造期平台分发；加 custom_ops 开关与 Inductor 协商；加注册表与 OOT 类替换。

什么时候用：你要给一个"标准语义层"（归一化/激活/RoPE）提供多平台实现，并希望单测、兜底、编译三条需求一次满足。

2.2 direct_register_custom_op——Python kernel 注册成 torch custom op

建立在机制 d 上。vLLM 封装了 §1.5.1 的底层三行注册，官方函数是 direct_register_custom_op（vllm/utils/torch_utils.py:1068）：

# vllm/utils/torch_utils.py:1065-1104（有删节）
vllm_lib = Library("vllm", "FRAGMENT")      # 所有 vllm Python custom op 共用此库

def direct_register_custom_op(
    op_name: str,
    op_func: Callable,
    mutates_args: list[str] | None = None,   # 如实声明就地修改的参数
    fake_impl: Callable | None = None,       # §1.5.2 的 fake kernel
    target_lib: Library | None = None,
    dispatch_key: str | None = None,         # 缺省 = current_platform.dispatch_key
    tags: tuple[torch.Tag, ...] = (),
):
    """`torch.library.custom_op` can have significant overhead ... This function
    directly registers a custom op and dispatches it to the CUDA backend."""
    ...
    schema_str = infer_schema(op_func, mutates_args=mutates_args)
    my_lib = target_lib or vllm_lib
    my_lib.define(op_name + schema_str, tags=tags)           # ① schema
    my_lib.impl(op_name, op_func, dispatch_key=dispatch_key) # ② kernel
    if fake_impl is not None:
        my_lib._register_fake(op_name, fake_impl)            # ③ fake kernel

它比 torch.library.custom_op 装饰器少做很多通用分发逻辑（docstring 直说了这是为了绕开开销；schema 由函数签名自动推导），但三件套一个不少。为什么 vLLM 模型里到处是它？因为 piecewise compilation 需要切图锚点。vLLM 把整图交给 dynamo 后，按 CompilationConfig.splitting_ops 切开，attention 系算子是预声明的切点：

# vllm/config/compilation.py:768-787（节选，_attention_ops）
_attention_ops: ClassVar[list[str]] = [
    "vllm::unified_attention_with_output",
    "vllm::unified_mla_attention_with_output",
    ...
    "vllm::sparse_attn_indexer",
    "vllm::deepseek_v4_attention",      # :786
    ...
]

这些 vllm:: op 正是用 direct_register_custom_op 注册出来的。DeepSeek-V4 的 Lightning Indexer top-k 是标准用例——先写普通 Python 函数与 fake，再注册，然后再包一层 CustomOp 给"层"语义：

# vllm/model_executor/layers/sparse_attn_indexer.py:992-1001
direct_register_custom_op(
    op_name="sparse_attn_indexer",
    op_func=sparse_attn_indexer,
    mutates_args=["topk_indices_buffer", "candidate_blocks"],
    fake_impl=sparse_attn_indexer_fake,

class SparseAttnIndexer(CustomOp):        # 层级 CustomOp：平台分发、可 OOT 替换

注意这个双层结构：函数级 custom op（进编译图、可切图）套在层级 CustomOp（§2.1 平台分发）里；forward_cuda 里只是一句 torch.ops.vllm.sparse_attn_indexer(...)（sparse_attn_indexer.py:1139）。fake impl 在这里不是可选项——op 的输出要进 CUDA graph 与编译图，没有 fake kernel 图就推不完（§1.5.2）。另一侧的约束是 mutates_args 必须如实（两个 buffer 就地写，漏报会被 Inductor 错误重排）。若某段逻辑真的依赖 host 信息、无法进捕获图，vLLM 用 @eager_break_during_capture（vllm/compilation/breakable_cudagraph.py:67）把它主动断成 eager 区域，写进调用方预分配的输出 buffer——graph break 在这里被当成工具而非缺陷。

小结 · direct_register_custom_op

PyTorch 机制：途径 d——Library.define/impl/_register_fake 三件套；fake kernel 支撑 FakeTensor 推图。

vLLM 的工程化：直通注册绕开通用封装开销；统一 vllm:: 命名空间；attention 系 op 进 splitting_ops 成为 piecewise 切图锚点。

什么时候用：你的 kernel 是 Python 编排（可能内部还调 Triton/deep_gemm），又必须对 torch.compile 可见、可切图、可捕获。

2.3 attention backend 注册表——"一组预编译 kernel + 一份协议"整体可换

建立在机制 c 上：每个 backend 背后是一组来自外部库（flash-attn / FlashMLA / flashinfer / aiter / Triton…）的预编译 kernel，接法即 §1.4。vLLM 加的东西，是把"选哪组 kernel"从函数调用升级为可注册、可校验、可覆盖的注册表。attention 之所以值得整体抽象，是因为它不是单个算子，而是"一组算子 + 一份 metadata 协议 + 一种 KV cache 布局"的绑定整体（KV cache 机制见 第 3 讲）。

# vllm/v1/attention/backends/registry.py:34-109（节选）
class AttentionBackendEnum(Enum, metaclass=_AttentionBackendEnumMeta):
    FLASH_ATTN = "vllm.v1.attention.backends.flash_attn.FlashAttentionBackend"
    TRITON_MLA = "vllm.v1.attention.backends.mla.triton_mla.TritonMLABackend"
    FLASHMLA = "vllm.v1.attention.backends.mla.flashmla.FlashMLABackend"
    FLASHMLA_SPARSE_DSV4 = (            # :100 —— 模型驱动的 DSV4 成员
        "vllm.models.deepseek_v4.sparse_mla.DeepseekV4FlashMLABackend")
    FLASHINFER_MLA_SPARSE_DSV4 = (...)
    CUSTOM = None     # 第三方占位：使用前必须 register_backend

枚举成员是类限定名字符串（惰性 import），三个扩展口都开在枚举上：register(name, class_path) 动态加成员、register_backend(...) 装饰器把实现记进 override 表（可覆盖已有成员或填 CUSTOM——仓外后端的官方入口）、解析函数每次都尊重 override。

选择逻辑压缩成三句：用户显式指定 backend 时直接校验、不合法就报错（不静默回退）；未指定时按平台维护的优先级列表逐个"import 试试 + 校验"，第一个合法者胜出（入口 get_attn_backend，vllm/v1/attention/selector.py:105；平台实现 get_attn_backend_cls，vllm/platforms/cuda.py:420）；结果缓存。DeepSeek-V4 是对这套通用机制的模型驱动例外：不走通用 Attention 层与优先级竞逐，而是模型构造期直接指定层类——

# vllm/models/deepseek_v4/nvidia/model.py:537-568（有删节）
def _select_dsv4_attn_cls(vllm_config):

    if backend in (AttentionBackendEnum.FLASHMLA_SPARSE,
                   AttentionBackendEnum.FLASHMLA_SPARSE_DSV4):

    # 默认：SM12 → FlashInfer；其他 CUDA arch → FlashMLA

最终 kernel 落到外部库：FlashMLA 变体调 torch.ops._flashmla_extension_C.fwd_kvcache_mla_fp8 与 flash_mla_sparse_fwd（vllm/v1/attention/ops/flashmla.py:119-145），FlashInfer 变体走 flashinfer_trtllm_batch_decode_sparse_mla_dsv4（vllm/utils/flashinfer.py:331）。论文侧的 CSA/HCA/Lightning Indexer 结构见 DeepSeek-V4 Attention 解读与 Lightning Indexer 解读。

小结 · attention backend 注册表

PyTorch 机制：途径 c——外部预编译库经 dispatcher 接入；backend 类只是这组 kernel 的 Python 门面。

vLLM 的工程化：把"选哪组 kernel + metadata 协议 + KV 布局"做成可注册/可校验/可覆盖的枚举注册表；DSv4 由模型层直接指定，通用 selector 只兜底。

什么时候用：你要整体替换注意力实现（含 KV 布局与 batch metadata 协议），而不是换单个算子。

2.4 量化与 MoE 方法类——用对象多态替换 GEMM 算子的实现

建立在 OO 多态上：这条途径甚至不经过 dispatcher——它是 Python 的老朋友"鸭子类型"。nn.Linear（vLLM 的 LinearBase）在构造期拿到一个方法对象，前向只剩一句多态调用：

# vllm/model_executor/layers/linear.py:620（RowParallelLinear 同型，:623）

vLLM 加的东西有两层。第一级：checkpoint 的量化配置决定方法类（Fp8LinearMethod/Mxfp4MoEMethod…，第 7 讲详述）。第二级：方法类内部再按平台优先级选具体 GEMM kernel——FP8 线性走 vllm/model_executor/kernels/linear/__init__.py:449 的平台 × 类型候选表：

小结 · 量化与 MoE 方法类

PyTorch 机制：对象多态替换 apply（不是 dispatcher）；最终 kernel 仍经途径 c（scaled_mm/分组 GEMM 库）进入。

vLLM 的工程化：get_quant_method 按 checkpoint 配置发方法对象；方法内再做平台 × 算力 × 依赖的 kernel 优先级选择。

什么时候用：你要替换 GEMM 算子的数值实现（量化格式、分组方式、kernel 库），而不改层的语义接口。

2.5 JIT kernel 与外部库探测回退

建立在机制 e + c 上。相当一部分 kernel 不是 AOT 编译的，而是运行时 JIT（途径 e）：@triton.jit 首调编译、@triton.autotune 枚举块形状（如 vllm/model_executor/layers/mamba/ops/ssd_chunk_scan.py:17）；TileLang（DSv4 的 mHC 算子族，vllm/model_executor/kernels/mhc/tilelang.py，mHC 解读）与 CuTeDSL 同理。vLLM 加的第一样东西是声明式 warmup：VllmTritonJitKernel/JitWarmupRegistry（vllm/model_executor/warmup/jit_warmup.py，register_warmup 在 :971）——kernel 类声明 CompileKey 与 launch 描述，启动期把所有可能 shape 预编译，消除服务首请求的编译抖动（DSv4 一层构造函数就注册了十余个，vllm/models/deepseek_v4/attention.py:375-468）。这正是 §1.7 那条约束"编译/捕获不得发生在请求路径上"的工程化。

第二样东西是外部库（途径 c 的产品）的统一探测模式——"平台支持 ∧ 环境开关 ∧ 包存在"：

# vllm/utils/deep_gemm.py:113-117
@functools.cache

    """仅 Hopper/Blackwell。"""
    is_supported_arch = current_platform.support_deep_gemm()   # 平台/算力
    return is_supported_arch and envs.VLLM_USE_DEEP_GEMM and has_deep_gemm()
        # 环境变量开关                          # 包是否存在（utils/import_utils.py:512）

回退有两种风格：静默降级（backend selector 把 ImportError 记为该候选不可用换下一个；RMSNorm 的 XPU 路径 hasattr(torch.ops._C, "gemma_rms_norm") 不在则走 native）与硬失败（被选中的 backend 缺依赖时直接 raise，如 SparseAttnIndexer.__init__ 的 "CUDA op requires DeepGEMM" RuntimeError，sparse_attn_indexer.py:1057-1059）。另有一类数值兜底：MXFP4 无任何可用后端时退 EMULATION（反量化成 bf16 跑普通 GEMM）——"能跑"优先于"跑得快"。

小结 · JIT 与外部库

PyTorch 机制：途径 e（@triton.jit 运行时编译）+ 途径 c（外部库经 dispatcher 接入）。

vLLM 的工程化：CompileKey + 启动期 warmup 消除请求路径上的编译；"平台 ∧ 开关 ∧ 包存在"三级探测 + 两种回退风格。

什么时候用：kernel 需按 shape 特化编译，或你依赖一个环境里"有没有、开没开、支不支持"都不确定的第三方 kernel 库。

2.6 插件与 out-of-tree 扩展

建立在机制 c 的 load_library + Python entry_points 上。前五条途径都发生在仓内；这条解决"仓外代码如何不 fork 就接入"。机制本身是标准的：torch.ops.load_library（§1.4）加载预编译扩展 + Python 的 importlib.metadata.entry_points 发现插件。vLLM 加的东西是分层契约：

  1. general plugins：entry point 组 vllm.general_plugins（vllm/plugins/__init__.py:18），进程启动时经 load_plugins_by_group（:36）逐个发现并执行 load_general_plugins（:77），可用 VLLM_PLUGINS 白名单收窄。插件函数体里调 CustomOp.register_oot（custom_op.py:335）即可整体替换仓内层。
  2. platform plugins：entry point 组 vllm.platform_plugins（plugins/__init__.py:23），每个插件返回平台类限定名，与内置探测器一起竞选 current_platform——新硬件支持由此接入，随后自动获得 CustomOp 的 forward_oot 分发位与 attention backend 选择权。
  3. 直接注册 custom op：direct_register_custom_op(..., target_lib=自己的 Library)（§2.2 函数签名支持），仓外 Python kernel 与仓内在编译图里待遇完全一致；C++ 侧则回到 torch.ops.load_library 的本源。

小结 · 插件与 OOT

PyTorch 机制：途径 c 的加载时注册 + Python 打包的 entry point 机制。

vLLM 的工程化：general/platform 两组 entry point + register_oot 类替换 + target_lib 参数，形成"不 fork 就能换层/换平台/注册 op"的官方接口。

什么时候用：你的扩展代码与 vLLM 仓库不同生命周期（独立发包、独立版本）。

4.2 给 vLLM 新增一个算子：五步指南

  1. 分层定位（先想清楚挂在 PyTorch 哪个机制上）：标准语义的新实现 → CustomOp 平台分支或 IR op provider；Python 编排的重 kernel 聚合 → direct_register_custom_op；整组注意力行为 → 新 attention backend；GEMM 数值实现 → 量化方法类。
  2. 实现双路径：forward_native 必写（兜底 + 单测 + Inductor 融合原料），平台分支按需补；这是途径 a 的地基作用。
  3. 注册并声明契约：语义层 @CustomOp.register；进编译图的再 direct_register_custom_op，如实写 mutates_args 与 fake kernel（§1.5.2：没有 fake，Inductor 推不完图）。仓外则经 general plugin 在 import 时完成同样动作。
  4. 接入选择机制：给实现写 is_supported 类判定，加进对应注册表/优先级候选；同时支持用户显式指定 + 校验。
  5. 过编译与图捕获关：跑一次 piecewise 编译与 CUDA graph 捕获；有 host 依赖的区域用 @eager_break_during_capture 或声明合适的 AttentionCGSupport；JIT kernel 补 register_warmup，确保编译不落在请求路径上。
