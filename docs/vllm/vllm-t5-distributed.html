一句话：vLLM 把"多卡"拆成两个正交问题——逻辑切分（TP/PP/PCP/DCP/EP 决定每个 rank 干什么活，由 initialize_model_parallel 画成一张 rank 网格）与物理承载（Executor 决定这些 rank 的进程从哪来：单进程 / 多进程 / Ray）；DP 再把整套东西复制 N 份，每份独立的 EngineCore + Scheduler + KV cache，互不通信。

本篇主线：rank 布局公式 → 通信组 → Executor 选型 → 启动 collective → TP 的 all_reduce 六级 fallback → PP 接力 → EP/EPLB → DP 负载均衡。

1. 五维并行全景：ParallelConfig 与 rank 布局

所有并行参数都在 ParallelConfig（vllm/config/parallel.py:119）。先看五个"模型内"维度（它们决定一台进程内 world 的形状）：

维度参数切什么本树备注
TPtensor_parallel_size（:124）每层权重矩阵（列并行切输出 / 行并行切输入）层内通信最频繁
PPpipeline_parallel_size（:122）按层段切模型，stage 间只传激活world_size = PP×TP×PCP（:833-838）
PCPprefill_context_parallel_sizeprefill 长上下文的上下文维切分与 DP 互斥（:530-532）
DCPdecode_context_parallel_size（:342）decode 的上下文维（KV 沿序列切）PCP 禁用时复用 TP ranks，要求 tp % dcp == 0（:535-537）
EPenable_expert_parallel（:165）MoE 专家放到不同 rank，token 走 all2all不改变 world 形状，只改专家分布

DP 是另一个层级：data_parallel_size 乘在进程世界外面——world_size_across_dp = world_size × DP（:549-551），每个 DP rank 是一整份独立的模型副本 + 调度器（第 8 节）。

rank 全局编号的排布规则只有一句注释 + 一行 reshape（vllm/distributed/parallel_state.py:1822-1830）：

# the layout order is: ExternalDP x DP x PP x PCP x TP
all_ranks = torch.arange(world_size).reshape(
    -1, data_parallel_size, pipeline_model_parallel_size,
    prefill_context_parallel_size, tensor_model_parallel_size)

# TP 组：view(-1, tp)              → 相邻 rank（:1846）
# DCP 组：transpose(-1,-2) 跨 PCP/TP（:1852-1860）
# PCP 组：transpose(3,4)           （:1874）
# PP 组：transpose(2,4)            （:1883）
# DP 组：transpose(1,4)            （:1893）

TP 是最快变化的维度——rank 0 和 rank 1 永远是同一层内通信最频繁的伙伴，这也解释了为什么排布时"相邻 rank 放同一台机器"（initialize_model_parallel docstring，:1771-1774）。

图 1：五维并行的 rank 网格。小字 (dp,pp,tp) 是各维度坐标，与 rank 编号满足 rank = dp×4 + pp×2 + tp。跨 DP 的复制由第 8 节的引擎级复制承担，不在这张进程世界图里。

2. GroupCoordinator：通信组怎么分

第 1 节的 reshape 产出的每组 rank 列表，交给 init_model_parallel_group 包成 GroupCoordinator（vllm/distributed/parallel_state.py:380），注册成全局单例 _TP/_PP/_DP/_PCP/_DCP，之后全代码库用 get_tp_group() 等访问。GroupCoordinator 是"一个组 + 该组内本 rank 的角色"的组合体：

方法位置语义
all_reduce / reduce_scatter:662 / :722TP 组的核心操作（行并行层输出求和）
all_gather / all_gatherv:691 / :712列并行输出拼回 / 不等长 gather
broadcast / broadcast_object:766 / :781PP 输出广播、控制面对象下发
send_object 等 P2P:822PP stage 间接力

两个容易忽略的细节：

  • torch.compile 兼容：collective 另有 free-function 版本注册成 custom op（parallel_state.py:152-196，all_reduce/all_reduce_fake…），piecewise 编译时 attention 两侧的通信段才能被正确 trace；
  • 全局 rank 折算：开 DP 后进程世界被拉大，全局 rank = dp_rank × world_size + rank，全局 world = world_size_across_dp（:1561-1562）——NCCL 初始化用这套全局编号（init_distributed_environment）。

3. Worker 从哪来：Executor 四种后端

"rank 网格"画好了，还得有人扮演每个 rank。Executor（vllm/v1/executor/abstract.py:37）负责这件事，选型集中在 Executor.get_class（:49-98）：

后端类进程模型PP何时启用
uniUniProcExecutor（uniproc_executor.py:45）无子进程，worker 就在 EngineCore 进程内—world_size==1 时默认（config/parallel.py:955-956）
mpMultiprocExecutor（multiproc_executor.py:103）spawn 每 rank 一个 WorkerProc 子进程（:568）✓（:104）未指定后端且 world_size_across_dp>1 时默认（config/parallel.py:911）
rayRayDistributedExecutor（ray_executor.py:64）；设 VLLM_USE_RAY_V2_EXECUTOR_BACKEND 则 RayExecutorV2（ray_executor_v2.py:219）Ray actor 扮演 rank✓（:68/:230）多机；V2 复用 WorkerProc + 消息队列（RayWorkerProc，:76）
自定义字符串 → resolve_obj_by_qualname，或直接传类（校验 Executor 子类，:54-59）自定—verl 等外挂框架
external_launcherExecutorWithExternalLauncher（uniproc_executor.py:150）通信组由外部预先建好—RL 框架集成（此时 world 含 DP，config/parallel.py:840-841）

MultiprocExecutor 的骨架（_init_executor，:111-330）：建 rpc_broadcast_mq 共享内存消息队列把 SchedulerOutput 广播给所有 worker（:144-152），逐 local_rank WorkerProc.make_worker_process（:161）拉起子进程（未就绪句柄 UnreadyWorkerProcHandle，:531），心跳监控 + 死亡即整体 shutdown（:470/:784）。execute_model（:321）把 SchedulerOutput 写进广播队列，各 worker 读完自行执行，输出经各自队列回传聚合。

所有跨进程控制面走一个口子：collective_rpc。EngineCore 持有 self.model_executor（engine/core.py:132），任何"对全体 worker 执行方法 X"都调 collective_rpc（engine/core.py:953-960）：UniProc 直接本地调用（uniproc_executor.py:79），Multiproc 打进广播队列（multiproc_executor.py:354）。execute_model 本质上也是 rpc 的一种。

4. 启动时序：从 EngineCore 到可服务的 KV cache

图 2：启动时序三泳道。注意 Worker 的三步都由 EngineCore 通过 collective_rpc 驱动：init_device（建通信组）、load_model（第 7 讲）、determine_available_memory（第 3 讲的 profile 公式）。

通信组建立后，get_tp_group().ranks 等在每个 worker 进程里各有一份——进程间没有共享这些单例，靠的是大家用同样的参数（rank、init_method、backend）各自初始化出"拓扑一致"的组。这也是为什么 initialize_model_parallel 必须在所有 rank 上以一致的配置调用。

5. TP：一次 forward 的集合通信

TP 的层间规则第 4 讲已经露过面：ColumnParallelLinear 把权重按输出维切开（每 rank 一份 weight_loader narrow，layers/linear.py:560-581），输出无需通信；RowParallelLinear 按输入维切开，输出是各 rank 的部分和，forward 末尾一次 all_reduce 求和（:1766-1767）。一个 transformer 层因此是"两个无通信的列并行 + 中间激活 gather + 两个带 all_reduce 的行并行"。

实际执行 all_reduce 的是 CudaCommunicator（vllm/distributed/device_communicators/cuda_communicator.py:29），它内部持有一排候选实现，all_reduce（:275）按六级 fallback 链选路：

#实现触发条件价值
1NCCL symmetric memory AR（NVLS）should_nccl_symm_mem_allreduce（:278）硬件组播，大消息最快
2QuickReduce仅 ROCm MI3\*（:286 注释）AMD 专用快路径
3FlashInfer ARfi_ar_comm.should_use_fi_ar（:293）融合 norm 的 AR（TRT-LLM 风格）
4AITER ARROCm（:303）AMD custom AR
5vLLM custom allreduce输入 < 8 MiB（custom_all_reduce.py:74 max_size=8192*1024；should_custom_ar :348）单 kernel NVLink 直写，小消息延迟最低；CUDA graph 需 register_graph_buffers（:329）
6PyNCCL兜底（pynccl.py）Python 封装的 NCCL，异步可 overlap

decode 时每层 all_reduce 的消息只有几 KB 到几百 KB，正落在 custom allreduce 的甜点区——这是 vLLM 小卡间 decode 吞吐的关键优化之一。all_gather / reduce_scatter 走类似的分级（symm mem NVLS 优先，见 cuda_communicator.py 的 _all_gather_symm_mem 等）。

6. PP：stage 之间的接力

PP 把模型按层切成 pipeline_parallel_size 段，每个 stage 是一个（或一组 TP）worker。V1 的 PP 是同步微批接力，关键分支全在 gpu_model_runner.py：

角色行为位置
first rank唯一处理多模态输入 / prompt embeds 的 rank（embedding 只存在于 stage 0）:3559、:3570、:3623
中间 / 非 last不做采样（logits 只在最后一个 stage 算），前向完把隐藏态 send_tensor_dict 给下一 stage:1333、:1408、:4497
last rank采样并产出 ModelRunnerOutput；broadcast_pp_output 时把结果广播回各 rank（broadcast_tensor_dict，src=last）:4469-4511
async scheduling非 last rank 收到 use_async_scheduling 输出时的特殊处理（占位输出）:4560

调度器侧对 PP 无感知——每个 EngineCore 只有自己的 stage 的请求状态，KV cache 也是各 stage 各管一段层。PP 的代价是气泡；vLLM 目前不做 interleave/virtual pipeline 调度，推理场景更常用 TP 或 DP 扩容。

7. EP：专家并行与 EPLB

EP（enable_expert_parallel，config/parallel.py:165）不动 rank 网格，只改 MoE 层的专家分布：专家权重散到 EP 组各 rank，token 按 gate 选中的专家经 all2all 送到"专家所在 rank"计算再送回。MoE 实现在 vllm/model_executor/layers/fused_moe/。

EPLB（Expert Parallelism Load Balancer）（vllm/distributed/eplb/）解决 EP 的经典问题——热门专家被挤爆：

组件位置职责
EplbStateeplb_state.py:220逻辑→物理专家映射、专家负载统计、重平衡触发
EplbCommunicatoreplb_communicator.py:45rank 间统计/映射同步，四种实现：NCCL（:98）、Gloo staged（:155）、NIXL（:241）、PyNCCL（:614）
policy/ + rebalance_execute.py同目录重平衡策略与权重在 GPU 上的实际搬运

配置校验串成一串：EPLB 必须开 EP（config/parallel.py:499-500）；Elastic EP（运行期增减 EP rank）必须开 EPLB（:845-849），由 AsyncLLM.scale_elastic_ep（v1/engine/async_llm.py:1032-1073）配合 DP 协调器在排水后改 data_parallel_size。

8. DP：引擎级复制与请求路由

DP 是最"贵"也最简单的扩容方式：data_parallel_size=N 时，AsyncLLM 启动 N 份完全独立的 EngineCore（各含自己的 Scheduler、KV cache、模型副本），彼此零通信。好处：

  • 调度完全并行，N 份 token budget；
  • prefill/decode 干扰被物理隔离；
  • TP 组变小（TP×1 即可），all_reduce 频率大幅下降。

请求路由在 client 侧：DPAsyncMPClient（v1/engine/core_client.py:1249）docstring 明说 "Assumes external load-balancing by default"——典型部署前置一个外部 LB。内置策略维护每 engine 的 lb_engines = [waiting, running, kv_cache_usage]（:1271-1273）做最低负载选择。跨 engine 的统计与弹性伸缩由独立协调进程负责：DPCoordinator（v1/engine/coordinator.py:23）/ DPCoordinatorProc（:146）。

DP 组（transpose(1,4) 建出的通信组）在纯推理里几乎不用——同 DP 组的 rank "应同时 generate"的语义（parallel_state.py:1824-1829 注释）主要服务 verl 这类 RL 训练集成的同步采样。
