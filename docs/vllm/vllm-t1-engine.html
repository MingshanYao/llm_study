一句话：vLLM 把"说话"（API/流式输出）与"干活"（调度+GPU 执行）拆到不同进程，用一组 ZMQ socket 相连；EngineCore 是无阻塞消息泵，前端 AsyncLLM 是纯 asyncio 消费者。理解了 socket 拓扑与消息类型，vLLM 的"骨架"就通了。

本篇主线：进程拓扑 → AsyncLLM 的三个关键任务 → CoreClient 三形态 → 全部 socket 清单 → DP wave 协调 → 崩溃时会发生什么。

1. 为什么要分进程

把调度器和 uvicorn 放在同一个进程里行不行？技术上可以（InprocClient 就是这么做的），但 vLLM 默认选择分进程，动机有四个：

  • 错误隔离：EngineCore 操作 CUDA，任何 CUDA error 都是"进程级不可恢复"（CUDA context 损坏后同进程继续跑必然 UB）。拆出子进程后，EngineCore 崩溃时前端能体面地返回 503 并重启，而不是整个 uvicorn 进程被 abort。
  • GIL 与阻塞：调度器做 KV 块分配、prefix cache 查找是纯 CPU 工作；detokenizer、logprobs 处理也是。分进程后前端的事件循环永远不会被调度逻辑卡住，流式延迟（TTFT/ITL）更平滑。
  • DP 扩展：数据并行 = 多个 EngineCore 进程 + 一个前端做路由。分进程让"1 个前端带 N 个引擎"成为自然拓扑（见 第 6 节）。
  • 前端可替换：引擎接口就是一组 ZMQ 消息，所以官方可以用 Rust 重写前端（rust/，"vllm-frontend-rs"）而完全不动引擎。

代价是跨进程消息开销。vLLM 的对策是把消息做"薄"：EngineCoreRequest/EngineCoreOutputs 用 msgspec 编码（比 pickle 快一个量级），tensor 本体不走消息（多模态例外，见 第 9 节）。

2. 进程拓扑与启动握手

图 1：默认单机拓扑（DP=1）。三个方框 = 三类进程。DP>1 时"EngineCoreProc + Worker 池"这一整套按 DP rank 复制 N 份，MoE 模型还会多一个 DPCoordinator 进程（图 2）。

2.1 启动握手

进程不是拉起来就能用的，两侧有一段仪式（vllm/v1/engine/utils.py:1054 的 launch_core_engines / wait_for_engine_startup）：

  1. 前端先 bind 一个随机端口的 ROUTER socket 作为握手地址，把它随 CoreEngineProcManager 启动参数传给子进程（utils.py:120 的 CoreEngineProcManager 用 multiprocessing.Process(target=EngineCoreProc.run_engine_core)，每个本地 DP rank 一个）。
  2. EngineCore 进程用 DEALER socket（identity 为 2 字节 rank 编号，core.py:1205）连上握手地址，发送 HELLO。
  3. 前端回 EngineHandshakeMetadata（各 socket 地址 + DP 配置），EngineCore 完成自己的 socket 连接后回 READY（core.py:1233-1269）。
  4. 前端收齐所有 rank 的 READY 才继续构建 AsyncLLM。任何一侧超时/崩溃都会让启动直接失败——这是 vLLM 启动报错最常见的来源，读懂握手就懂了怎么排查。

EngineCore 进程内部再由 Executor 拉起 Worker：MultiprocExecutor（v1/executor/multiproc_executor.py:103）spawn 每个 TP/PP rank 的 WorkerProc（:568）。所以完整的进程树是：API server → EngineCore×DP → Worker×(TP·PP)。

3. AsyncLLM 解剖：前端的事件循环

AsyncLLM（v1/engine/async_llm.py:72）是前端的全部。它不持有任何模型，只有四样东西：InputProcessor、OutputProcessor、一个 engine_core client、一个后台输出任务。关键成员与任务：

成员/任务位置职责
output_handlerasync_llm.py:657（_run_output_handler 内 :676）唯一的输出汇聚点：循环 engine_core.get_output_async()，按 VLLM_V1_OUTPUT_PROC_CHUNK_SIZE=128（envs.py:160）分块调 process_outputs；发现 stop-string 触发完的请求就回发 abort
add_requestasync_llm.py:283先 process_inputs_async（在线程池渲染+分词），再注册 RequestOutputCollector，最后 _add_request（:420）：注册到 OutputProcessor → 发 EngineCore
generateasync_llm.py:544AsyncGenerator：循环从 collector 的队列取输出并 yield；客户端断开（CancelledError）→ 自动 abort 该请求
ParentRequestv1/engine/parallel_sampling.py:13n>1 的并行采样：一个父请求 fan-out 成 n 个子请求（child id = {index}_{request_id}），流式直传、非流式聚合
erroredasync_llm.py:1094引擎死亡 = engine_core.resources.engine_dead 或 output_handler 任务退出

一个容易忽略的设计：每个请求的输出用一个"单槽 collector"（RequestOutputCollector，output_processor.py:45）接力。生产端（output_handler）只 put 最新输出，消费端（generate 协程）只取一次；如果消费端消费慢了，后续输出会在 collector 里合并（RequestOutput.add(aggregate=True)，output_processor.py:62）——这就是为什么慢客户端不会拖垮整台服务器的内存，代价是丢失中间 delta 的粒度（对 OpenAI 流式语义无损）。

4. CoreClient 家族：三种客户端形态

前端与 EngineCore 的所有交互都收口在 EngineCoreClient 抽象（core_client.py:78）。工厂 make_client（:90）按两个维度分派：是否多进程 × 是否 asyncio：

实现位置使用场景关键机制
InprocClientcore_client.py:306单进程调试（VLLM_ENABLE_V1_MULTIPROCESSING=0）直接持有 EngineCore 对象，get_output() = 直接调 step()
SyncMPClient:802离线 LLM（同步世界）后台线程跑 process_outputs_socket + queue.Queue；utility 调用走 concurrent Future（:893）
AsyncMPClient:974在线 serving（AsyncLLM）asyncio task 收 socket → asyncio.Queue（:1037）；utility 走 call_utility_async（:1125）
DPAsyncMPClient / DPLBAsyncMPClient:1249 / :1431DP>1：外部负载均衡 / 内置负载均衡打分订阅 coordinator 统计（waiting/running/KV 占用），按引擎健康度路由请求

跨进程的消息类型只有 6 种，定义在 v1/engine/__init__.py:261：

class EngineCoreRequestType(enum.Enum):
    """Request types defined as hex byte strings, so it can be sent over sockets
    without separate encoding step."""

    ADD = b"\x00"
    ABORT = b"\x01"
    START_DP_WAVE = b"\x02"
    UTILITY = b"\x03"
    # Sentinel used within EngineCoreProc.
    EXECUTOR_FAILED = b"\x04"
    # Sentinel to wake up input_queue.get() during shutdown.
    WAKEUP = b"\x05"

每条消息的第 1 字节就是上表的类型字节，随后的 payload 是对应的 msgspec 结构（EngineCoreRequest / UtilityResult 等）。注意 WAKEUP 和 EXECUTOR_FAILED 不是"请求"，而是哨兵消息：前者用来在优雅关闭时叫醒阻塞在 input_queue.get() 的引擎（core.py:1322），后者是 EngineCoreProc 内部把 executor 死亡传播给主循环用的。

6. DP coordinator 与 wave 协调

数据并行有两种姿势：外部负载均衡（上游 LB 把请求打到不同 API server 实例，各 DP rank 完全独立，MoE 模型除外）和内置协调。MoE 模型做 DP 时，每个 DP rank 都有全部专家，如果各 rank 各自跑各自的 batch，all-to-all 通信时就会出现"有 rank 没活干"的空泡。vLLM 的解法是 wave 同步：

  • DPCoordinator 进程（v1/engine/coordinator.py:146）：仅 DP>1 且 MoE 时由 rank0 前端拉起（utils.py:1091）。状态极简：current_wave + engines_running（:199），外加每个引擎的 [waiting, running, kv_cache_usage] 统计。
  • wave 生命周期：所有引擎 idle 时，第一个请求到达任意 rank → 前端经 PAIR 发 FIRST_REQ → coordinator 广播 START_DP_WAVE（coordinator.py:349）→ 所有引擎醒来并开始调度；rank0 引擎跑完最后一个 step 后发 wave_complete → coordinator current_wave+1，回到 idle（:422）。
  • 引擎侧配合：没有请求时跑 dummy batch，并每 32 步 all-reduce 一次 _has_global_unfinished_reqs 确认全局没有活跃请求（core.py:2144）——这是把"独立 run loop"焊成"同步 wave"的胶水。
  • 前端侧配合：DPLBAsyncMPClient（core_client.py:1431）做内置 LB 打分：waiting+running 越多分越低、KV 占用 >50% 额外惩罚（:1468）；也可以配外部 LB（如生产环境的 kube 服务发现）让 DPAsyncMPClient 只做粘性路由。

8. 优雅关闭与错误传播

EngineCore 死亡时，前端有三条独立的感知路径，对应三种死法：

  1. 应用层死信（优雅崩溃）：EngineCore 捕获到自身异常 → _send_engine_dead（core.py:1605）在 output socket 上发 ENGINE_CORE_DEAD 字节串（linger=4000 确保送达）→ 前端 validate_alive（core_client.py:490）置 engine_dead=True 并抛 EngineDeadError → 异常被塞进每个请求的 collector → 所有 in-flight generate() 立刻结束 → /health 返回 503。
  2. 进程层监控（OOM kill、segfault）：前端有专门的 monitor_engine_liveness 线程等进程 sentinel（core_client.py:708）；Ray 模式用 ray.wait 捕获 RayActorError（utils.py:965）。
  3. socket 断链：PULL socket 收到 EOF/异常 → 同样落进 outputs_queue（core_client.py:1084）转成引擎死亡。

反向（前端先死）：API server 收 SIGTERM → engine_client.shutdown(timeout) → 向 EngineCore 发终止信号；EngineCore 置 EngineShutdownState.REQUESTED，按 shutdown_timeout 决定立即 abort 还是 drain 完存量请求（core.py:1459）。另外 uvicorn 侧还有个 watchdog_loop（entrypoints/launcher.py:168）每 5s 检查引擎健康——因为 StreamingResponse 内部的异常无法自然上抛，watchdog 是兜底的"最终退出手段"。

9. 多模态 tensor 的零拷贝通道

普通请求的输入是 token ids，msgspec 编码毫无压力；但多模态请求可能携带 mm embedding tensor（几百 MB 级）。走 msgpack 序列化就是一次全量拷贝。解法在 v1/engine/tensor_ipc.py：

  • 前端侧 TensorIpcSender（:69）：tensor 先 share_memory_() 进共享内存，msgpack 帧里只留轻量句柄（TensorIpcData，:30）；共享内存创建失败则回退普通序列化（:99）。
  • 引擎侧 TensorIpcReceiver（:114）：drain-and-buffer 支持多生产者乱序到达，按 tensor_id 配对。
  • 接线：queue 在 launch_core_engines 创建（仅 multimodal 且 mm_tensor_ipc=="torch_shm"、DP=1，utils.py:1079），client 侧挂到 MsgpackEncoder 的 out-of-band 钩子（core_client.py:622）。

这个"msgpack 帧内引用 + 共享内存传 tensor"的模式是理解 vLLM 大张量传输的通用范式，PD 分离的 KV 传输（第 5 讲）走的是另一条专用通道但设计思想类似。
