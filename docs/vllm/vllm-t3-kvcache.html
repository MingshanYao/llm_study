一句话：vLLM 把显存当成一台"虚拟内存机"——KV cache 是物理页框（BlockPool），每个请求持有一张页表（block_table），相同内容自动共享（prefix caching），写共享页前复制（CoW），放不下时换出到 CPU/远端（offload）。第 2 讲调度器做的每个决定，都要经过这一层的记账。

本篇主线：显存 profile 公式 → spec 分组 → BlockPool 结构 → 三个块操作函数 → CoW 与驱逐 → offload / connector。

1. PagedAttention 的今天：从 kernel 名到基础设施

2023 年读 vLLM，"PagedAttention" 是一个 CUDA kernel；这棵 dev 树里它已经是一整套显存管理子系统的代称：

  • 旧 kernel 已删除：原版 CUDA paged_attention_v1/v2 在本树已被移除（csrc/attention 只剩 dtype 头文件），主路径是 FlashAttention / FlashInfer / Triton 等 backend 直接按 block_table + (num_blocks, page_size) 布局的 KV tensor 计算（仅 ROCm 保留 paged 系 kernel）。
  • 概念上升为接口：KVCacheSpec（v1/kv_cache_interface.py:107）描述每层 KV 的形状/页大小，KVCacheManager（v1/core/kv_cache_manager.py:117）在调度器侧记账，BlockTable（v1/worker/block_table.py:48）在 worker 侧变成 kernel 可直接吃的张量。
  • 衍生出整个生态：prefix caching、hybrid 模型分组、KV offload、PD 分离传输、投机解码 lookahead 块，全部长在同一套块池上。

2. 显存是怎么算出来的

启动时四步 collective（第 5 讲详述启动链），这里聚焦显存公式：

  1. profile_run：Worker.determine_available_memory（gpu_worker.py:460）在 memory_profiling 上下文中跑一次 model_runner.profile_run()（gpu_model_runner.py:6425，dummy run 最大 batch）。用 mem_get_info 前后差值算出 total_consumed，加 transient 峰值余量得 non_kv_cache_memory（utils/mem_utils.py:317）。
  2. 公式（gpu_worker.py:544-548）： 
    available_kv = requested − non_kv_cache_memory − cudagraph_memory_estimate
requested   = total_memory × gpu_memory_utilization
    注意 cudagraph 显存单独预留——捕获几十张 graph 的输入缓冲不是小数目。
  3. 页数：get_kv_cache_configs（v1/core/kv_cache_utils.py:2094）按组求 num_blocks = available_memory // page_size // group_size（:993），多 rank/PP 分段不一致时取最小值并按比例收缩张量（:2210）。
  4. 分配：initialize_kv_cache（gpu_model_runner.py:7616）→ _allocate_kv_cache_tensors（:7304）一次性大块分配，之后所有"分配/释放"都只是这个大张量上的索引记账，不再触碰 cudaMalloc。

3. KVCacheSpec 体系与 hybrid 分组

不同层要的 KV 形状完全不同。spec 体系（v1/kv_cache_interface.py）用一组数据类描述：

Spec位置对应注意力关键点
FullAttentionSpec:234普通 full attention页大小 = 2·block_size·kv_heads·head_dim·dtype
SlidingWindowSpec / RSWASpec:558 / :478SWA / 递归分段 SWA窗口外的块要换成 null 并释放（回收感知）
MLAAttentionSpec:388DeepSeek MLA无 K/V 之分，656B/584B 特殊布局（:408）
MambaSpec:709Mamba/SSM 状态"页"是每请求一份的 state；align 模式内存 page·(2+spec_blocks)（:729）
ChunkedLocalAttentionSpec / SinkFullAttentionSpec 等:518 / :782分块局部注意力 / attention-sink各带自己的命中/驱逐语义

分组：KVCacheCoordinator（v1/core/kv_cache_coordinator.py:60）持有全局唯一 BlockPool + 每组一个 SingleTypeKVCacheManager。混合模型（如 full + sliding + mamba）按 spec 分组、full attention 组排最前（:633），页大小不齐时统一放大 block_size（kv_cache_utils.py:1070）。

找最长命中（find_longest_cache_hit）各组算法差异巨大：

组类型搜索方向命中条件位置
FullAttention左→右逐块哈希命中，miss 即停single_type_kv_cache_manager.py:681
SlidingWindow右→左窗口内需连续块命中；窗口外补 null:897
Mamba右→左只需 1 个命中的 state block:1279

多组并存时 coordinator 做不动点迭代（coordinator.py:685-817）：任一组缩短命中长度就全体重扫，直到没有组再缩短。这就是 hybrid 模型 prefix cache 查找比单组贵的原因。

6. prefix caching 端到端与 CoW

一条命中的完整链路：

  1. 查找：scheduler 在 num_computed_tokens==0 时调 get_computed_blocks（本地哈希索引）+ connector 外部查找；num_computed_tokens = local + external（scheduler.py:829）。远端命中与本地部分块冲突时，截断本地尾块避免 CoW 竞争（:773）。
  2. 引用：命中块 touch ref_cnt+1 并移出 free 队列；cascade attention 用 ref_cnt == len(req_to_blocks) 判定"所有请求共享的公共前缀"（single_type_kv_cache_manager.py:821），让多个请求的 attention 共享一次 kernel 计算。
  3. CoW：只在部分块命中（fine-grained 模式，hash_block_size < block_size）时发生——_cache_partial_tail_block 登记部分哈希条目，下一步 allocate_new_blocks 发现 partial hit 就取新块执行 _apply_cow（:347-425）；运行中的 Mamba 请求因 block table 只增不改，改用 move_block_hashes 迁移哈希（:1590）。副本指令经 SchedulerOutput.kv_cache_block_copies 下发，worker 在前向前 copy_kv_cache_blocks_inplace 执行（gpu_model_runner.py:1223）。
  4. 驱逐：请求结束 ref_cnt−1；归零后带 hash 的块进 free 队尾继续当缓存，不带 hash 的进队首等着被复用；_maybe_evict_cached_block（block_pool.py:679）驱逐时只清哈希、不动 ref_cnt>0 的块。

7. KV offload 与 PD 分离

两套机制、一个抽象。共同思想：本地未命中的前缀，去"更慢但更大的地方"找。

7.1 KV offload 框架

v1/kv_offload/base.py 定义了对偶原语：调度侧 OffloadingManager（:220：lookup / prepare_load / complete_load / touch / prepare_store / on_request_finished）与worker 侧 OffloadingWorker（:545：submit_store / submit_load / get_finished）。Key = block_hash + group_idx（:26），所以 offload 与 prefix caching 共享同一套块哈希。实现有三档：

实现位置说明
CPU offloadingkv_offload/cpu/GPU↔CPU 异步 DMA（Triton swap kernel）；调度器管元数据，worker 管搬运
Tieringkv_offload/tiering/CPU 主层 + 文件/对象/点对点二级层，异步 lookup 与上浮 promotion
SimpleCPUOffloadv1/simple_kv_offload/以 KV connector 形态实现的轻量版（eager+lazy store 策略）

7.2 KV connector（PD 分离）

KVConnectorBase_V1（distributed/kv_transfer/kv_connector/v1/base.py:157）把"预填充实例 → 解码实例"的 KV 传输抽象成两组钩子：

侧钩子语义
Schedulerget_num_new_matched_tokens（:466）查外部命中；返回 None 表示"稍后再问"，bool 表示可异步
update_state_after_alloc（:501）分配完成后提交加载任务
build_connector_meta / take_events（:527/:580）每步元数据下发 / 事件回收
Workerstart_load_kv / wait_for_layer_load（:305/:323）逐层加载，与 forward 重叠
save_kv_layer / wait_for_save（:337/:359）逐层保存（预填充实例侧）
get_finished / get_block_ids_with_load_errors（:369/:387）完成/失败回报，驱动调度器晋升或重算

注册表在 factory.py:27：LMCache、Nixl、Mooncake、MultiConnector、OffloadingConnector 等。异步加载与失败重算：加载中的请求置 WAITING_FOR_REMOTE_KVS 并预占块（scheduler.py:1023）；完成则晋升并 cache_blocks（全命中也留最后 1 token 重算，:2673）；失败按 recompute_kv_load_failures 策略保留已验证前缀、把未写块记入置零清单后重试（:2651）。远端命中体现为 num_external_computed_tokens（kv_cache_manager.py:351）——外部上下文不占本地 prefill 计算，但槽位照常分配。

8. 正确性新机制四件套

这一节是"踩过坑的人才会写"的代码，也是面试/排查的高频考点：

机制位置解决的问题

另有两个 hybrid 特有的设计：Mamba align 模式（mamba_cache_mode，config/cache.py:139）按块边界对齐切 chunk、双块滚动写 state，使 SSM 状态也能参与哈希复用；partial_tail_offloads（kv_cache_manager.py:848）把"最后一个 prompt 边界的部分块"pin 住交给 connector offload，实现 sub-block 粒度的跨请求复用（Marconi 式稀疏保留）。
