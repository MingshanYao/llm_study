一句话：V1 调度器把"prefill 和 decode 混跑"统一成一个模型——每个请求都有一个 num_computed_tokens 在追赶它的总 token 数；schedule() 唯一的任务是在 max_num_batched_tokens 预算内，决定这一步让哪些请求追赶多少个 token。

本篇主线：统一模型 → 主循环两个 for（running 先、waiting 后）→ 三个 KV 交互点 → 抢占与状态机 → async scheduling 的乐观记账。

1. V1 调度的世界观：没有 prefill / decode 之分

Scheduler（v1/core/sched/scheduler.py:69）源码开头的注释（:441-450）值得逐字读：V1 里没有 prefill/decode 阶段之分，每个请求只有 num_computed_tokens 追赶 num_tokens_with_spec（= prompt + output + spec tokens，v1/request.py:276）。差距为几千 → 这一步做"长 prefill"；差距为 1 → 这就是 decode；差距为 500 但预算只剩 200 → 切成 chunked prefill。

这个统一模型带来两个直接推论：

  • 混批是免费的：decode 请求每步只吃 1 个 token 的预算，剩下的预算自然给 prefill 吃，不需要"阶段切换"逻辑。
  • chunked prefill 不是特性而是本态：prefill 大请求自动被预算切碎，跨越多个 step。真正的问题只剩"每一刀切在哪"，见 第 3 节。

3. schedule() 主循环走读

schedule() 本体在 scheduler.py:439（近 700 行）。流程如下：

图 1：schedule() 主循环。左列 running（decode + 在途 prefill chunk）先吃预算，右列 waiting（新 prefill）用剩余预算；④ 的抢占循环只发生在 running 侧，⑨ 的失败只会 break。

3.1 running 循环的关键细节

  • num_new_tokens 的计算（:516-520）：num_tokens_with_spec + num_output_placeholders − num_computed_tokens——async scheduling 的"占位 token"也计入（第 8 节）。随后经过 long_prefill_token_threshold 截断（:521）与 max_model_len 上限（:527）。
  • 预算耗尽时 continue 而非 break（:557-573）：某个 running 请求这次轮不到（num_new_tokens==0），跳过它继续看下一个——源码注释明说"不严格遵循 FCFS"，这让小请求不必排在大 prefill 后面。
  • chunk 大小决策：除预算截断外还有三种切法——disable_chunked_mm_input 时切到多模态 item 边界（:1559）；encoder cache/预算不足时截断（:1572）；Mamba "align" 缓存模式下按 block 边界对齐切分（_mamba_block_aligned_split，:362-437），保证 hybrid 模型的 SSM 状态哈希在块边界完整。
  • 在途 prefill 记账：请求是否处于"prefill 半途"由 request.is_prefill_chunk（request.py:188）+ _inflight_prefills（:1080）追踪，不再有 V0 时代的独立 request_state 概念。

3.2 waiting 循环的关键细节

  • 准入闸门：len(running) + num_waiting_for_streaming_input >= max_num_running_reqs 即停（:690）。
  • prefix cache 在这里查（:745-766）：仅当 num_computed_tokens==0（还没算过任何 token）时调 kv_cache_manager.get_computed_blocks；命中多少，本步就少算多少。
  • spec decode 的 pad（:884-897）：投机解码的 draft token 数会被 pad 到统一长度，保证 cudagraph shape 稳定。
  • 失败语义不对等：waiting 侧 allocate_slots 失败直接 break（:987-994）——绝不为了新请求去抢占已经在跑的 decode。这是"decode 延迟优先"的显式设计。

4. 与 KV cache 的三个交互点

调度器与 KV cache 的耦合被压缩到三个函数调用（都在 v1/core/kv_cache_manager.py，详见第 3 讲）：

交互点调用位置语义
get_computed_blockskv_cache_manager.py:229prefix cache 查找：只命中完整 block；即使全命中也保留最后 1 个 token 重算（max_cache_hit_length = num_tokens − 1，:259），因为需要最后一个 token 的 logits
allocate_slots:344为本步新 token 分配块。两个防御性设计：full_sequence_must_fit（:472，默认开）要求整条序列最终放得下才准入，防止 chunked prefill 上钩后显存不够、全体被抢占；watermark（:463）只在有请求被抢占过之后生效，避免水位长期偏低
cache_blocks:760step 结束（update_from_output 内，scheduler.py:2650）把已填满的块提交进 prefix cache，供后续请求命中

另有一个独立小系统：EncoderCacheManager（v1/core/encoder_cache_manager.py）按 mm_hash 缓存视觉 encoder 的输出，引用计数 + OrderedDict LRU 驱逐；每步的 encoder 输入调度由 _try_schedule_encoder_inputs（scheduler.py:1469）完成——输出区间重叠、未缓存、预算够才调度，否则把该请求的 num_new_tokens 截断到下一个 mm item 之前。

5. 抢占：V1 只有 RECOMPUTE

V0 时代有 RECOMPUTE / SWAP 两种抢占模式；V1 把 SWAP 删了，全仓只有一种抢占 = 重算（全仓 grep 无 PreemptionMode）。逻辑链：

  1. 触发：running 循环里 allocate_slots 返回 None（:588-625）——本步的 KV 分不下去了。
  2. 选择受害者：FCFS 下抢 running.pop()（队尾 = 最晚到的）；PRIORITY 下抢 (priority, arrival_time) 最大者（:590-594）。
  3. 执行：_preempt_request（:1274）：free 它的 KV 块 → free encoder cache → status=PREEMPTED、num_computed_tokens=0（= 之后从零重算）→ 清 spec tokens → 在途未确认的输出标记 stale（num_stale_output_tokens，async 场景）→ num_preemptions += 1 → prepend 回 waiting 队头（:1314，队头 = 最先恢复）。
  4. 恢复：waiting 循环里重新走 prefill；output tokens 重放（:876-879）；ModelRunner 侧 resumed_from_preemption 用新 block_ids 整体替换（gpu_model_runner.py:1442）。

为什么敢只有重算？因为重算的成本被 prefix cache 大幅摊薄：被抢占请求重算时，已提交进 prefix cache 的完整块会重新命中——最坏情况只是重算最后一个不完整块。SWAP 的"省重算"收益不再值得它的复杂度。

此外还有一条"全体抢占"路径：reset_prefix_cache(reset_running_requests=True)（:2441）强制清空 prefix cache 并把所有 running 请求打回 waiting，用于 connector 元数据失效等罕见场景。

6. 优先级与公平

  • 策略二选一：SchedulerPolicy = "fcfs" | "priority"（vllm/config/scheduler.py:22）。PRIORITY 用最小堆，比较序是 Request.__lt__ = (priority, arrival_time, request_id, id)（request.py:334）——数值越小越优先，同优先级按到达时间（还是 FCFS）。
  • 双队列选择：FCFS 下 skipped_waiting 优先（让异步 KV 加载完成的请求尽快恢复）；PRIORITY 下比较两队队首（_select_waiting_queue_for_scheduling，:2064）。
  • 公平性三板斧：running 优先于 waiting（decode 不饿死）；抢占只牺牲低优先级/队尾；num_new_tokens==0 时 continue 允许"插队"。
  • V0 的 delay_factor（延迟调度换吞吐）已删除；本树新增的节流旋钮是 DP 场景的 throttle_prefills / prefill_schedule_interval（:304、config :143）。

7. 请求状态机与 finish/abort

RequestStatus（request.py:348）：

WAITING ─┬─→ WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR ─┐
         ├─→ WAITING_FOR_REMOTE_KVS ────────────────┤（条件满足后晋升）
         └─→ WAITING_FOR_STREAMING_REQ ─────────────┘
WAITING ──→ RUNNING ⇄ PREEMPTED ──→ FINISHED_*
FINISHED 终态：STOPPED / LENGTH_CAPPED / ABORTED / IGNORED / ERROR / REPETITION（本树新增）
is_finished = status > PREEMPTED（枚举序即生命周期）
  • stop 判定逐 token 进行：check_stop（sched/utils.py:94）查 eos、stop_token_ids、length/max_model_len，以及本树新增的序列重复检测（check_sequence_repetition，:28，防退化复读，终态 FINISHED_REPETITION）。grammar 拒绝 token → FINISHED_ERROR（scheduler.py:1841）。
  • 清理：客户端 abort 走 finish_requests（:2237）两遍式处理；_free_request（:2300）释放块/encoder cache，req_id 进 finished_req_ids——注意它随下一个 SchedulerOutput 才发给 worker（让 worker 清 persistent batch，:1222），这是 pipeline 深度为 1 的消息传递。
  • 观测：make_stats（:2495）产出 running/waiting/kv_cache_usage/prefix_cache_stats，就是第 1 讲 coordinator 统计的数据源。

8. async scheduling：乐观并发

朴素主循环里，CPU 调度与 GPU 执行是串行的：schedule → 等 GPU → update → 再 schedule。GPU 越快，CPU 调度的固定开销越扎眼。async scheduling（本树默认开启，自动决策逻辑在 config/vllm.py:1095）把这个流水线打深一层：

图 2：同步 vs 异步 step。异步模式下 CPU 在 GPU 跑第 N 步时就完成第 N+1 步的调度与提交；代价是"结果未回来就记账"带来的对账复杂度。

乐观并发的三件配套机制：

  • 占位记账：AsyncScheduler._update_after_schedule（async_scheduler.py:19）在结果回来前就推进 num_computed_tokens，未确认的输出用 num_output_placeholders（request.py:151）占位，spec token 置 -1。下次调度时占位数参与 num_new_tokens 计算，到 max_tokens 的请求不再多调。
  • 早期返回 / EOS 兜底：GPU 上没法预知哪个请求这步会出 EOS，所以 model runner 维护 discard_request_mask（gpu_model_runner.py:2100）——乐观 seq_len 超界的请求不参与采样，结果回收时 num_output_placeholders -= len(new_token_ids) 对账（async_scheduler.py:61）。
  • 释放栅栏：第 N 步的 GPU kernel 可能还在读写第 N−1 步的 KV 块，所以块的 free 必须延迟：defer_block_free（scheduler.py:130）+ sched_step_seq / processed_step_seq 栅栏计数（:327、:2341）。结构化输出请求的占位未消化时还会把采样推迟到上一步处理完（core.py:665 的 pending_structured_output_tokens）。

9. SchedulerOutput：调度器的"合同"

调度器与 ModelRunner 之间没有方法调用，只有一份自描述数据。核心字段（v1/core/sched/output.py:193，节选）：

@dataclass
class SchedulerOutput:
    # 首次调度的请求：全量数据（prompt / mm features / block_ids / num_computed_tokens）
    scheduled_new_reqs: list[NewRequestData]
    # 已调度过的请求：只发增量 diff，minimize 通信
    scheduled_cached_reqs: CachedRequestData
    # req_id -> 本步调度 token 数
    num_scheduled_tokens: dict[str, int]
    total_num_scheduled_tokens: int
    # 投机解码：req_id -> draft token ids
    scheduled_spec_decode_tokens: dict[str, list[int]]
    # 多模态：req_id -> 需要跑视觉 encoder 的 item 下标
    scheduled_encoder_inputs: dict[str, list[int]]
    # cascade attention 用：各组 KV 的公共前缀块数
    num_common_prefix_blocks: list[int]
    finished_req_ids: set[str]          # 通知 worker 清 persistent batch
    free_encoder_mm_hashes: list[str]   # encoder cache 驱逐
    # KV connector 元数据 / 新块置零（防 NaN）/ CoW 拷贝 / 动态 spec K
    kv_connector_metadata: KVConnectorMetadata | None
    new_block_ids_to_zero: list[int] | None
    kv_cache_block_copies: list[KVCacheBlockCopy] | None
    num_spec_tokens_to_schedule: int

三个设计点值得留意：① scheduled_cached_reqs 是增量 diff——Worker 进程持久缓存了请求状态，长请求几千步只传增量（CachedRequestData，output.py:115）；② new_block_ids_to_zero——块池复用后显存里是脏数据，attention/SSM 前必须置零，把"零初始化"显式变成合同的一部分；③ kv_cache_block_copies——prefix caching 的 CoW（写时复制）也下放为 worker 侧的拷贝指令。
