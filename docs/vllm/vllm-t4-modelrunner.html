一句话：GPUModelRunner（v1/worker/gpu_model_runner.py:453，约 4700 行，是全仓最重的单文件）把 SchedulerOutput 这份"数据合同"翻译成 kernel 输入：维护持久批、准备 position/slot 映射、在 CUDA Graph 里重放前向，最后跑采样并把 token 写回。本篇的主线是 execute_model 与 sample_tokens 这对被刻意拆开的函数。

1. ModelRunner 的角色与持久批

为什么需要"持久批"？如果每步都从零构造 batch 张量，decode 阶段每次只多一个 token，重建整个输入的 CPU 开销会吃掉 GPU 收益。vLLM 的解法是持久批：Worker 里常驻两份状态，请求跨 step 累积更新：

状态位置内容
CachedRequestStategpu_input_batch.py:34每请求一份：prompt_token_ids、block_ids、num_computed_tokens、output_token_ids、采样参数、per-request generator（seed 复现）
InputBatchgpu_input_batch.py（创建于 runner :704）行式持久缓冲：CPU pinned 的 token_ids_cpu_tensor（[max_num_reqs, max_model_len] int32，:134）、num_tokens/num_computed 计数、MultiGroupBlockTable、采样参数张量、logits processors 状态
预分配 GPU 缓冲runner :764-810input_ids/positions/query_start_loc/seq_lens/discard_request_mask 等固定地址张量——CUDA Graph 的前提

InputBatch.remove_request（:530）有个值得学的细节：删除请求只在行上"挖洞"（索引表移除），物理行不动；批量删除后 condense()（:708）一次性把空洞压实，避免每步 memcopy。

图 1：一步执行的完整数据流。注意 ⑥ 与 ⑦ 之间没有"回到 GPU 等待"——grammar bitmask 是 CPU 侧准备好的张量，恰好卡在 logits 之后、采样之前。

3. _update_states：十件事

_update_states（gpu_model_runner.py:1192）按序做：

  1. 清 finished：self.requests pop + input_batch.remove_request（:1203-1217）；
  2. 新块置零 _zero_block_ids（:1221，KVBlockZeroer 用单独 stream）；
  3. 执行 CoW 拷贝 copy_kv_cache_blocks_inplace（:1223）；
  4. 处理 encoder cache 释放（:1231）；
  5. 未调度的请求移出持久批（保留 CachedRequestState，:1238）；
  6. 新请求建 CachedRequestState（:1295）；
  7. async+spec 的乐观扩展与延迟校正（:1363，依 valid_sampled_token_count 回滚 num_computed_tokens）；
  8. resumed_from_preemption：普通请求 block_ids.extend(new_ids)，被抢占恢复的请求整组替换 block_ids（:1442-1452），并从 all_token_ids 恢复输出；
  9. 更新持久批行：num_computed、block_table.append_row、token_ids（:1471）；
  10. condense + 重排 + refresh_metadata（:1516-1520）。

5. 编译与 CUDA Graph

模型前向不是裸调用 model(...)（_model_forward，:3879），而是包了三层：

  1. torch.compile piecewise：@support_torch_compile 装饰的模型由 VllmBackend/PiecewiseCompileInterpreter（compilation/backends.py:687/:805）在 attention 算子处切段编译（splitting_ops，:554）——每段可独立编译成优化 kernel。
  2. CUDA Graph wrapper：按模式包 BreakableCUDAGraphWrapper / CUDAGraphWrapper / UBatchWrapper（load_model，:5452-5478）。
  3. dispatch：cudagraph_dispatcher（v1/cudagraph_dispatcher.py）每步决定用哪张图。

图 2：CUDA Graph 的"捕获一次、重放万次"。混合模式决议取各 attention backend get_cudagraph_support 的最小值（_check_and_update_cudagraph_mode，gpu_model_runner.py:7153）——一个不支持的 backend 会把整批拉回 eager。

7. Attention 后端体系

后端注册在 v1/attention/backends/（flash_attn、flashinfer、triton_attn、flex_attention、rocm 系、mla 子目录、线性注意力/SSM 系等 20+ 文件）。选择入口 get_attn_backend（selector.py:101）→ CUDA 平台 get_attn_backend_cls（platforms/cuda.py:397）：显式 --attention-backend 只做校验，否则按优先级表（:83）取通过 validate_configuration 的最小 priority 后端：

场景优先顺序备注
MLA @ SM100FlashInfer_MLA → TokenSpeed → Cutlass → FA_MLA → FlashMLA → Triton_MLA:118-129
非 MLA @ SM100FlashInfer 优先SM100 要求 HND 物理布局（get_required_kv_cache_layout）
其余 GPUFlashAttention 优先block_size 须 16 的倍数（flash_attn.py:134）

接口契约在 AttentionBackend（v1/attention/backend.py:56）与 AttentionMetadataBuilder（:623）：get_kv_cache_shape / get_kv_cache_stride_order（KV 物理布局协商）、supports_block_size（决定调度器能用什么 block_size）、build(common_prefix_len, …)（每步元数据）、use_cascade_attention、build_for_cudagraph_capture。KV layout 的分歧是真实存在的：FlashAttn 用 (num_blocks, heads, block, 2·head)，FlashInfer SM100 要 HND——由 get_kv_cache_stride_order 在分配期统一，混合布局由 _has_mixed_attention_kv_layout（gpu_model_runner.py:7473）+ _reshape_kv_cache_tensors（:7356）处理。

8. ubatching：双微批交叠

调度器不感知 ubatch——切分发生在 ModelRunner（maybe_create_ubatch_slices，:4293）。UBatchWrapper（gpu_ubatch_wrapper.py:441）的逻辑：

  • 两个 ubatch 各自一个线程（各自 init CUDA context），捕获期主线程在 torch.cuda.graph 内 join 两线程再 cat 输出（:287）；
  • 执行期 UBatchContext（ubatching.py:20）用 CPU 环形事件 + barrier 保证"单线程语义"：_cpu_yield（:94）让两个 ubatch 的 Python 代码像交替协程一样跑，同时 GPU 侧 compute/comm 双 stream 通过 switch_to_comm/compute（:107）交叠——这就是 DB0/DB1 双微批的落地，用于隐藏 all-to-all 等通信空泡。

9. ModelRunnerOutput 与 async 输出

最终产物 ModelRunnerOutput（v1/outputs.py:261）：req_ids、sampled_token_ids、logprobs、prompt_logprobs、connector 输出、num_nans_in_logits（数值健康度）、cudagraph 统计、routed_experts（EPLB 用）。async 模式下走 AsyncGPUModelRunnerOutput（:259）：D2H 拷贝由独立 copy stream 完成（:4794），被 discard_request_mask 标记的请求以 invalid_req_indices 形式上报，由 scheduler 丢弃——这就是乐观调度"错了怎么办"的最后一环。
