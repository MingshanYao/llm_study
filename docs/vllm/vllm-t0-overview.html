一句话：vLLM 是一个"进程分治"的推理引擎——API/前端进程负责输入输出与流式体验，EngineCore 进程负责调度与 KV cache 生命周期管理，Worker 进程负责真正的 GPU 执行；三者之间用 ZMQ 消息总线连接，每一层都可以独立替换。

本篇给你：① 一张可对照源码的分层架构图；② 一次请求从 HTTP 到流式 token 的完整调用链（带行号）；③ 这棵 dev 树相对你印象中 vLLM 的关键变化（V0 已删除、ubatching、KV offload 等）。

1. 本系列怎么读：九讲地图

vLLM 代码量很大（仅 vllm/ 包就有数百个 Python 文件），直接按目录顺序读很容易迷失。本系列按"控制流"来切分：一篇对应请求生命周期中的一段，读完任意一篇都能独立回到源码对照。各篇之间的依赖关系是 0 → 1 → 2 → 3 为主线（前端 → 调度 → 显存），4 以后可按需跳读。

2. 一张图看懂：分层架构

下图自上而下是控制流的传递方向：用户请求从入口层进入，经引擎前端做输入/输出处理，通过 ZMQ 跨进程交给 EngineCore，由 Scheduler 决定本步调度内容，Executor 把任务分发给 Worker 进程，最终落到模型执行层。右向箭头之外，输出沿虚线反向回流。

图 1：vLLM（V1，dev 树）分层架构。实线箭头为请求/指令下行路径，虚线箭头为输出回流路径。EngineCore 是"大脑"：Scheduler + KVCacheManager 决定每一步做什么，Executor 只负责把决定送达 Worker。

这张图里有三个最值得记住的"关节"，后续每一讲都围绕它们展开：

关节位置职责
进程边界ZMQ 消息总线前端与 EngineCore 之间全部走消息（msgspec 序列化），任一侧崩溃不影响对端的数据结构
调度边界Scheduler.schedule() → SchedulerOutput调度器产出的不是"决定"，而是一份自描述的数据（本步调度哪些请求、各自几个 token、块的增量变化），Worker 是这份数据的纯消费者
执行边界Executor → Worker（collective_rpc）单机无 TP 时走 UniProcExecutor（同进程），多卡时走 MultiprocExecutor / Ray，EngineCore 代码不变

3. 从 V0 到 V1：这棵树已经是"纯 V1"

如果你上次认真读 vLLM 是 2024 年，请注意几个"地标"已经变了：

  • V0 引擎已整体删除。全仓搜索 VLLM_USE_V1 零命中——不存在 V0/V1 切换开关。vllm/engine/llm_engine.py:6 和 vllm/engine/async_llm_engine.py:6 只是两个指向 vllm.v1.* 的兼容别名（shim），vllm/v1/engine/llm_engine.py:48 的 LLMEngine 自述为 "Legacy LLMEngine for backwards compatibility"——即"同步引擎"这个用法保留，"V0 实现"没有了。
  • PagedAttention 从论文级概念变成了基础设施。V0 时代它是一个突出的 kernel 名；这棵树里它下沉为 v1/core/ 下的通用块管理（BlockPool / KVCacheManager / KVCacheCoordinator），并衍生出 hybrid 模型（Mamba + Attention）的多组 KV 布局、prefix caching、KV offload、PD 分离传输等一整个子系统。
  • speculative decoding、structured output 成为一等公民，直接接入 EngineCore.step 主循环（见 第 6 讲）。
  • async scheduling 默认开启：调度与 GPU 执行重叠一个深度（EngineCore.step_with_batch_queue，core.py:625），这改变了"一步 = schedule + execute + update"的朴素理解，第 2 讲详述。

以 POST /v1/chat/completions 流式请求为例。下图是时间轴（自上而下），圆角虚线框标出的部分是"每个 step 循环一次"的部分：

图 2：在线流式请求的进程间时序。注意 ③–⑦ 在 EngineCore 侧是紧密循环，与前端 ⑧–⑨ 完全异步——前端只在 PULL socket 上等输出，不参与调度决策。

逐步展开（行号可直接跳转）：

#阶段调用链
①HTTP → 引擎前端create_chat_completion（openai/chat_completion/serving.py:219）→ AsyncLLM.generate（v1/engine/async_llm.py:544）→ add_request（async_llm.py:283）→ process_inputs_async（v1/engine/input_processor.py，在线程池里做渲染与分词，避免阻塞事件循环）
②注册与发送前端先在 OutputProcessor 注册 per-request 的 RequestOutputCollector，再经 engine_core.add_request_async 把 EngineCoreRequest（msgspec 编码）发往 EngineCore 进程（v1/engine/core_client.py:1145）
③调度Scheduler.schedule()（v1/core/sched/scheduler.py:439）：内部先 kv_cache_manager.get_computed_blocks 查 prefix cache 命中，再 allocate_slots 为新 token 分配 KV block；产出 SchedulerOutput
④⑤执行Executor.execute_model（v1/executor/abstract.py:210）经 collective_rpc 到各 Worker：Worker.execute_model（gpu_worker.py:1019）→ GPUModelRunner.execute_model（gpu_model_runner.py:4166）：更新 persistent batch → 准备输入 → 模型前向 → 存中间态返回
⑥采样拆分本树的 decode 采样从 execute_model 中拆出：EngineCore 随后调 sample_tokens（gpu_model_runner.py:4553），应用 grammar bitmask 后跑 Sampler
⑦更新状态Scheduler.update_from_output（scheduler.py:1670）：把采样出的 token 写回请求状态、kv_cache_manager.cache_blocks 把完整 block 纳入 prefix cache、处理 stop 条件与抢占恢复
⑧输出回流EngineCoreOutputs 经 PUSH→PULL 回到前端；AsyncLLM 的后台任务 _run_output_handler（async_llm.py:657）循环取出并按 engine_index 分发
⑨流式输出OutputProcessor.process_outputs（output_processor.py:589）用 IncrementalDetokenizer 增量解码、检查 stop string，写入 collector；generate 的 AsyncGenerator 与 SSE 生成器逐块吐给客户端

5.2 离线路径（LLM.generate）

离线入口复用同一套引擎，只是把"流式 generator"换成"for 循环 step"：LLM.generate（entrypoints/llm.py:414）→ _add_completion_requests（entrypoints/offline_utils.py:290，逐条 LLMEngine.add_request）→ _run_engine（offline_utils.py:573）反复调 LLMEngine.step（v1/engine/llm_engine.py:296）直到 has_unfinished_requests() 为假。同步 LLMEngine 与 AsyncLLM 共享同一套 Input/OutputProcessor 代码；区别只在 EngineCore client 的形态——默认 SyncMPClient（子进程 + 后台线程），设置 VLLM_ENABLE_V1_MULTIPROCESSING=0 时退化为 InprocClient（同进程直调 EngineCore.step，core_client.py:306），这是单进程调试时最方便的模式。

6. EngineCore.step：主循环的五拍

整个引擎的"心跳"只有 30 行（v1/engine/core.py:584）：

def step(self) -> tuple[dict[int, EngineCoreOutputs], bool]:
    """Schedule, execute, and make output. ..."""
    if not self.scheduler.has_requests():
        return {}, False
    scheduler_output = self.scheduler.schedule(self._should_throttle_prefills())
    future = self.model_executor.execute_model(scheduler_output, non_block=True)
    grammar_output = self.scheduler.get_grammar_bitmask(scheduler_output)
    with (...):
        model_output = future.result()
        if model_output is None:
            model_output = self.model_executor.sample_tokens(grammar_output)
    self._process_aborts_queue()
    engine_core_outputs = self.scheduler.update_from_output(scheduler_output, model_output)
    return engine_core_outputs, scheduler_output.total_num_scheduled_tokens > 0

五拍节奏值得背下来，它是理解 vLLM 所有优化的坐标系：

  1. schedule：纯 CPU 决策——本步调度谁、各几个 token、KV 块怎么增减（第 2、3 讲）。
  2. execute_model（异步提交）：non_block=True 返回 future，GPU 开始跑；CPU 不等它，立刻做第 3 拍（第 4 讲）。
  3. get_grammar_bitmask：与 GPU 执行重叠，为结构化输出请求计算约束掩码（第 6 讲）。
  4. sample_tokens：等模型前向完成，采样下一个 token；decode 采样独立成拍是为了让 grammar bitmask 能在采样前注入，也让 CPU 调度与 GPU 前向的重叠成为可能。
  5. update_from_output：用采样结果更新请求状态、KV cache 引用计数，产出回程消息；处理此刻积压的 abort（_process_aborts_queue）。

注意：以上是"同步 step"的心智模型。开启 async scheduling 后实际运行的是 step_with_batch_queue（core.py:625）：schedule 第 N+1 步不等第 N 步的采样结果，用"占位 token"（num_output_placeholders）先记账，等第 N 步结果回来再对账。第 2 讲会展开这套乐观并发。
