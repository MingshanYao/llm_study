一句话：多模态的核心难题是"媒体 token 与文本 token 混在同一个序列里"——vLLM 用占位符区间（placeholder）标记媒体位置、用 mm_hash 内容指纹让 encoder 输出与 prefix cache 都能复用、用独立 encoder cache 避免重复编码。LoRA 的核心难题是"一个 batch 里混着多个适配器"——解法是逐 token 的适配器 id 映射喂给 punica kernel，权重则常驻在 stacked buffer 里靠 LRU 换入换出。

本篇主线：多模态六步流水线 → processor 体系 → mm_hash → encoder cache 记账 → LoRA 三层栈（请求/管理器/kernel）。

入口是 InputProcessor（vllm/v1/engine/input_processor.py:38，旧版 processor.py 已改名），它持有 InputPreprocessor（inputs/preprocess.py:48）与预算器 MultiModalBudget（multimodal/encoder_budget.py:45）。一次带图请求经过六步：

图 1：多模态六步流水线。③④ 的分界很有意思：mm_hash 在请求侧就算好，scheduler 与 runner 两级 cache 都以它为键——"同样的图第二次发"从 encoder 到 KV cache 全链路免费。

2. 解析与 processor 体系

vllm/multimodal/parse.py 的 MultiModalDataParser.parse_mm_data（:718）把原始输入（URL / base64 / PIL / 张量 / 直接给 embeddings）整理成每模态的 item 集合：ImageProcessorItems（:326）、AudioProcessorItems（:300）、VideoProcessorItems（:359）；limit_mm_per_prompt 的数量校验在 processing/context.py:409-428（报错文案会提示 --limit-mm-per-prompt）。

真正的 tokenizer + 特征提取发生在 processor 的 apply（processing/processor.py:1722）：

  • _cached_apply_hf_processor 调 HF processor（_call_hf_processor :1150），再把输出里的媒体特殊 token 定位出来；两种模板机制：PromptReplacement（:423，替换）与 PromptInsertion（:354，插入）；
  • 占位区间由 _find_mm_placeholders（:1127）找出，封装成 PlaceholderFeaturesInfo（:688，to_range() :699）；
  • 每个媒体项的特征怎么切成 kwargs 由 MultiModalFieldConfig（processing/inputs.py）描述，最终装进 MultiModalKwargs；
  • processor 按模型类注册——各模型文件里 @MULTIMODAL_REGISTRY.register_processor(...) 自带自己的 processor（multimodal/registry.py:98，装饰器 :142），没有全局默认表。

产物进入请求：process_inputs（input_processor.py:251）把 mm_kwargs / mm_placeholders / mm_hashes 按位置排序展平成 MultiModalFeatureSpec 列表（:344-377，数据类 multimodal/inputs.py:322）。

3. mm_hash：多模态的内容指纹

get_mm_hashes（processing/inputs.py:26-78）优先复用用户提供的 UUID；否则把媒体内容交给 MultiModalHasher（multimodal/hasher.py:51）：

输入类型参与哈希的内容位置
PIL 图像mode + 像素字节；EXIF ImageID 存在时用原始字节hasher.py:62-90
视频抽帧后逐帧哈希；给原始字节时直接哈希字节:92-96
tensor含 bfloat16 的字节视图（不能直接 tobytes）:98-118
ndarray / 其他dtype+shape+data / pickle 兜底:120-143

哈希算法默认 blake3，FIPS 环境切 sha256/sha512（:22-48，配置 MMHasherAlgorithm）。这个 hash 有两个下游消费者：

  1. encoder cache 命中键（下一节）；
  2. prefix cache 的块哈希：_gen_mm_extra_hash_keys（v1/core/kv_cache_utils.py:450-514）把 (mm_feature.identifier, 块内偏移) 追加进块哈希的 extra keys（聚合于 generate_block_hash_extra_keys :558-593，最终进 hash_block_tokens :596-623）——第 3 讲的块哈希公式在多模态下因此多了一项"这块里含哪张图的第几段"。

4. Encoder cache 与预算

媒体 embedding 的编码是贵的一次性计算，且一个媒体项可能被 chunked prefill 分多个 step 消费。两级 cache 配合：

角色位置语义
EncoderCacheManager（调度侧）v1/core/encoder_cache_manager.py:18按 mm_hash 记账（cached: dict[str, set[str]] :74）；allocate :185；请求消费完所有占位区间才释放（free :244，freed hashes 回传 :256）。调度器在放行 mm 请求前调用（scheduler.py:663/669/1088），完成时释放（:993）
runner.encoder_cache（GPU 侧）gpu_model_runner.py:572dict[mm_hash, Tensor]。_execute_mm_encoder（:3005）只把本步调度的 encoder 输入凑批执行（_batch_mm_inputs_from_scheduler :2956），输出存入（_cache_encoder_output :2993-3003）

消费端 _gather_mm_embeddings（:3227）按每个占位区间的 offset/length 从缓存张量切片（:3294-3296），mrope 类模型的多轴位置交错也在这里处理（:3314-3325）；最后 model.embed_input_ids(input_ids, multimodal_embeddings=..., ...)（:3607-3611）一次性把占位 token 的 embedding 替换掉——对模型而言，"图"和"文本"在进入第一层之前就已是同一种东西。

预算从哪来：启动 profile 时 profile_run（:6425）用"token 数最多的模态"造 dummy batch 跑一遍 encoder（model.embed_multimodal :6473，临时占位 tmp_i :6482），据此得 mm_encoder_cache_size；compute_mm_encoder_budget（encoder_cache_manager.py:273）拆成"每 step 编码预算 + cache 容量"，单请求媒体超限直接在 input_processor.py:463-476 拒绝。

5. LoRA：请求侧与管理器

图 2：LoRA 三层栈。适配器权重" residency"（常驻哪些槽位）与"激活"（本 batch 用哪些）是两级独立 LRU——加载贵、激活便宜，所以磁盘→CPU→GPU 的路径走注册 LRU，batch 切换只动指针。

请求侧的关键约定（lora/request.py:8）：lora_int_id 必须 > 0 且全局唯一（:40），相等性/哈希按 lora_name（:58-73）；MoE 3D 融合权重用 is_3d_lora_weight 标记（:31）。管理器加载链：_load_adapter（worker_manager.py:105）→ PEFTHelper.from_local_dir 读 adapter_config.json 并校验合法性（peft_helper.py:91-93,118）→ LoRAModel.from_local_checkpoint 读 adapter_model.safetensors（lora_model.py:167,205,269），落 CPU（:147）。

6. 层 wrapper 与 punica kernel

LoRA 不是"把 W 换成 W+BA"，而是每个并行层外面包一层 BaseLayerWithLoRA（layers/base.py:16）：基础权重照旧分片常驻，A/B 矩阵进 stacked buffer（形状按 max_loras × rank 预分配）。前向时 punica kernel 一次处理 batch 里所有 token，每个 token 按自己的适配器 id 选 A/B 行：

  • PunicaWrapperGPU（punica_wrapper/punica_gpu.py:33）持两份 LoRAKernelMeta 缓冲（token 级 + prompt 级，:57-73，cudagraph 专用的 lora 数量维度 :53-55）；
  • 每步 update_metadata（:75）消费 LoRAMapping（layers/utils.py:34）：`index_mapping` = 每个 token 的适配器 id（由 request_lora_mapping.repeat(num_scheduled_tokens) 展开，gpu_input_batch.py:1020-1027），`prompt_mapping` = 每个采样槽位的 id（采样出的 token 也要算 LoRA 投影）；
  • kernel 对：`add_shrink`（X·Aᵀ，SGMV 风格，:90）→ 中间加基础层输出 → `add_expand`（:123）；embedding 与线性层辅助路径 :171/:203；
  • 元数据链：set_active_loras（gpu_model_runner.py:2269-2277）→ mixin（lora_model_runner_mixin.py:73-91）→ set_adapter_mapping（model_manager.py:360-383）→ update_metadata。

这种"逐 token id + stacked buffer"设计的直接收益：一个 batch 混任意多个适配器不需要任何特殊调度——代价只是 punica kernel 比纯 GEMM 慢一些（SGMV/BGEMV 形状不规整）。
