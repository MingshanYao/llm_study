一句话：加载是一条四级流水线——config.json 定型 → 注册表把 architectures 变成模型类 → 建空模块树（同时装好 quant_method）→ 权重流式灌入，每个参数经过自己的 weight_loader 回调切成本 TP rank 的分片 → 最后 process_weights_after_loading 把 HF 布局重打包成 kernel 布局。量化不是"换模型"，是 Linear 层上的方法多态。

本篇主线：流水线 → 注册表 → 迭代器 → 分片回调 → 量化方法注册表 → 重打包 → KV 量化。

1. 加载四级流水线

图 1：加载流水线。③→④ 的折线表示"先建树、后灌水"：模块树先于任何权重存在，量化方法在此时就位，权重只是流经的流水。

# base_loader.py:43-82 的骨架（意译）
with set_default_torch_dtype(dtype):      # 空参数以目标 dtype 建模

    model.load_weights(weights_iterator)  # ④⑤ 流式灌入

2. ModelRegistry：架构名怎么变成类

get_model_architecture（model_loader/utils.py:52，缓存包装 :239-255）读 hf_config.architectures，交给 ModelRegistry.resolve_model_cls（models/registry.py:1296-1348）三级解析：

层级机制位置
in-tree 模型架构名 → ("模块","类名") 惰性映射字典（如 "LlamaForCausalLM"，:74+）registry.py:74+
Transformers 后备in-tree 找不到时尝试用 transformers 的实现（_try_resolve_transformers）:1148-1216
报错带提示_raise_for_unsupported 列出相近名字与帮助链接:1103-1134

自定义模型三种姿势：@register_model("名字") 装饰器（接受类或 "模块:类" 惰性字符串，:1057-1101）；trust_remote_code 动态模块（try_get_class_from_dynamic_module，:1171,1185）；或直接传实现类的 path 给 registry。架构名先过 _normalize_arch 归一化后缀（:1218-1242），所以 ...ForCausalLM/...ForConditionalGeneration 的大小写差异能兜住。

3. DefaultModelLoader 与格式选择

默认加载器（default_loader.py:43）两阶段：

  • _prepare_weights（:128-242）：下载/筛选文件——auto 格式下含 Mistral 系检测（:151-163），按格式套 allow_patterns（:166-184），index 文件去重防止重复读分片（:217-235）；
  • _get_weights_iterator（:244-319）：按环境与参数选迭代器——np_cache（:256）、fastsafetensors（:267）、instanttensor（:272）、多线程 safetensors（:278,300）、标准 safetensors（:287）、pt（:310）。迭代器实现都在 weight_utils.py：自然排序分片（:857）、大文件 NFS/RAM 预取启发式（:859-921）、tqdm 进度（:634）。

load_format 全家福（分发表 model_loader/__init__.py:50-66）：

format类一句话

老版本常见的 gguf load_format 在本树已从 LoadFormats 移除；GGUF 权重要先转 safetensors。加载完还有 strict 校验：迭代器未消费完或参数没被灌到都会报错（default_loader.py:436-470）。

4. TP 分片：weight_loader 回调

TP 下每个 rank 只存自己的那份权重。实现方式不是"加载器知道怎么切"，而是每个参数自带回调——model.load_weights 遍历迭代器时，按参数名把张量递给对应模块的 weight_loader(param, loaded_weight, shard_id, ...)：

层切法位置
ColumnParallelLinear输出维 narrow：loaded_weight.narrow(output_dim, rank*shard_size, shard_size) 后 param_data.copy_layers/linear.py:560-581
MergedColumnParallelLinear按 shard_id（含融合 gate_up 的两段）分别定位偏移:746+
QKVParallelLinearq/k/v 三段各自偏移（:1248-1261）；FP8 block-scale 分片校正（:1270-1274）；marlin 打包特判（:1280）:1222+
RowParallelLinear输入维 narrow（:1717-1737）；forward 末尾 all_reduce（:1766-1767）:1717+
VocabParallelEmbedding词表 padding 感知的分片vocab_parallel_embedding.py:445

新版还在迁移"v2 路径"：直接调用 param.load_column_parallel_weight(...) 等批量接口（:583-589、:1178、:1739-1746），跳过逐参回调的开销。

5. 量化框架：quant_method 多态

图 2：量化的全部秘密是"Linear 持有一个方法对象"。checkpoint 里的 HF 布局从左边进来，kernel 要的布局在右边出去，中间由方法对象的三个合同阶段衔接。

注册表侧（layers/quantization/__init__.py）：

  • QUANTIZATION_METHODS 列举全部方法名（:12-48）；第三方可用 @register_quantization_config 注册（:59-106）；
  • get_quantization_config（:109-183）：方法名 → config 类（"fp8"→Fp8Config :145，gptq/gptq_marlin→AutoGPTQConfig :153-154，compressed-tensors :155），在线量化简写（"fp8_w8a8" 等）也在这里展开（:177-178）；
  • 配置从 HF 的 quantization_config json 解析：get_quant_config（weight_utils.py:240-275，compression_config 兜底 :256）；
  • 逐层动态覆盖（同一模型不同层不同位宽）：get_dynamic_override（utils/gptq_utils.py:51）。

方法基类的三个合同（base_config.py）：create_weights（:31，按方法建参数，比如多建一个 weight_scale）、apply（:40）、process_weights_after_loading（:67）。

6. 重打包：为什么 load 完还要再动一遍

HF checkpoint 的权重布局是"给人看的"；GPU kernel 要的布局是"给机器算的"。两者之间的差全部由 process_weights_after_loading 抹平（遍历模块逐个调 quant_method 的钩子，model_loader/utils.py:100-152，attention 层单独一轮 :127-134）：

方法重打包内容位置
FP8per-tensor 策略会重新量化（:414）、权重转置以匹配 kernel（:423）；block-wise（如 DeepSeek 128×128，weight_block_size 配置 :115-132）保留块 scale；marlin 后端再重编码（:389-398）fp8.py:388-434
GPTQ-Marlinops.gptq_marlin_repack 把 int4 列布局转成 marlin 的 tile 布局marlin_utils_fp4.py:254,721、marlin_utils_fp8.py:147
AWQ位序重排 + AWQUtils.repackauto_awq.py:981（原理 docstring :102）
compressed-tensors按 recipe 分派：wNa16（:198,637,798）或 fp8-w8a8（:526,812-854），scheme 自己执行 repack（:975-976）compressed_tensors/…py
MXFP4（gpt-oss）GptOssMxfp4Config 把 HF 的 mxfp4 块转成 triton_kernels 的张量布局mxfp4.py:110-151,342,355

这个设计的好处：同一份 checkpoint、同一个模型类，换量化方法只是换掉 quant_method，模型代码零改动；kernel 选择也收敛到工厂函数（fp8 的 init_fp8_linear_kernel，kernels/linear/__init__.py:612，按形状/硬件挑 cutlass / triton / marlin / deep_gemm）。

7. KV cache 量化

KV 量化与权重量化共用 quantization_config，但作用点在 attention 层：

  • cache_config.cache_dtype 选 fp8_e4m3/fp8_e5m2（vllm/config/cache.py:24-25,76）；
  • Attention.__init__ 读入并决定是否加载 scale 参数（layers/attention/attention.py:271-273）；默认 1.0 的 q/k/v/prob scale 占位（:124-150）；_init_kv_cache_quant（:153-220）仅在后端需要时把 k_scale 注册成 parameter（:195-220）；
  • checkpoint 里的键名是 kv_scale，加载时经 get_cache_scale_mapper 映射成 attn.k_scale（base_config.py:194-227）；在线重算走 calculate_kv_scales（attention.py:586-589）；
  • 方法侧统一入口 BaseKVCacheMethod（quantization/kv_cache.py:42）。
