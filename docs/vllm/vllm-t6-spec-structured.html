一句话：投机解码把"采样 k+1 次"换成"草稿器免费猜 k 个 + 目标模型一次前向验证 k+1 个"——接受与否由拒绝采样保证输出分布与直接采样完全一致；结构化输出则是在采样前用 grammar 的 bitmask 把"非法 token"的 logits 压成 -∞。两者都汇合在同一个点：_sample 之前对 logits 做手脚。

本篇主线：proposer 家族 → step 全流程 → ngram 细节 → EAGLE 细节 → 拒绝采样数学 → scheduler/KV 配合 → 结构化输出管线与 backend 矩阵。

3. ngram：零模型成本草稿

最便宜的草稿器完全不跑模型——它赌"输出会重复 prompt 或已生成内容里的片段"。实现要点（ngram_proposer.py）：

  • 窗口参数 prompt_lookup_min/max（:19-21），草稿数 k = num_speculative_tokens（:25）；
  • 直接读持久批的 CPU 缓冲 num_tokens_no_spec 与 token_ids_cpu（形状 [max_num_seqs, max_model_len]，gpu_input_batch.py:134-140,390）——零 H2D 拷贝；
  • 核心是 numba @njit(parallel=True) 的 batch_propose_numba（:177）：KMP 式 LPS 在反转的 token 序列上找 [min_n, max_n] 内最长匹配，然后抄匹配后面的 k 个 token（_find_longest_matched_ngram_and_propose_tokens，:206-293）；
  • k 会被 max_model_len − total_tokens 截断（:226），超出 max_model_len 的请求整只跳过（:156-158）；
  • 线程数被钉在 1（:48，注释：留给 TP 并行），总量 ≥ 8192 token 才开并行（:36）。

适用场景非常明确：翻译/改写/代码补全这类"输入里已经出现过答案"的任务，接受率可以很高；闲聊任务接近零收益（白付验证成本——好在接受率低时只多花一次 k+1 前向中拒绝的部分，正确性无损）。

4. EAGLE：草稿模型怎么跑

EAGLE 用一个轻量草稿模型，输入 = 目标模型的特征层 hidden states + token，自回归地草拟 k 步。关键机制：

4.1 草稿模型的发现与加载

load_model(target_model)（llm_base_proposer.py:1330）加载草稿权重后，用"草稿模型的 attention 层 = 草稿配置的层列表 − 目标模型的层列表"求差集定位草稿层（:1343-1350）；embedding 与 lm_head 默认与目标模型共享（_maybe_share_embeddings :1424 / _maybe_share_lm_head :1517）。EAGLE-3 额外收集多个 aux hidden states 合并（model.combine_hidden_states，:531-543）。

4.2 草稿循环与草稿 KV

propose（:502）先做 first pass（set_inputs_first_pass :821 + 一次完整前向 :592-599），之后：

  • num_speculative_tokens==1（或并行草拟）直接返回（:612-621）；
  • 否则自回归循环 for token_index in range(k−1)（:670-760）：每步把 input_ids/hidden_states 写进预分配的 cudagraph 缓冲（:699-702），按层重建草稿 attention 元数据（draft_index=token_index+1，:689-695），草稿前向后采样（_sample_draft_tokens :743）；
  • 草稿 KV 必须归属同一个 kv cache 组（validate_same_kv_cache_group :1698-1717；组 id 与 block size 在 initialize_attn_backend :1721 从 kernel 实际 block sizes 推出 :1780-1795）；滑窗/Mamba 型草稿层因多步语义被拒（allowed_attn_types 检查，:632-642）；
  • 拒绝后的 slot 重算由 prepare_inputs（:1164）完成：num_rejected = n+1−len(sampled)（:1193-1195），配套 triton kernel 在 spec_decode/utils.py:88。

4.3 草稿模型的 CUDA Graph 策略

草稿执行体 EagleSpeculator（vllm/v1/worker/gpu/spec_decode/eagle/speculator.py:12，基类 autoregressive/speculator.py:28）配两张图（init_cudagraph_manager，:61-83）：草稿 prefill 用 PIECEWISE、草稿 decode 用 FULL_DECODE_ONLY（:71-73）。同时主图的 capture 尺寸被对齐到 uniform_decode_query_len = num_speculative_tokens + 1 的倍数（compilation.py:1518-1530）——这就是第 2 讲里"decode 被 pad 到 k+1"在图形状层的落点。

5. 拒绝采样：数学与 kernel

验证的目标是无损：输出分布必须等于直接用目标模型采样。实现在 vllm/v1/sample/rejection_sampler.py（RejectionSampler，:38，MAX_SPEC_LEN=128 :36），两条路径：

路径接受条件拒绝位怎么补kernel
greedy（全温度 0）draft token == 目标 argmax，逐位比较（:756-762）第一个不等处停止；全部接受才补一个 bonus token（:766-771）rejection_greedy_sample_kernel（:454-467）
采样逐位 u < p_target/q_draft（隐式在 kernel 内）恢复分布 max(p_target − q_draft, 0) 归一化后采样（:482-489），证明可还原目标分布rejection_random_sample_kernel（:491-506）

公共前置（forward :92）：bonus token 先采样（:127-140）；目标 logits 升 fp32、过 logits processors 与采样约束（:159-172）；目标概率 = softmax(fp32)（:479）。被拒槽位填 PLACEHOLDER_TOKEN_ID = −1，由 parse_output（:253）在记账时剥掉（调用点 gpu_model_runner.py:327,3770-3779）。

# 采样路径的直觉：draft 分布 q，目标分布 p
# 接受位：  Bernoulli(min(1, p/q))          → 分布恰好是 p 的"截断修正"
# 拒绝位：  sample(max(p − q, 0) / ‖max(p−q,0)‖₁)  → 把残差补回 p
# 两者合成的输出分布 = p，与直接采样目标模型完全一致

6. Scheduler 与 KV 侧的配合

投机解码对调度器是"隐形"的，只有四处可见：

  1. lookahead 分配：allocate_slots(..., num_lookahead_tokens=self.num_lookahead_tokens)（scheduler.py:578-580）——k 个草稿位先占 KV；分配失败会抢占其他请求（:588-646）。各方法的 lookahead 数在 :246-270 初始化；
  2. 批形状对齐：decode 被统一 pad 到 1 + num_spec_tokens 以匹配 FULL cudagraph（:885-897，pad_spec_decode :1076-1079）；
  3. 草稿往返：scheduled_spec_decode_tokens[req_id]（SchedulerOutput 字段，core/sched/output.py:212）带下去，回来时 update_draft_token_ids_in_output（:2168）按实际接受数修剪、被 grammar 拒的填 −1（:2189-2199）；
  4. async 乐观并发：use_async_spec_decode = use_async_scheduling and num_spec_tokens>0（:671-673）——第 2 讲的占位/校正机制在 spec 下最复杂：乐观接受、valid_sampled_token_count 事后回滚 num_computed_tokens，结构化输出请求还要过 pending_structured_output_tokens 门（output.py:241）。

统计面：SpecDecodingStats（spec_decode/metrics.py:18）逐位置记录接受数，Prometheus 指标 vllm:spec_decode_num_drafts/_num_draft_tokens/_num_accepted_tokens（:228-232）与 per-pos（:254-264）。

7. 结构化输出：从 JSON schema 到 bitmask

图 2：结构化输出管线。编译在请求进入调度前就开始（后台线程），但调度会等它——grammar 没就绪的请求停在 skipped_waiting，不占 token budget。

要点拆解：

  • backend 是单选：StructuredOutputManager（v1/structured_output/__init__.py:33）按 params.structured_outputs._backend 实例化一个后端（xgrammar :138 / guidance :142 / outlines :148 / lm-format-enforcer :154），不做运行时故障切换；_backend 在 InputProcessor 校验阶段就已定死（:131 注释）；
  • 自动选型：用户没指定时按优先级试——先 validate_xgrammar_grammar，schema 带 guidance 不支持的特性或 Mistral 非 tekken tokenizer 则落到 outlines/guidance（sampling_params.py:1050-1075）；
  • 编译异步：grammar_init（:169-176）把编译丢进 ThreadPoolExecutor，主循环不阻塞；请求状态置 WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR（v1/request.py:112-114），调度器把它放进 skipped_waiting（scheduler.py:2049-2056）轮询完成；
  • bitmask 形状：[num_struct_reqs × (1+spec), ⌈vocab/32⌉] int32——每个草稿位 + bonus 各占一行（__init__.py:226-241），所以投机解码与结构化输出的组合是"每行一个草稿位"地展开；
  • 应用时机：apply_grammar_bitmask（structured_output/utils.py:86）把压缩行号映射回 batch 顺序（考虑 spec 偏移，:110-116），异步 H2D 后在 GPU 上原地掩 logits（:148-150），调用点在 gpu_model_runner.py:4584-4587——紧贴 _sample 之前，这就是第 0 讲 step() 里 grammar_output 的去向。
