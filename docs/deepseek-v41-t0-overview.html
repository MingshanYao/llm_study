1. 前置知识速览：四个词看懂全文

这一节给完全没接触过大模型推理细节的读者补四块积木。已经懂的读者可以直接跳到第 2 节。

1.1 KV cache：模型边读边记的「笔记本」

大语言模型（LLM）生成文字时是一个 token（词元，可以粗略理解为「半个词」）一个 token 往外蹦的。每生成一个新 token，模型都需要「回头看」之前所有 token 的信息。Attention（注意力）机制为了回头看得快，会把每个历史 token 算出的 Key 和 Value 两组向量缓存下来，这就是 KV cache。

打个比方：你读一本 1000 页的资料并写总结，为了不每次都重读全书，你会边读边在便签上记「每页的要点索引」。KV cache 就是这些便签。便签的麻烦在于：读多长，就要存多长——上下文 100 万 token，便签就要记 100 万份，而且每层网络都要单独记一份。这些便签存哪？主要存在 GPU 的 HBM（High Bandwidth Memory，GPU 显存，快但小且贵）里，装不下时溢出到 SSD（固态硬盘，大但慢）。KV cache 有多大，直接决定了单张显卡能同时伺候多少用户、部署成本多少——这就是整篇论文拼命压缩它的原因。

延伸阅读：DeepSeek-V4 KV cache 设计解读。

1.2 prefill vs decode：先「读完」再「作答」

LLM 处理一次请求分两个阶段：

  • Prefill（预填充）：一次性读入用户给的整段 prompt（可能几千到几十万 token），为每个 token 算好 KV 并存进 cache。这一步计算密集——几百万个 token 一起做矩阵乘法，GPU 能吃满。好比考试前通读全书、做笔记，费脑子。
  • Decode（解码）：逐个 token 生成回答。每步只处理 1 个新 token，算量小，但要把整个 KV cache 从显存里搬出来读一遍——这一步访存密集（受显存带宽限制）。好比答题时不断翻自己的笔记，费的是「翻页速度」。

这两段的参数激活量在普通模型里是同一套。V4.1-Flash 的一个核心卖点（CED 架构，见第 5 节）就是让 prefill 阶段只激活 8B 参数、decode 阶段激活 16B 参数——「读书时轻装上阵，答题时全力以赴」，而这恰好匹配 Agent 场景「读得多、答得短」的负载。

1.3 MoE：一个超大公司，每次只派一支小分队

MoE（Mixture-of-Experts，混合专家）是把 Transformer 里的前馈层换成许多个并行的「专家」网络，每个 token 由一个路由器挑出少数几个专家来处理。好处是总参数可以做得非常大（知识储备多），但每个 token 实际激活的参数很少（算得便宜）。V4.1-Flash 每个 MoE 层有 1 个共享专家 + 384 个路由专家，每个 token 只激活其中 6 个路由专家（§4.2.1）。延伸阅读：DeepSeekMoE 解读与系列入门篇 MoE 零基础第 0 讲。

1.4 稀疏注意力：不必每句话都细读全文

标准注意力里，每个新 token 要和所有历史 token 算一遍相关度，长上下文下这笔账是平方级增长的。稀疏注意力的思路是：先用一个轻量的「索引器」（indexer，像一个图书管理员）快速给所有历史内容打分，只挑出最相关的 top-k 条参与精细的注意力计算，其余略过。代价是得额外维护一份「索引 KV」。V4 系列的 CSA（压缩稀疏注意力）更进一步：先把每 m 个 token 压缩成 1 条 KV entry，再在压缩后的条目上做稀疏选择。延伸阅读：DeepSeek-V4 Attention 设计解读、Lightning Indexer 解读、CSA 压缩过程详解。

2. V4.1-Flash 是什么模型

先给出一句话定位（摘要 + §2.1）：DeepSeek-V4.1-Flash 是一个原生多模态、上下文最长 100 万 token 的 MoE 大模型，专为把 KV cache 压到极限而设计。论文标题就叫「Pushing the Limits of KV Cache Compression」（把 KV cache 压缩推到极限）——它不是一篇追求榜单第一的模型报告，而是一篇「把部署成本打下来」的模型报告。

两个容易疑惑的点先解释一下：

  • 为什么叫「Flash」？论文没有正式定义这个名字，但对照可以看出来：同代还有 1.6T 参数的 DeepSeek-V4-Pro，Flash 是同系列里参数更小、激活更少、主打性价比的档位。V4.1-Flash 用 1/3 的总参数、1/4 的激活参数，做到了与 V4-Pro-Base 相当的水准（§4.3.2）。
  • 多模态指什么？模型从语言模型预训练一开始就同时喂图片和文本（§2.1：multimodal data incorporated from the start of language-model pre-training）。图片先经过自研的 DeepSeek-ViT 视觉编码器变成一串「视觉 token」，插进文本 token 序列里，之后所有层一视同仁地处理。它不只是「能看图」，还能在视觉 Agent 工作流里用屏幕截图做视觉检查和自我纠错（§1）。

3. 它为谁而生：长程 Agent 的三重瓶颈

3.1 长程 Agent 的负载长什么样

Agent（智能体）是能自主调用工具、连续多轮干活的 AI：写代码的 Agent 会反复读仓库、跑测试、改文件，一轮任务可能持续成百上千次模型调用，每次调用都携带越来越长的历史上下文。论文 §1 开篇就说：「长程 Agent 的普及让模型工作负载越来越 input-heavy（输入占大头）」。

为什么输入占大头？两个原因（§1、§2.2）：

  • 每次工具调用都是一次「重新读书」：Agent 每调一次工具，就要把系统提示、全部历史、工具返回结果重新喂给模型。如果 KV cache 命中不了（cache miss，即笔记丢了），就要重新 prefill 一大段文本——§2.2 原话：「频繁的工具调用产生大量 prefill 请求，在 KV cache 未命中时造成严重计算开销」。
  • 读的内容远多于写的内容：一个 Agent 轨迹可能输入几十万 token、只输出几千 token。计算和存储的大头都在输入侧。

3.2 三重瓶颈：算力、存储、带宽

论文把长上下文部署的负担归纳为三个互相叠加的瓶颈（摘要与 §1）：

图 1｜三重瓶颈与 V4.1-Flash 的三条对策（对应论文摘要、§1 Introduction）。

用开图书馆的比喻把三个瓶颈讲透。把 KV cache 想象成图书馆为每位读者准备的「读书笔记」：

  • 算力瓶颈：读者（Agent）每次回来都带着一大箱新书要登记造册。登记（prefill）本身就要动用全馆人手——长 prompt 的 prefill 是计算密集的，GPU 算力直接决定登记速度。笔记一旦丢失（cache miss），整箱书还得重新登记一遍。
  • 存储瓶颈：笔记越来越多，馆内快架（HBM，快但格子小）必须放「随手要翻的全局笔记」，放不下就得堆到地下库房（SSD，大但取货慢）。地下库房也会被塞满——这就是持久 KV cache 对 SSD 与主机内存容量的压力（§1）。
  • 带宽瓶颈：笔记在馆内和库房之间搬来搬去要过走廊（I/O 与互连带宽）。走廊一次只能过那么多人，搬得越多、等得越久，直接拖慢服务吞吐（§1：I/O and interconnect bandwidth also limit cache migration and loading）。

论文还点明了一个趋势性事实：之前的稀疏注意力工作（DeepSeek-V4 等）已经把长序列计算的成本大幅压下来了，于是持久存储与数据搬运反而成了越来越突出的瓶颈（§1）。这也是为什么 V4.1 这一代的主攻方向从「算得少」转向「存得少、搬得少」。

3.3 一个必须理解的分工：全局 KV vs 滑窗 KV

V4 系列每层都有两套 KV（§1）：

  • 全局 KV（global KV）：覆盖整个上下文的「全套笔记」，包括主 KV（main KV）和索引器 K（indexer K）。它必须常驻 HBM（推理时随时可能被任意位置的 query 查询），序列越长越大——长上下文下运行时 KV footprint 的主导项。
  • 滑窗 KV（SWA KV）：只保留最近 \(n_{win}\)=128 个 token 的局部笔记，窗口固定，存储量不随序列长度增长。但它有一个隐藏麻烦：滑窗 KV 依赖逐层累积的隐状态，丢了之后想精确恢复，得把最近 \(L \times n_{win}\) 个 token 逐层重放一遍（L 是层数）——这笔重算账催生了第 4 讲的 SWA Bounded Replay。

于是压缩战役分成两条战线：全局 KV（压它在 HBM 里的常驻体积）和持久 KV cache（为多轮会话缓存复用而存在 SSD/主机内存里的部分）。V4.1-Flash 的成绩分别是 1/4 和 1/8。

4.1 从数字到体感：890 B/token 意味着什么

「890 bytes」太抽象，我们换算一下（纯算术推演，论文未直接给出该算例，标注为推断）。全局 KV 常驻 HBM，它的大小决定了「一张卡能同时装下几个长会话」：

  • 100 万 token 上下文：全局 KV ≈ 1,000,000 × 890 B ≈ 890 MB。同样 1M 上下文，若按 V4-Flash 的约 1/4 倍率反推则约 3.5 GB，按 V1 的 437 倍率反推更是约 389 GB——后者单张最大的 GPU 都装不下，前者一张卡就能放下。
  • 多会话并发：以 32K 上下文的典型会话为例，全局 KV 仅约 28 MB/会话，一台 8 卡机在留给权重的空间之外也能同时挂相当数量的长会话——这正是「降低部署成本、扩大服务规模」的具体含义。
  • decode FLOPs 近乎恒定的含义：Figure 2 显示 V4.1-Flash 的单 token decode FLOPs 几乎不随上下文变长而增长（4K→1M 只涨 1/4），意味着模型「翻自己的笔记」的速度不会因为书变厚而明显变慢——长会话的生成延迟与短会话基本同级。

5. 技术全家桶一览（六讲内容的预告）

V4.1-Flash 的 KV 压缩不是单个技巧，而是一套「架构 + 缓存精度 + 部署策略」的联合优化（§1）。论文的视角很清晰：DeepSeek-V4 可以看作「SWA 局部处理主干 + 压缩的全局上下文」，所以 V4.1 的思路是简化全局分支、基本保留局部注意力设计。下面按六讲的顺序把全家桶每个部件用一两段话讲清「是什么、解决什么」。

图 3｜V4.1-Flash 全家桶位置图（简化自论文 Figure 3，§2.1）。左半是因果编码器（prefill 便宜），右半是解码器（decode 激活 16B）；黄色框是横跨全局的机制。CSA2 的三种模式、Engram/DSpark/FP4 细节分别在对应讲次展开。

5.1 CED：因果编码器-解码器架构（第 1 讲细讲）

是什么：CED（Causal Encoder-Decoder，因果编码器-解码器，灵感来自 YoCo）把 40 层网络劈成两半：下半 20 层是「因果编码器」，上半 20 层是「解码器」。解码器的全局 KV 不再由各层自己的隐状态算出，而是直接从编码器最后一层的隐状态 \(H_{L/2}\) 投影得到（§2.2，式 1）：

\[ C^{l} = H_{L/2}\, W^{KV}_{l}, \qquad Z^{l} = H_{L/2}\, W^{Z}_{l}, \qquad l > L/2 \]

其中 \(C^l\) 是第 \(l\) 层解码器的 KV entry，\(Z^l\) 是配套的压缩权重，\(W^{KV}_l, W^Z_l\) 是各层自己的投影矩阵。注意每个矩阵是各层独立的——解码器每层仍「各看各的」，只是看的原材料统一来自编码器末层。

解决什么：prefill 时解码器这 20 层不必对全部 N 个 token 做完整计算，序列复杂度从 \(O(NL)\) 降到 \(O(NL/2 + n_{win} \times L/2) \approx O(NL/2)\)——预填充计算近乎减半（§2.2）。这正是给 input-heavy 的 Agent 负载量身定做的：输入 token 数千千万万，但它们只需要「过一遍」编码器就能产出解码器全部层的全局 KV。这也是 8B/16B 激活参数差异的来源。

5.2 CSA2：跨层 KV 与索引复用 + 层级稀疏索引器（第 2 讲细讲）

是什么：CSA2（Compressed Sparse Attention 2，压缩稀疏注意力 2）是 V4.1 对全局 KV 的主压缩手段。它抓住三个相乘的压缩维度（§2.3）：条目大小（entry size，GQA/MLA 压 KV 头）、序列维（每 m 个 token 压成 1 条 entry）、层维（跨层复用缓存与选择）——CSA2 的独特点是把第三个维度用满，且缓存共享与索引复用互相解耦。每个 CSA2 层被静态分配为三种模式之一（§2.3.1，Figure 4）：

  • Full 模式：自己算主 KV 与 indexer K，完整跑索引器，产出新的 top-K 索引；
  • Reindex 模式：复用前一层的全局 KV 与 indexer K，但用自己的 indexer Q 重新打分，选出新的 top-K——缓存共享，但每层看到的内容可以不同；
  • Reuse 模式：全局 KV 和 top-K 索引全部复用，直接做稀疏注意力，连索引器都不用跑。

所有模式里每层保留自己的全局 Q 和 SWA KV（所以「读书笔记的钥匙」仍是每层独立学出来的）。此外，解码器还配了层级稀疏索引器（Hierarchical Sparse Indexer，§2.3.2）：解码器第一个 Full 层在全上下文打分时顺带按块（block）做粗筛，选出的块汇成一个共享候选池（最多 2048 块 × 每块 8 位置 = 16384 个候选位置），后续 Reindex 层只在池子里选 top-512——后续索引器的打分成本从「随上下文线性增长」变成常数。

解决什么：存储上，共享主 KV 与 indexer K 消除了层间重复缓存（配合 FP4 精度，全局 KV 压到 890 B/token，约为 V4-Flash 的 1/4）；计算上，Reuse 层完全跳过索引、层级索引器把后续打分限制在固定候选池。相比 V4 的 CSA+HCA 混合架构，V4.1 改用纯 CSA2，并简化了压缩器（去掉重叠窗口与绝对位置编码）与索引器（indexer K 直接从主 KV entry 投影，不再单独从隐状态压缩，§2.3）。Reuse 层的推理执行只需 15 个 kernel（prefill）/ 11 个（decode）（§3.2），实现又快又省。

5.3 四个架构扩展（第 3 讲细讲）

Single-Pass mHC（§2.4.1）：mHC 是 V4 引入的「多残差流」机制——在相邻 Transformer 块之间维护 n 条并行的残差流 \(X^l \in \mathbb{R}^{n \times d}\)，用可学习系数矩阵混合。问题：原始实现要三个内核顺序执行，激活访存是 \((4n+4)d\)，是理论下界 \((2n+2)d\) 的两倍。V4.1 的 Single-Pass 改动极小却巧妙：把输入混合系数错后一块（每个块使用上一块算出的系数 \(A_{l-1}\)），消除了数据依赖，于是残差更新、输入混合、系数预测可以融成单个内核 Mega-mHC，访存正好达到下界、减半——性能几乎无损。这属于「动了部署经济学」的改动：mHC 本身不省算力，省的是显存带宽。

Engram（§2.4.2）：条件记忆模块，思路是「把记忆从计算中解耦」——不靠大参数慢慢算，而是用 n-gram 多头哈希直接查表拿到记忆向量。V4.1-Flash 挂了 196B Engram 参数（分两个模块，放在第 1 和第 14 层）：每个模块用 2/3/4 阶 n-gram、8 个哈希头、每头一张约 1600 万条目的嵌入表，表与投影全用 FP8。推理时地址是确定性的，可以提前用 RDMA 从主机内存后台预取，预取与第一块 Transformer 的计算重叠。解决什么：给模型加「外挂记忆」，参数量巨大但访问极便宜。

DSpark（§2.4.3）：投机解码（speculative decoding，用一个便宜的小模型先「猜」好几个 token，再用大模型一次性验证）架构，特点是半自回归起草 + 置信度调度的验证长度：3 个滑窗 128 的 Transformer 块一次前向并行算出 5 个草案位置的基础 logits，一个小型 Markov 头建模草案 token 间的依赖，置信头预测每个位置的条件接受概率；调度器结合引擎吞吐曲线动态决定每个请求验证多长。与 V3 的 MTP 在预训练全程联合训练不同，DSpark 在主干预训练之后单独训练（主干冻结），后训练时与主干一起继续训练但不回传梯度到主干。解决什么：decode 阶段一步吐多个 token，提高解码吞吐。

FP4 主 KV cache（§2.4.4）：把全局主 KV 从 FP8 进一步压到 FP4。V4 已对索引器的 Q/K 做过 FP4 量化感知训练（QAT），V4.1 把 QAT 扩展到主 KV cache。格式上采用 OCP 标准 MXFP4 兼容的 E2M1 + 每 16 通道一个 E4M3 scale（类似 NVFP4 但去掉第二级全局 scale，论文论证了动态范围足够：KV latent 经 RMSNorm 后幅值上限约 \(\sqrt{512} \approx 22.6\)，训练中实测最大约 10，而格式支持到 448×6=2688）。量化在 RoPE 之后进行，注意力计算前反量化——不需要硬件原生支持 FP4 矩阵乘。SWA KV 因对量化敏感而保持 FP8。解决什么：FP8→FP4 让主 KV 在 HBM 与 SSD 上的存储再近似减半，是 890 B/token 的关键组成之一。

890 B/token 的具体构成（各组件各占多少字节）论文没有在本报告引用的章节里逐项给出明细，只给出总量与倍数关系；如需逐字节账目，建议等第 2、3 讲结合 CSA2 结构与 V4 系列文档进一步推算。

5.4 训练与推理基础设施（第 4 讲细讲）

训练侧（§3.1）：多模态训练基础设施做了三件事——对比学习阶段的通信-计算重叠（all-gather 藏进前向/反向）；视觉编码器与 LLM 解耦部署（encoder 复制到 LLM 参数树之外，三个阶段交替执行，LLM 阶段保持纯文本并行策略）；超长图文序列的均衡图像分片（一张图密集的长序列会打爆单机 I/O，把图按负载均衡切到各 CP rank，每图只读一次）。CSA2 的跨层共享给分布式训练带来真麻烦：共享的层可能被切到不同流水线阶段，论文用影子索引器（shadow indexer，每个参与阶段放一个可执行的轻量副本、逻辑上单一 owner）、流水线载荷扩展、微批次级共享状态管理三件套解决。Engram 的嵌入表按行切分、预取与视觉编码器计算重叠。

推理侧（§3.2）：采用 Encoder–Prefill–Decode（EPD）三段 disaggregation，视觉编码、预填充、解码各自独立扩缩并重叠执行。核心是持久 KV cache 管理 + SWA Bounded Replay：V4 部署中 SWA KV 占了持久 cache 近一半容量，但它的复用只发生在活跃会话的分钟级窗口内、会话结束即死——长期存 SSD 极不划算。V4.1 干脆把 SWA KV 踢出持久 cache，改存到一个只占每台机器 10% 主机 DRAM 的分布式内存池（TTL 只有几分钟，到期即回收；全局 KV 仍在持久 cache 里保底 72 小时以上）。踢出去必然有 miss，兜底就是 SWA Bounded Replay：丢了滑窗状态不再重放 \(L \times n_{win}\) 个 token，只重放最近 \(n_{win}\) 个并截断滑窗，接受近似状态（§3.2.2 给出公式：从位置 s 起重放时，位置 i 的 query 只看 \([\max(s, i-W+1),\ i]\) 内的 SWA keys）。实验显示性能几乎无损；分 Encoder 与 Decoder 两条路径，后者让 prefill 在编码器就收尾、解码器只需跑 \(n_{win}\) 个 token，进一步把预填充总量砍到约一半。这正是持久 KV 1/8 的来源：SWA KV 不再持久化（约省一半）×全局 KV 压到 1/4（§3.2.1）。

5.5 预训练（第 5 讲细讲）

是什么：45T token 多模态语料（文本 : 多模态 ≈ 7:1；多模态部分以网络原生图文对、交错图文与领域数据为主，不做大规模合成），序列从 64K 起步、34T token 处扩展到 1M。值得注意：稀疏注意力是从零直接在 64K 长度上训练的，没有任何稠密注意力热身阶段（§1、§4.2.2）——稠密热身曾是稀疏注意力训练的惯例，这里直接省掉。优化器配置是三代演进：线性层用 Muon（Query/Key 用 head-wise Muon，按头拆分预条件器），归一化层等非矩阵参数用 AdamW，Engram 嵌入表/token 嵌入/预测头用「动量更新 + Sinkhorn 平衡」（只带动量缓冲、效果超 Adam 且省优化器状态内存）；另有多模态各自独立的 aux-loss-free 负载均衡。视觉编码器 DeepSeek-ViT 单独两阶段训练（约 470 亿图文对的 SigLIP 对比学习 + 接 4B MoE LLM 的 2360 亿 token 自回归微调），之后才并入主干预训练。训练全程无不稳定。

5.6 后训练（第 6 讲细讲）

是什么：论文坦白：后训练没有任何算法创新，就是标准的 SFT → RL → OPD（on-policy distillation，在线策略蒸馏，用 40 多个教师模型做全词表蒸馏）；所有实质投入都在数据与工程上（§5.1）。三个值得记住的点：①大规模 Agent 任务自动合成流水线——把任务形式化为（问题、环境、验证系统）三元组，覆盖通用 Agent 与代码 Agent，模型甚至学着给自己造训练题；②DSec 沙箱平台支撑百万级并发沙箱（单节点容器密度从约 1000 提到 2500+，还要防模型「越狱」搞 reward hacking）；③可控推理努力：给模型一个标量旋钮 \(b \in \{1,\dots,100\}\)（系统提示里写 Reasoning Effort），RL 中用指数衰减的 token 长度惩罚 \(k(b) = k_0 \exp\!\left(-\frac{b-b_{min}}{\tau}\right)\) 让高努力档位少罚长度，一个 checkpoint 就能在成本-质量曲线上滑动——2026 年 9 月上线的公开 API 的 max/high/low 三档即对应 \(b=100/75/50\)（附录 C 给了这个指数设计的边际效用推导）。另有异步后训练基础设施（token 级中断、断点续跑）与多智能体 Agent Team 模式的初步实验（多 Agent 在各时限下全面优于单 Agent）。

7. 论文自己承认的局限与未来方向（§6）

技术报告的 Conclusion 部分通常最有信息量，V4.1-Flash 的 §6 写得相当诚实，分三层：

7.1 已做的声明

通过架构、缓存精度与部署策略的联合优化，全局 KV 压到 890 B/token（V4-Flash 的约 1/4）、持久 KV 压到约 1/8，同时性能显著优于 V4-Flash；与 GLM-5.3、Kimi-K3 等当代开源模型相比参数足迹小得多，却在关键基准上 comparable 甚至部分任务 superior。

7.2 局限（Limitations）——两条都关于「压缩的边界」

  • 鲁棒性边界尚未完全刻画：虽然 V4.1 简化了 V4-Flash 的不少组件，但新架构也带来了新的失效面。内部评测覆盖了大量边界条件、未观察到系统性能力退化，但论文明确承认：没有任何有限测试集能覆盖所有极端输入与部署条件——CSA2 的潜在选择错误（selection errors）与 SWA Bounded Replay 的近似状态重建，在未测试的边界情况下仍可能造成能力退化。
  • 基准饱和掩盖了真实差距：V4.1-Flash 与 Fable-5、GPT-6 Astra 等顶级模型的分数差距很小、日常体验相当，但论文直言「分数接近不等于在最难任务上追平前沿」——复杂高难度推理与边缘案例上与领先闭源系统仍有差距。

7.3 未来方向（Future Directions）

  • 扩大压力测试与评测栈，重点关注长上下文稀疏检索与 cache 恢复边界处的 SWA 状态重建；持续监控真实负载、系统性地刻画失效模式与鲁棒性边界。
  • 持续更新评测协议，严格评估最先进的推理边界。
  • 数据、模型容量与 RL 的协同扩展（coordinated scaling）：以 V4.1-Flash 为新起点，攻关大规模数据合成与 RL 扩展的关键难题。
  • 模型-脚手架协同设计（model–harness co-design）：让模型与 Agent 框架作为一个联合系统一起进化优化。
  • 总纲：降本与能力扩展两条腿走路，让高能力 Agent 更易得、更易部署。

8. 本讲小结与自测清单

8.1 本讲小结

  • V4.1-Flash 是 552B 主干（+196B Engram）的多模态 MoE 模型，1M 上下文，prefill 激活 8B / decode 激活 16B，预训练 45T token。
  • 它的靶子是长程 Agent 的三重瓶颈：prefill 算力（CED 近乎减半）、存储（CSA2+FP4 把全局 KV 压到 890 B/token ≈ V4-Flash 的 1/4、V1 的 1/437）、带宽/持久存储（SWA Bounded Replay 把持久 KV 压到约 1/8）。
  • 压缩的哲学：全局分支大胆共享与简化（纯 CSA2 + 三种复用模式 + 层级索引器），局部分支（SWA）保持逐层独立与 FP8 精度。
  • 成绩：性能不但没掉还反超基线，与 1.6T 的 V4-Pro-Base 相当，Agent 任务可完成 95% 以上真实任务；诚实承认 CSA2 选择错误与近似重建的鲁棒性边界、以及最难任务上的差距。

8.2 自测清单（点击括号展开答案）

  1. 为什么说 Agent 工作负载是「input-heavy」的？这对模型设计提出了什么要求？
    答案Agent 每次工具调用都携带完整历史与工具返回重新请求模型，读入的 token 远多于生成；一旦 KV cache 未命中就要重新 prefill 大段文本。因此模型要优先降低 prefill 的计算成本（CED：prefill 只需跑一半的层，激活 8B），并让 KV cache 便宜地持久化与复用。
  2. 全局 KV 和 SWA KV 有什么本质区别？为什么 SWA KV 不适合长期持久化？
    答案全局 KV 覆盖全部上下文、体积随序列增长、必须常驻 HBM；SWA KV 只保留最近 \(n_{win}\)=128 个 token、体积与序列长度无关。SWA KV 的复用只发生在活跃会话的分钟级窗口内、会话结束即失效，与持久 cache 的 72 小时级保留策略不匹配——长期存 SSD 花钱买了一个基本不会命中的缓存（§3.2.1）。
  3. 890 bytes/token 这个数字压缩了什么？两个倍数（1/4 与 437 倍）分别相对谁？
    答案890 B/token 是 V4.1-Flash 的全局 KV cache（常驻 HBM 部分）每 token 体积；1/4 相对 DeepSeek-V4-Flash，437 倍相对 DeepSeek-V1（摘要、Figure 1(b)、§6）。
  4. CSA2 的三种模式分别复用什么、各自解决什么？
    答案Full 模式完整计算（生成全局 KV、跑索引）；Reindex 模式复用全局 KV 与 indexer K、用自己的 Q 重新选 top-K（省缓存但不省选择自由度）；Reuse 模式连 top-K 索引也复用、跳过索引计算（最省）。存储省在共享 KV，计算省在复用索引，两者解耦。
  5. SWA Bounded Replay 用什么换了什么？为什么敢这么换？
    答案用「近似」换「重算」：丢失滑窗状态后不再精确重放 \(L \times n_{win}\) 个 token，只重放最近 \(n_{win}\)=128 个并截断滑窗，接受近似状态。敢换的依据是实验显示性能退化可忽略；且后训练时同步模拟了这种重放（train-aware adaptation，§3.2.2）。论文同时在 §6 承认这是需要在极端边界下继续压力测试的点。
  6. 「推理努力」旋钮是怎么训练出来的？API 的 max/high/low 对应什么数值？
    答案RL 时在系统提示里注入标量 \(b \in \{1,\dots,100\}\)，同组内做组相对优势计算，长度惩罚系数随 b 指数衰减 \(k(b)=k_0\exp(-(b-b_{min})/\tau)\)——高努力档位允许更长的思考（§5.1.4）。API 三档 max/high/low 对应 \(b=100/75/50\)（§5.1.4 表 2）。
