TL;DR：混合注意力把 KV cache 从「一种条目」变成了五类异构条目（CSA Indexer / CSA Main / HCA / 各层的 SWA 窗 / 未压缩尾部缓冲），尺寸和淘汰策略逐层不同，PagedAttention 的同质假设直接失效。V4 的解法是拆成两个组件：① KV Cache（经典分页式，每请求多块）只装压缩条目，每块覆盖 \(\mathrm{lcm}(m,m')=128\) 个原始 token，产出 \(k_1=128/4=32\) 条 CSA 条目 + \(k_2=128/128=1\) 条 HCA 条目，同块分段共存；② State Cache（每请求固定一块，大小与上下文长度无关，Flash 约 4.6 MB）把 SWA 窗口和还没攒够压缩窗口的未压缩尾部当状态空间模型的状态管理。落盘时只存压缩条目，SWA 则有 Full / Periodic / Zero 三种存法可按部署场景选型。最终 1M 上下文的 KV cache 只有 V3.2 的 7%（Flash）/ 10%（Pro）。

1. Cache 里有什么：混合注意力撕出的五类条目

传统 Transformer 的 KV cache 是同质的：每一层都缓存「每个 token 一组 K/V」，唯一要管理的量是长度。DeepSeek-V4 换成 CSA/HCA 交替的混合注意力之后（架构见姊妹篇），不同层产出的条目种类、条目数量、淘汰规则全都不一样：

  • 压缩率不同：CSA 层每 \(m=4\) 个 token 压成 1 条 entry，HCA 层每 \(m'=128\) 个 token 压成 1 条 entry（\(\gg m\)）——同样是「缓存 1M token」，HCA 层只要 8192 条，CSA 层要 26 万条。
  • CSA 层多一套 Indexer 缓存：稀疏选择由 Lightning Indexer 在压缩 entry 上打分，其压缩 indexer keys \(K^{\mathrm{I}}_{\mathrm{Comp}}\in\mathbb{R}^{n/m\times c_I}\)（\(c_I=128\)）也要缓存——这是一套维度与主注意力不同的额外条目。
  • 每个 CSA/HCA 层还带一个 SWA 窗分支：最近 \(n_{\mathrm{win}}=128\) 个 token 的未压缩 KV，弥补「query 看不到自己所在压缩块」造成的局部信息缺口。窗口滑动，旧条目直接淘汰。
  • 未压缩尾部也是缓存状态：压缩按完整窗口进行，尾部不足 \(m\)（或 \(m'\)）个 token 时没法压，这些 token 及其隐状态必须原地等待——论文明确把它们「也纳入 KV cache 框架管理」。
  • 纯 SWA 层（Flash 的前 2 层）只有滑窗条目，没有压缩条目。

图 1｜五类 KV 条目按层类型分组。压缩条目（Indexer / Main / HCA）随序列增长线性累积、进 KV Cache；SWA 窗与未压缩尾部大小有上界、进 State Cache。Indexer 条目是 CSA 独有的额外维度（\(c_I=128\)，与主注意力的 512 维不同）。逐条目字节为按混合精度口径的推算，见 §6。

2. 为什么 PagedAttention 装不下

PagedAttention 及其变体的前提是所有层的 KV 条目同质：同样的每-token 尺寸、同样的增长与淘汰规则，于是可以统一分页、统一索引。V4 的混合注意力打破了两个基本假设（论文原文归纳）：

  1. cache 策略多样：SWA 层只保留最近窗口、旧条目可随时丢弃；压缩层条目 append-only 且序列长度按 1/m、1/m′ 折叠；尾部缓冲则会「攒满即压缩、原地清空」。一个统一页表无法同时表达这几种生命周期。
  2. 高性能 kernel 的对齐约束：注意力 kernel 通常假设每个 block 固定 \(B\) 条 token，以换取最优访存；压缩之后「每块 \(B\) 条 entry」对应的原始 token 数在 CSA 层是 \(B\cdot m\)、HCA 层是 \(B\cdot m'\)，再加上 kernel 对 cache line 对齐、按索引 gather 的要求，块的组织必须与 kernel 联合设计。

V4 对这两个障碍各给了一个机制：把「窗口态」从「前缀态」里拆出来（State Cache，§3.2），以及以 \(\mathrm{lcm}(m,m')\) 为块粒度的 kernel co-design（§5）。

3. 整体布局：KV Cache + State Cache 双组件

论文 Figure 6 给出的布局可以概括成一句话：前缀类的压缩条目走经典分页，位置类的易变态走状态池。

图 2｜DeepSeek-V4 的 KV cache 总布局（依论文 Figure 6 重绘）。左：State Cache，每请求固定一块，装 SWA 窗（各层）与未压缩尾部（各压缩层）；右：KV Cache，经典分页，每块内 CSA Indexer / CSA Main / HCA 三种段按同一 token 区间对齐共存。尾部攒满压缩窗口即压缩成 entry、写入 KV Cache（灰箭头）。

3.1 经典 KV Cache：以 lcm 为周期的压缩条目分页

每请求分配多个块，每块覆盖 \(\mathrm{lcm}(m, m')\) 个原始 token。选 lcm 是为了让两类压缩层的窗口边界在这个区间上同时对齐：区间内恰好产出 \(k_1=\mathrm{lcm}(m,m')/m\) 条 CSA 条目和 \(k_2=\mathrm{lcm}(m,m')/m'\) 条 HCA 条目。Flash 配置下 \(\mathrm{lcm}(4,128)=128\)，即每块 128 个原始 token → 32 条 CSA Indexer + 32 条 CSA Main + 1 条 HCA：

图 3｜Flash 配置下一个 KV Cache 块的内部构成。每 4 个原始 token 压出 1 条 Indexer entry（128 维）与 1 条 Main entry（512 维），128 个 token 才压出 1 条 HCA entry——所以块内 HCA 段近乎全空。字节按 §6 的混合精度口径推算。

3.2 State Cache：把窗口与尾部当「状态」管理

SWA 窗和未压缩尾部有一个共同的数学性质：它们只由当前位置决定，不由整个前缀决定。SWA 窗天然只含最近 \(n_{\mathrm{win}}\) 个 token；压缩尾部最多攒 \(m-1\)（CSA）或 \(m'-1\)（HCA）个 token 就会被压走。论文据此把它们类比成状态空间模型（SSM）的序列状态：与上下文总长无关、可整体换入换出。于是管理方式也换了——

预分配一个固定大小的状态池，按序列动态租借。每个运行中的请求租一块，里面有各层的 SWA 段（每个 CSA/HCA/SWA 层各 \(n_{\mathrm{win}}\times 512\) 维）和各压缩层的尾部段。请求结束或被抢占时整块归还即可，不需要页级淘汰。按 Flash 配置推算一块的容量：

  • SWA 段：43 层 × 128 token × 576 B ≈ 3.0 MB
  • CSA 尾部段：21 层 × ≤3 token × 576 B ≈ 0.04 MB
  • HCA 尾部段：20 层 × ≤127 token × 576 B ≈ 1.4 MB
  • 合计 ≈ 4.6 MB/请求，与 1M 还是 4K 的上下文无关（Pro 约 6.8 MB）。
论文只说「固定且有限大小的状态池」，没有给出块容量数字与分配粒度（是否按 token 槽位细分）；4.6 MB 是按配置逐层累加的估计，实际以参考实现为准。另外，Figure 6 是逻辑视图——块在各层的物理张量排布（是否逐层独立 block pool）论文未写明。

4. 特写：Indexer Cache 是什么、怎么算、怎么用

前三节把 Indexer 段当作块布局里的一个「格子」带过了，这一节把它放大。它最容易让人困惑，因为一个 Lightning Indexer 里同时存在三种容易被混为一谈的量：缓存的 keys、现算的 queries、即弃的 scores。先分清这三样，Indexer Cache 就不再神秘。

4.1 它是什么：一次压缩，两份产出

每个 CSA 层的压缩器只干一件事：把每 4 个 token 的隐状态门控池化成 1 条 entry（机制详见姊妹篇式 9–12）。但它配了两套独立投影，对同一批 token 压出两种条目：

  • 正文 entry（512 维）：\(C^{\mathrm{Comp}}\)——真正的注意力素材，等 top-k 挑中后作为 K=V 进核心注意力；
  • 目录卡片（128 维）：\(K^{\mathrm{I}}_{\mathrm{Comp}}\)——同一批 token 在 indexer 自己空间里的压缩「指纹」，专供未来的 query token 打分用。

所谓「题库」，就是全部历史块的卡片按块序排成的数组（每个 CSA 层一套），住在 KV Cache 块的 Indexer 段（图 3 第一行），全 FP8 存储约 128 B/条。它能被缓存的根本原因只有一个：卡片只依赖「那 4 个 token」的隐状态，算完永不改变——是标准的不可变前缀数据。

图 4｜一次压缩，两份产出。每 4 个 token 攒满一个压缩窗口，同一套门控池化机制配两套投影：压出 512 维「正文」（进 Main 段，等被选中）与 128 维「目录卡片」（进 Indexer 段，供打分）。二者同块序号、同生同灭。

4.2 它怎么被算出来：写入节奏

  • Prefill：整段序列进来，压缩器沿序列滑窗推进，每攒满 4 个 token 产出「1 条卡片 + 1 条正文」，顺序追加进块内两段；
  • Decode：每生成 1 个 token，当前压缩窗口计数 +1；恰好攒满 4 个时当场压缩，新卡片与新正文同时入库。写入频率 = 每 4 token 一次、每次两条；
  • 尾部：不足 4 个的在途 token 留在 State Cache（§3.2），攒满即补压——所以目录柜永远不会缺「最新完整块」的卡片。

4.3 它怎么被使用：解码一步的四步旅程

看 layer-2（CSA 层）处理一个新 token 的全过程（Flash 数字）。打分公式（式 16）长这样：

\[ I_{t,s} \;=\; \sum_{h=1}^{64} w^I_{t,h}\cdot \mathrm{ReLU}\!\left(q^I_{t,h}\cdot K^{\mathrm{I}}_{\mathrm{Comp},s}\right) \]

图 5｜解码一步中 Indexer Cache 的完整旅程（layer-2，Flash 配置）。①写入：块攒满 4 token 时压缩出卡片 + 正文（见图 4）；②打分：新 token 的 64 个 query 头对每张卡片各得一个标量分，n/4 张卡片扫一遍；③选择：top-k=512 产生索引列表，按索引去书架取正文；④消费：正文 + SWA 窗进核心注意力。query、分数、索引当步即弃；卡片与正文留在 cache。每个 CSA 层都有独立的一套书架与目录，每步各翻一遍。

逐步对应：② 里 64 个 query 头与同一张 128 维卡片各做一次内积，ReLU 后按可学习头权 \(w^I\) 加权求和——一张卡片得一个标量。③ 里取 top-k=512（Pro 为 1024）得到索引列表，按索引去 Main 段 gather 正文——kernel 按任意索引列表取条目的能力，正是 §5 co-design 的要求之一。④ 里 512 条正文与 SWA 窗一起进核心注意力（MQA + attn sink），产出本层结果。

两个代价注脚：每步每层都要全量扫目录——1M 上下文时每层每步约 \((10^6/4)\times64\times128\) ≈ 2×10⁹ 次乘加，论文因此把 indexer 的计算放到 FP4 精度（§2.3.4）；也因为每步要整段连续扫，Indexer 段在块内整段连续排布、对齐 cache line（§5）。

5. 与稀疏注意力 kernel 的 co-design

块的组织不是 cache 管理器单方面定的，而是与注意力 kernel 联合设计（论文称「Sparse Attention Kernel Co-Design」），要点有三：

  • 变长 token/块：常规 kernel 为吃满算力假设每块固定 \(B\) 条 token；V4 的稀疏 kernel 允许不同层每块容纳可变数量的原始 token而不掉性能——这正是「同一块里 CSA 段 32 条、HCA 段 1 条」能成立的前提。
  • 对齐与填充：把块填充到 cache line 边界可提升访存效率；训练侧的上下文并行（CP）同样按 \(\lceil s/m\rceil + 1\) 补齐压缩条目、再用 select-and-pad 算子重排，两者是同一思想在训练/推理两侧的投影。
  • 可见性两类：HCA 与 CSA Indexer 的「每个 query 能看到哪些压缩条目」可以按规则预计算；CSA 稀疏注意力则由 top-k selector 显式给出索引列表——cache 布局必须支持 kernel 按任意索引列表 gather 压缩条目。

对照官方口径：1M 上下文下，DeepSeek-V4-Pro 的累计 KV cache 为 V3.2 的 10%（9.5× 缩减），V4-Flash 为 7%（13.7× 缩减）；若以 BF16 GQA8（8 组、head dim 128）为基线，V4 系列把它压到约 2%。三个乘法因子分别是：序列维压缩（÷4、÷128）、头维/头数精简（MQA 单 KV 头、512 维）、存储精度（RoPE 64 维 BF16 + 其余 FP8，较纯 BF16 近乎减半）。注意 SWA/尾部状态是 O(1) 的——这正是长上下文下省显存的关键结构性原因：随长度增长的只有压缩条目。

7. 盘上存储：共享前缀复用与 SWA 三策略

Agentic 工作流里大量请求共享同一段长前缀（系统提示、工具手册、代码库上下文），逐请求重复 prefill 极不划算。V4 的推理框架把 KV cache 落盘，命中前缀直接读回。但「哪些条目值得存」要分两类讨论：

CSA/HCA 压缩条目：全存。它们本来就是体积最小、随前缀单调追加的部分，直接全部落盘。命中时读回前缀对应的压缩条目，直到最后一个完整压缩块为止；尾部不完整块的未压缩条目没有存，需要重算这段尾 token 来恢复（反正它最长也就一个块，128 token）。

SWA 条目：三选一。SWA 条目未压缩、且每层都有，全量体量约为压缩条目的 8 倍（论文口径），成为盘上存储的主要矛盾。论文给出三种可按部署场景选型的策略：

图 6｜盘上 SWA KV 的三种存法。三者共享同一份盘上 CSA/HCA 压缩条目，区别只在 SWA 的存储量与命中后的重算量。①零重算但写放大严重（每次命中只读得动「每层最后 n_win」那一小截）；②用周期 checkpoint 换取可调折中；③零存储，代价是重算最后 \(n_{\mathrm{win}}\cdot L\) 个 token。

③ 之所以可行，靠的是 SWA 的一个 telescoping 性质：第 \(\ell\) 层某 token 的 SWA KV 只依赖第 \(\ell-1\) 层最近 \(n_{\mathrm{win}}\) 个 token 的 SWA KV。要从盘上恢复「最后一层」的最近 \(n_{\mathrm{win}}\) 条 SWA KV，依赖链沿层向后每层扩 \(n_{\mathrm{win}}\) 个 token，\(L\) 层合计重算最后 \(n_{\mathrm{win}}\cdot L\) 个 token 即可——而这些 token 所需的 CSA/HCA 压缩条目已经落盘，重算只是重建 SWA 分支和层间隐状态。

8. 设计动机 FAQ

Q1：为什么 SWA 和尾部要「另立门户」，不一起分页？

因为它们不是「前缀的函数」。分页 cache 的价值在于页内容不可变、可跨请求共享、可精确寻址；而窗口态随每个新 token 滚动改写、尾部态攒满即清空。把它们当成 SSM 状态放进固定块，管理复杂度从「页表 + 多种淘汰策略」降为「租借 + 归还」，还顺带保住了共享前缀的块级复用——共享的本来就是不可变的前缀压缩条目。

Q2：块长为什么取 lcm(m, m') 而不是 max 或分别分块？

取 lcm 让 CSA（m=4）与 HCA（m'=128）的压缩窗口边界在同一 token 区间上同时对齐，一块之内的两类条目都是完整的：32 条 CSA 对应的 128 个 token，恰好也是那 1 条 HCA entry 覆盖的 128 个 token。这样块成为自洽的复用与调度单元；又因为块长可以是 lcm 的任意倍数（256 → 64+2），kernel 侧仍保留了「每块 token 数可变」的自由度。

Q3：Indexer 条目也要缓存吗？会不会很贵？

要。DSA 的稀疏选择发生在压缩 entry 上，Indexer 的打分对象是压缩 indexer keys，解码每个新 token 都要用它们重新算 index score，所以 \(K^{\mathrm{I}}_{\mathrm{Comp}}\) 必须逐层缓存。但它维度小（\(c_I=128\)）且同样按 1/4 压缩，摊销约 32 B/token（推断），只相当于 Main 条目的零头。§4 对「它是什么、怎么算、怎么用」有逐步展开。

Q4：命中前缀为什么还要重算尾块？

盘上只存了压缩条目。前缀的最后一个压缩块可能没攒满（< 128 token），这些 token 的未压缩条目从未落盘——重算它们既是为了补齐这截尾部，也是 Zero 策略里重建 SWA 态的原料。

Q5：这套布局省在哪？一句话版本。

时间维上压（4:1、128:1）、头维上精简（MQA 单 KV 头）、精度上混存（FP8+BF16）、位置态上封顶（SWA/尾部 O(1)）——四项相乘，1M 上下文的 KV cache 从几十 GB 压到个位数 GB。
