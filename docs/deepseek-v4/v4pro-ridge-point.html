逐算子看 DeepSeek-V4-Pro 的算术强度：prefill 与 decode 的 roofline 账本

分析对象：DeepSeek-V4-Pro（arXiv:2606.19348 §4.2.1 p.24–25，与官方 config.json 逐项核对，commit b5968e9）
复算脚本：scripts/ridge_point_v4pro.py（逐算子推导见附录 A，脚本全文见附录 B，Python 3 标准库即可运行）
关联报告：LLM 架构演进技术报告（§4 定量账本、§6 训推硬件分野、§9 专题）、V4 注意力、V4 KV cache、DSpark
生成日期：2026-10-08

一句话：把 V4-Pro 拆成 6 类算子核、分别算 \( \mathrm{AI}=\text{FLOPs}/\text{Bytes} \)，对照硬件 ridge point：在 H800（FP8 ridge ≈ 591）上，decode 全线带宽受限（AI 4.7~455），prefill 全线计算受限（AI 849~58254）。decode 每步搬运的 1.44 TB 字节里 97.4% 是路由专家权重流，曾被当作头号敌人的 KV cache 只占 0.6%。

三个推论：① DSpark 把每步有效 token 从 150 抬到 750，本质是把 decode 的 GEMM 类核 AI 抬过 ridge——投影/共享专家/LM head 三个核翻转成计算受限（251→755、279→1093、287→1229），但注意力核 AI 与 batch 无关、路由专家要 21458 token/步才翻转，所以「验证预算调度」只能部分治愈带宽病；② 硬件 ridge 点右移（591→1125→2273）比算子 AI 的自然演化快——在 Rubin FP4 上 decode 陷得更深，连 prefill 的 MoE（849）与投影（1485）也够不着 ridge；③ 序列维压缩（CSA）改的是 bytes 不是 AI——它把 KV 踢出带宽主舞台，但带宽戏的主角换成了专家权重。

一、口径：AI、ridge point 与硬件档位

Roofline 模型只问一件事：一个核每从 HBM 搬 1 字节，能配套做多少次浮点运算。定义算术强度：

\[ \mathrm{AI}=\frac{\text{FLOPs}}{\text{HBM Bytes}},\qquad \text{ridge point}=\frac{\text{峰值算力（FLOP/s）}}{\text{峰值带宽（Byte/s）}} \tag{式 1}\]

AI 高于 ridge point → 计算受限（算力打满、带宽富余）；低于 → 带宽受限（带宽打满、算力空转）。ridge point 是二者的分界，只由硬件决定。

精度口径（全文统一，敏感处单独注明）：

  • 权重 FP8（1 B/参数）、激活 BF16（2 B/元素）——沿用 V3.2 以来的 UE8M0/FP8 推理路线；GEMM 与注意力 FLOPs 都按 FP8 峰值口径判定。
  • KV 条目：主 entry 576 B（448 维 FP8 + 64 维 RoPE BF16），索引 entry 128 B（全 FP8，官方未明示精度，属推断口径）。
  • 一阶账本：不计 softmax/top-k/路由/通信开销与 kernel 实际效率（MFU）。AI 是结构上限口径——实际系统只会更带宽受限。

三、Prefill：全线计算受限，且离 ridge 很远

典型场景：单请求输入 L=32,768 token（agent 编码负载的中位输入是 142K，只会更饱和）。prefill 的 GEMM 一次看到全部 32K 个 token，权重只读一次、摊到每个 token 头上几乎为零：

\[ \mathrm{AI}_{\text{GEMM}}(B)=\frac{2B\,d_{\text{in}}d_{\text{out}}}{d_{\text{in}}d_{\text{out}}\,w_b+B(d_{\text{in}}+d_{\text{out}})\,a_b} \ \xrightarrow{\ B\to\infty\ }\ \frac{2}{a_b\!\left(\frac{1}{d_{\text{in}}}+\frac{1}{d_{\text{out}}}\right)} \tag{式 2}\]

B 为该 GEMM 一次处理的 token 数，\(w_b\)/\(a_b\) 为权重/激活字节数。注意渐近上限只由维度和激活精度决定——与权重量化无关，因为大 batch 下激活流量反超权重流量。

三个值得停一下的细节：

  • MoE 是 prefill 里最「瘦」的核：每专家摊 512 个 token，理想公式 AI ≈ 2×512 = 1024（FP8 权重），计入激活流量后 849（表 3）——仍高于 H800/B200 的 ridge，但在 Rubin FP4 的 2273 面前不够看。「prefill = 计算受限」的旧等式在 FP4 世代开始松动——除非激活也走 FP4（NVFP4 训练栈的 RHT/2D 量化正是为此铺路）。
  • 投影 GEMM 的渐近上限只有 ≈1520（式 2，d=7168、BF16 激活），L=32K 时已到 1485、接近封顶。它的 prefill bytes 由激活主导（14.1 GB 激活 vs 0.33 GB 权重）——换 FP4 权重几乎不帮忙，降激活精度才有效。
  • indexer 不改变 prefill 的计算受限属性：打分虽是 O(L²) FLOPs，但 flash 分块下索引条目也被 tile 摊销，AI 仍达 1.6 万量级。

4.1 DSpark 在 roofline 上做了什么

把表 4 的两列并排看，DSpark（τ=1 → 5）的作用一目了然：它不改变任何核的算法，只把每步有效 token 数 ×5。效果按核分三类：

  • 翻转组：投影 GEMM（251→755）、共享专家（279→1093）、LM head（287→1229）越过 H800 的 ridge 591，从带宽受限变成计算受限——「反正带宽闲着，把算力也用上」。
  • 不动组：两个注意力核的 AI 与 batch 无关（每请求读自己的 KV），255/455 纹丝不动。DSpark 的置信度调度不碰它们，也碰不到。
  • 追不上组：路由专家 4.7→23.3，离 591 还差 25×——翻转需要每步 21458 个有效 token（B·τ），在可见的部署规模内不可能。decode 的第一带宽大头注定流过。

这正是「把验证预算变成调度对象」的 roofline 本质：在带宽受限的 decode 里，多验证的 FLOPs 近乎免费，而摊薄权重流是纯赚。DSpark 论文报告的同吞吐单用户提速 57%~85%，在账本上对应 9.6 → 2.1 GB/token 的带宽效率差（图 1）。

六、与主线的呼应

  • 对 §2.3（MLA → CSA/HCA）：序列维压缩改变的是 decode 的字节构成而不是任何核的 AI——V4-Pro 把 KV 压到 V3.2 的 10%，KV 在每步带宽里的占比从主角跌到 0.6% 的配角。但带宽总账省下的部分立刻被专家权重流（97.4%）接管：注意力上省带宽、MoE 上花带宽，是同一枚硬币的两面。
  • 对 §3.7 与 §9.5（MTP 耦合与 DSpark）：DSpark 的置信度调度在 roofline 上的位置很清楚——它把「免费的多余 FLOPs」变成「摊薄 1.40 TB 专家权重流的分母」，翻转了三个 GEMM 类核，但追不上路由专家（差 25×）也动不了注意力核。调度能优化带宽的用法，改不了带宽是瓶颈这个事实。
  • 对 §9.4（硬件推理专用化）：ridge point 从 H800 的 591 移到 Rubin FP4 的 2273，本质是「每字节算力」的通胀——decode 各核相对更深的陷入带宽侧（连 DSpark 翻转的三个核在 Rubin 上也跌回去），而 prefill 的 MoE 与投影也开始够不着 ridge。这给「推理专用硅」两条路线同时供了弹药：带宽优先的大 HBM 池（服务 decode），与算力/带宽比适中的 prefill 专用硅。
  • 对 §9.3（PD 解耦）：prefill 全线计算受限、decode 全线带宽受限——两阶段不仅负载形状不同，在 roofline 上根本住在两个世界。分池部署不是工程偏好，是算术必然。
  • 对 EPLB / 大 EP：命中模型下 B=150 时 348/384 个专家被命中、每个只摊 2.3 个 token——负载均衡的意义不只是「不空转专家」，更是减少整份白读的权重。专家粒度越细（V4 的 3072 vs V3 的 2048），这个矛盾越尖锐。
本账本的边界：① 一阶口径——不含 all-to-all 通信、softmax/top-k、路由与 kernel 实际效率，实际 decode 的有效 AI 更低；② 均匀路由假设（EPLB 均衡后近似成立，热点专家更差）；③ prefill 注意力按 tile=128 摊销、causal 平均 s/8 的简化；④ 注意力核的 bound 判定依赖精度口径（FP8 vs BF16 翻转，见 §4 推断框）；⑤ H800 是 DeepSeek 公开披露过的部署档位（V3 系），V4 实际部署硬件未披露——但 ridge 点的结论对档位不敏感（B200 FP8 的 563 与 591 几乎重合）。

A.0 记号与通用约定

  • \(\mathrm{AI}=\text{FLOPs}/\text{HBM Bytes}\)（式 1）。矩阵乘 \([m{\times}k]\cdot[k{\times}n]\) 记 \(2mnk\) FLOPs（乘、加各计一次）。
  • 字节口径：权重 FP8（\(w_b{=}1\) B/参数）、激活 BF16（\(a_b{=}2\) B/元素）；KV 主条目 576 B、索引条目 128 B（§1）。
  • decode：每步权重与 KV 整份读一次，无跨请求复用；prefill：权重读一次摊给全部 token，KV 条目按 flash tile（128 query）摊销。
  • 61 层同构：投影与 MoE 的 AI 按单层计即可——分子分母同乘 61，比值不变。LM head 全局仅一个；prefill 按全部 L 个 token 计（账本口径，推理实现通常只算最后位置）。

A.1 投影 GEMM 组：8 个矩阵 → 251 / 755 / 1485

一个权重 GEMM 处理 b 个 token：读激活 \(X\,[b{\times}d_{in}]\)、权重 \(W\,[d_{in}{\times}d_{out}]\)，写输出 \(Y\,[b{\times}d_{out}]\)：

\[ F = 2b\,d_{in}d_{out}\,,\qquad \text{Bytes} = \underbrace{d_{in}d_{out}\,w_b}_{\text{权重，读一次}} + \underbrace{b\,(d_{in}{+}d_{out})\,a_b}_{\text{读 }X\text{ + 写 }Y} \tag{A-1}\]

wo_a 是 16 个独立的 4096→1024 块对角矩阵（输出分组 \(g{=}16\)），不是稠密 65536→16384——按稠密记会多算 16× FLOPs（2.15 G vs 134.2 M），decode 投影 AI 会虚高 4 倍。

记 \(P=326.70\) M（参数/层）、\(F=653.39\) M（FLOPs/token/层）、\(T=429{,}952\) B（激活/token/层），则 \(\mathrm{AI}(b)=bF/(Pw_b+bT)\)。三个工作点：

  • decode MTP-1（b = B·τ = 150）：F = 150×653.39M = 98.01 GFLOP；bytes = 0.327 GB 权重 + 150×429,952 = 64.5 MB 激活 → AI = 98.01G / 0.391G = 250.5 → 表 4 的 251。
  • decode DSpark（b = 750）：F = 490.05 G，激活 322.5 MB → AI = 490.05G / 0.649G = 754.9 → 755，越过 H800 ridge。
  • prefill（b = 32,768）：F = 21.41 TFLOP，bytes = 14.09 GB 激活 + 0.33 GB 权重 → AI = 21.41T / 14.42G = 1485。

渐近上限即式 2 的数值：\(F/T = 653.39\text{M}/429{,}952 = \mathbf{1520}\)。prefill 32K 已达封顶值的 98%——权重项只剩 2.3%，再怎么量化权重都无济于事，与 §3「激活主导」的观察互为印证。

翻转点闭式解：令 \(\mathrm{AI}(b^*)=r\)，移项得

\[ b^*(F-rT) = rPw_b \;\;\Rightarrow\;\; b^* = \frac{r\,P\,w_b}{F-r\,T} \tag{A-2}\]

有解条件是渐近值 \(F/T > r\)。H800 FP8 的精确 ridge = 1979/3.35 = 590.7（正文取整 591）：\(b^* = 590.7{\times}326.70\text{M}\,/\,(653.39\text{M} - 590.7{\times}429{,}952) = \mathbf{483}\)，与脚本二分结果一致。Rubin FP4 的 2273 > 1520，分母为负——无翻转点：任何 batch 下投影 GEMM 在 Rubin 上都是带宽受限（脚本输出 >1e7 即此意）。

A.2 decode 注意力：455 与 255 从哪来

decode 每步每个请求只有 1 个 query token（MTP-1 口径；DSpark 只是把 1 个变成 τ 个并列 draft，账目相同），注意力核的任务是：读若干条 KV 条目、逐条算一遍。推导分四步——先算一条条目的 FLOPs，再让条目数消掉得到结构值 455，然后分别代入 HCA 与 CSA 的条目清单。

第 1 步：一条 KV 条目花多少 FLOPs？关键前提是 MQA/MLA 式共享——全部 128 个查询头共用同一条 576 B 的条目（这条条目是该 token 的共享 KV 潜向量，V4 所有层的 KV cache 都按此组织）。读一条的成本因此固定为 576 B，而计算量随头数线性增长：

  • \(QK^\top\)：每个头拿自己的 512 维 q 向量与条目中 512 维的 k 做点积 = 512 次乘 + 512 次加 = 1,024 FLOPs；128 个头各做各的（k 是同一条）→ 128×1,024 = 2·n_h·c = 131,072 FLOPs。
  • \(AV\)：每个头把算出的注意力权重（标量）乘到 512 维的 v 上并累加 = 又是 1,024 FLOPs；×128 头 → 再 131,072 FLOPs。
\[ F_{\text{entry}} = 2c\,n_h + 2c\,n_h = 4\,n_h c = 4{\times}128{\times}512 = 262{,}144\ \text{FLOPs/条目} \tag{A-3}\]

indexer 打分是「减配版」：只有 \(QK^\top\) 型点积、没有 \(AV\)，且头更小（64 头 × 128 维），\(2\,n_{ih}c_i = 2{\times}64{\times}128 = 16{,}384\) FLOPs/条目。

第 2 步：条目数 e 在分子分母同时出现，消掉。读 e 条主条目：F = 262,144·e，bytes = 576·e，于是

\[ \mathrm{AI}_{\text{attn}} = \frac{4\,n_hc\cdot e}{576\cdot e} = \frac{262{,}144}{576} = \mathbf{455.1} \tag{A-4}\]

e 消掉后 AI 与「读多少条」无关；B 个请求各自读各自的条目，F 与 bytes 同乘 B，也不影响。只要读的全是主条目，AI 恒为 455.1——拿 HCA decode 验证（它没有 indexer，每步把 s/128 条压缩条目 + 128 条滑窗条目全部读一遍）：

s条目 e = s/128 + 128F = 262,144 × ebytes = 576 × eAI
8K64 + 128 = 19250.3 M110.6 KB455.1
32K256 + 128 = 384100.7 M221 KB455.1
1M8,192 + 128 = 8,3202.18 G4.79 MB455.1

三行 AI 完全相同——这就是正文式 3 第二行「注意力 AI 与 B、τ、s 无关」的全部内容，也是 DSpark 碰不到注意力核的数学原因。顺带看清 MQA 的分量：若 128 头各持一份 KV（bytes ×128），AI 会从 455 跌到 4c/576 ≈ 3.6——注意力的高 AI 是「共享 KV」买来的。

第 3 步：CSA 是两条流的串联，先分开算。CSA（m=4）+ indexer 把读取拆成单价完全不同的两段：

流条目数每条 FLOPs每条字节Fbytes单独 AI
indexer 打分（全扫压缩条目）s/4 = 8,19216,384128 B134.2 M1.049 MB16,384/128 = 128
主注意力（top-k 1024 + 滑窗 128）1,152262,144576 B302.0 M0.664 MB262,144/576 = 455.1

为什么主流只读 1,152 条：indexer 已经在便宜的压缩域（128 B/条）把「读哪些」筛好——从 8,192 条压缩条目里选出 top-k 1,024 条，主流对选中的条目 + 滑窗做注意力，不看其余。便宜流干粗活、昂贵流干精活的分工就是 CSA 的账目结构。

第 4 步：合并 = 按字节占比加权平均。两条流在同一核内串联，FLOPs 相加、bytes 相加。由于每条流各自的 AI 是常数，合并值恰好是两个 AI 的字节加权平均：

\[ \mathrm{AI}_{\text{CSA}} = \frac{F_{\text{idx}}+F_{\text{main}}}{B_{\text{idx}}+B_{\text{main}}} = \frac{128\,B_{\text{idx}} + 455.1\,B_{\text{main}}}{B_{\text{idx}}+B_{\text{main}}} = \frac{134.2\text{M} + 302.0\text{M}}{1.049 + 0.664\ \text{MB}} = \mathbf{254.7} \tag{A-5}\]

直觉版：indexer 流占 61.2% 的字节、主流占 38.8%，\(0.612{\times}128 + 0.388{\times}455 \approx 255\)——谁的字节多，谁的 AI 说了算。255 离 128 比离 455 近，原因即此。

s 决定占比，从而决定 AI：indexer 字节 (s/4)×128 随 s 线性涨，主流字节固定在 1,152×576。s 越长，字节权重越偏向 indexer，AI 从 455 单调滑向 128：

se_idx = s/4indexer 字节占比AI_CSA
4K1,02416.5%401
32K8,19261.2%255
128K32,76886.3%173
1M262,14498.1%134

这就是「区间 [128, 455]」的具体形状：s→0 时只剩滑窗（AI→455），s→∞ 时 indexer 流主导（AI→128），s=32K 落在 255。注意 CSA 压缩改变的是总字节量（主流从 s 条压到固定 1,152 条）和两条流的配比，但任何一条流自身的 AI 都没变——「压缩 ≠ 提高注意力 AI」。

A.3 prefill 注意力：×128 的 tile 摊销

prefill 的注意力核与 decode 跑的是同一种计算，账目上只变一件事：字节的记账单位从「每 query」变成「每 tile」。flash 注意力把 L 个 query 按 128 个一组（tile）处理：一条 KV 条目从 HBM 读进片上 SRAM 后，tile 里 128 个 query 复用同一份——576 B 只记一次账，FLOPs 却仍按「每 query 每条目全价」算。

第 1 步：一个 tile 的账，e 第三次消掉。设某 tile 覆盖 e 条主条目：

\[ \mathrm{AI}_{\text{tile}} = \frac{128\ \text{query}\times 262{,}144 \times e}{576 \times e} = 128\times\frac{4n_hc}{576} = 128{\times}455.1 = \mathbf{58{,}254} \tag{A-6}\]

e 又一次同时出现在分子分母并消掉——prefill 的注意力 AI = tile 大小 × decode 结构值。同一条目在两种记账口径下的对照：

记账口径一条条目的 F一条条目的 bytesAI
decode（1 query 独享）262,144576 B455.1
prefill（128 query 复用）128×262,144 = 33.6 M576 B（不变）58,254

第 2 步：HCA 全序列核对。位置 p 的 query 能看到 p/128 条压缩条目，对 p∈[0,s] 取平均得 s/256；再加固定的 128 条滑窗，\(e_{avg} = s/256 + 128\)。s=32K 时 e_avg = 256：

  • F = 32,768 query × 262,144 × 256 条 = 2.199 TFLOP；
  • bytes = (32,768/128) tile × 256 × 576 B = 37.7 MB；
  • AI = 2.199T / 37.7M = 58,254——与 A-6 完全一致（e_avg 在分子分母消掉，代入平均值即可）。

第 3 步：CSA = 两条流各自 ×128，再加权。decode 里的两条流（A.2 第 3 步）在 prefill 下逐流成账：

  • indexer 流：每 query 对当时可见的压缩条目打分，causal 平均 s/8 = 4,096 条；tile 内 128 个 query 的打分对象完全相同 → 条目读一次、128 query 全额复用，无利用率损失。AI = 128×(16,384/128) = 16,384；全序列 F = 32,768×16,384×4,096 = 2.20 T，bytes = 256 tile×524 KB = 134 MB。
  • 主注意力流：F 侧每 query 仍只对自己的 top-k+滑窗 1,152 条做全价计算；但 bytes 侧 tile 读入的是 128 个 query 选择的并集——相邻 query 的选择高度重叠，一阶近似取并集 ≈ s/8 = 4,096 条。于是利用率 = 1,152/4,096 = 28%（每条读入的条目平均只被 36 个 query 用到）：AI = 128×455.1×0.281 = 16,384；全序列 F = 32,768×302.0M = 9.90 T，bytes = 256×2.36 MB = 604 MB。
  • 合并：两流的 tile-AI 恰好都是 16,384，按字节加权（主 82%、indexer 18%）后仍是 16,384。全序列 F = 12.10 T、bytes = 738 MB → AI = 16,384，即表 3 的数。

两处近似要交代：① 主流「并集 ≈ s/8」是本账本最粗的一步（局限 ③）——它要求 s/8 ≳ 单 query 的 1,152 条（s ≳ 9K）才有意义；② indexer 的 s/8 是 causal 平均，实际逐 tile 波动。二者只影响分母的常数倍，不动「计算受限」的结论。

核decode AIprefill AI倍数机制
HCA 注意力45558,254×128条目读一次、128 query 全额复用
CSA 注意力25516,384×64同上，但 indexer 全扫 + top-k 利用率损耗

即便 Rubin 的 ridge 右移到 2,273，两个 prefill 注意力核仍高出它 7~26 倍——注意力在 prefill 阶段「永远计算受限」，与表 3 一致。

A.4 MoE：2b_e、命中模型与 21,458

第 1 步：路由记账。每 token 选 K=6 个专家，b 个 token 产生 6b 个「token→专家」指派；均匀路由（EPLB 均衡后）摊到每个专家头上：

\[ b_e = \frac{b\,K}{N} = \frac{b}{64}\ \text{token/专家} \tag{A-7}\]

三个工作点：b=150 → b_e = 2.34；b=750 → 11.7；prefill b=32,768 → 512。这个数字是 MoE 一切特性的根源。

第 2 步：FLOPs——每 expert·token 三个 GEMM。专家 FFN = gate（D→I）+ up（D→I）+ down（I→D），每个 2DI FLOPs，合计 \(6DI = 132.12\) M/expert·token；全 MoE \(F = b\,K\,6DI\)。@150：118.9 GFLOP；@750：594.5 G；prefill：25.98 T。

第 3 步：权重字节——MoE 与稠密 GEMM 的分水岭。稠密 GEMM 的权重服务于全部 b 个 token，摊薄后 AI 随 b 线性涨；专家的权重是「只要有一个 token 路由到它，66.06 MB 就整份过一遍线」——摊到 2 个 token 和摊到 200 个 token，字节一样。全命中口径（保守）：

\[ W = N\cdot 3DI = 384{\times}66.06\text{M} = 25.37\ \text{GB} \]

把第 1、3 步合成一个专家的时间线（b=150，H800）：66.06 MB 过线要 66.06M/3.35TB/s = 19.7 µs，而它挣的 FLOPs（2.34×132.12M = 309 M）只需 0.16 µs——算力利用率 0.8%，正是「AI 4.7 vs ridge 591」的时间域说法。

共享专家对照：同样 66.06 MB 权重，却服务全部 b 个 token（相当于 b_e = b）。理想 AI = 2b = 300 @150，是路由专家（2b_e = 4.69）的 N/K = 64 倍——同一数学结构，只差「摊到几个 token」。

第 4 步：命中模型——全读口径差多少？均匀路由下每个指派落到特定专家的概率 K/N = 1/64；b 个指派里专家至少被命中一次的概率 \(1-(1-1/64)^b\)，期望命中专家数：

\[ \mathbb{E}[\text{hit}] = N\left(1-\left(1-\tfrac{K}{N}\right)^{b}\right) = 384\left(1-\left(\tfrac{63}{64}\right)^{b}\right) \tag{A-8}\]

@b=150：\((63/64)^{150} = e^{150\ln(63/64)} = e^{-2.36} = 0.094\)，命中 384×0.906 = 348 个——权重流量比全读口径低 9%（22.99 vs 25.37 GB），脚本取全读是保守上界。@750：\(e^{-11.8}\approx 0\)，384.0/384 全命中，两口径重合。

第 5 步：激活字节。每 token·命中：读隐状态 h（D 元素 × 2 B）+ 写 gate/up 输出（2I 元素 × 2 B）= \(2(D+2I) = 26{,}624\) B（一阶口径，down 侧读写并入常数）；总量 \(bK\times 26{,}624\)：@150 = 24.0 MB、@750 = 119.8 MB、prefill = 5.23 GB。

A.5 共享专家与 LM head：单 GEMM 工作例与统一公式

这两个核都是 A-1 的裸 GEMM，推导只剩「代数字」；真正值得注意的是它们与投影组共享一个统一公式（本节末）。

共享专家 = 一个永被激活的专家：3·D·I = 66.06 M 参数，F = 2·D·3I = 132.12 M/token，激活 2(D+3I) = 32,768 B/token：

  • @150：F = 19.82 G，bytes = 66.06 MB 权重 + 150×32,768 = 4.92 MB 激活 → AI = 19.82G / 70.98M = 279.2。
  • @750：F = 99.09 G，激活 24.6 MB → AI = 1093.3。
  • 渐近 F/T = 132.12M/32,768 = 4,032；翻转 \(b^* = 590.7{\times}66.06\text{M}\,/\,(132.12\text{M}-19.36\text{M}) = \mathbf{346}\)。

LM head：D×V = 7168×129,280 = 926.6 M 参数，F = 2·D·V = 1.853 G/token，激活 = 读 h（2D）+ 写 logits（2V）= 272,896 B/token：

  • @150：F = 278.0 G，bytes = 926.6 MB 权重 + 40.9 MB 激活 → AI = 287.3。
  • @750：F = 1390.0 G，激活 204.7 MB → AI = 1228.6。
  • 渐近 = 1.853G / 272,896 = 6,791；翻转 \(b^* = \mathbf{324}\)。

统一公式：三个 GEMM 类核（投影组、共享专家、LM head）都有 F = 2P——GEMM 的 FLOPs/token 恒为参数量的 2 倍（A-1 与 A.1 表格可逐行验证，wo_a 的分组结构也不例外）。代入 A-1 并除以 P：

\[ \mathrm{AI}(b) = \frac{2bP}{P+bT} = \frac{2b}{1+b\,T/P}\,,\qquad b^* = \frac{r}{2-r\,T/P}\,,\qquad \text{渐近} = \frac{2P}{T} \tag{A-9}\]

        ("compressor", 4*D*C, 2*D*4*C, 2*(D+4*C)),
        ("wo_a", G*(N_H*C//G)*D_G, G*2*(N_H*C//G)*D_G, 2*(N_H*C+G*D_G)),
        ("wo_b", G*D_G*D, 2*G*D_G*D, 2*(G*D_G+D)),
        ("idx_q_b", D_C*N_IH*C_I, 2*D_C*N_IH*C_I, 2*(D_C+N_IH*C_I)),
        ("idx_w", D*N_IH, 2*D*N_IH, 2*(D+N_IH)),
        ("router", D*N_EXP, 2*D*N_EXP, 2*(D+N_EXP))]
P_PROJ = sum(p for _, p, _, _ in PROJ)
F_PROJ = sum(f for _, _, f, _ in PROJ)
T_PROJ = sum(a for _, _, _, a in PROJ)
P_SHARED = P_EXPERT = 3 * D * I_EXP
P_LMHEAD = D * V

total  = LAYERS*(P_PROJ + P_SHARED + N_EXP*P_EXPERT) + P_LMHEAD   # 1.572T ~ 1.6T
active = LAYERS*(P_PROJ + P_SHARED + K_TOP*P_EXPERT) + P_LMHEAD   # 49.06B ~ 49B

def proj_ai(b): return b*F_PROJ / (P_PROJ*W_B + b*T_PROJ)
def gemm_ai(b, d_in, d_out, w_b=W_B, a_b=A_B):
    return 2*b*d_in*d_out / (d_in*d_out*w_b + b*(d_in+d_out)*a_b)

def csa_decode_ai(s):        # indexer scores s/4 entries; main over topk+window
    e_idx, e_sel = s/4, TOPK + N_WIN
    return (2*N_IH*C_I*e_idx + 4*N_H*C*e_sel) / (e_idx*KV_IDX + e_sel*KV_MAIN)
def hca_decode_ai(s):        # dense over s/128 entries + window
    e = s/128 + N_WIN
    return 4*N_H*C*e / (e*KV_MAIN)
def csa_prefill_ai(s, tile=128):
    return s*(2*N_IH*C_I*(s/8) + 4*N_H*C*(TOPK+N_WIN)) \
         / (s/tile * (s/8) * (KV_IDX + KV_MAIN))
def hca_prefill_ai(s, tile=128):
    e_avg = s/256 + N_WIN
    return s*4*N_H*C*e_avg / (s/tile * e_avg * KV_MAIN)
def moe_ai(b, w_b=W_B):      # uniform routing, all-hit weight streaming
    return b*K_TOP*6*D*I_EXP / (N_EXP*P_EXPERT*w_b + b*K_TOP*2*(D+2*I_EXP))
