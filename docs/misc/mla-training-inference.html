一句话：MLA 用「KV 联合低秩压缩 + 解耦 RoPE」把 KV cache 从每 token 每层 \(2 n_h d_h\) 个元素压到 \((d_c + d^R_h) = 576\) 个元素（DeepSeek-V3 规格，仅为 MHA 的 1.76%，等效 GQA 2.25 组），再靠 weight absorption 把上投影矩阵 \(W_{UK}\)、\(W_{UV}\) 分别吸收进 query 侧与输出侧，使 decode 变成 K/V 同源的 MQA——缓存里永远只存 576 维 latent。

训练就是按论文公式 (37)–(47) 的朴素形式走标准线性层 + FlashAttention（head_dim 192/128 的 MHA），反向传播无特殊处理；推理 decode 走 absorbed MQA（省访存），prefill 走非吸收的 MHA 形式（省算力），vLLM/SGLang 都按这个分界调度。FlashMLA kernel 用页表 + 64×576 KV tile + 「seesaw」双 warpgroup 调度在 H800 上跑到 3000 GB/s / 660 TFLOPS。

1. 动机与谱系：KV cache 是怎么成为瓶颈的

自回归 decode 每生成一个 token，都要把全部前缀 token 的 K、V 读一遍。MHA 下每 token 每层要缓存 \(2 n_h d_h\) 个元素（K 和 V 各 \(n_h d_h\)）：DeepSeek-V3 规格下 \(n_h=128,\ d_h=128\)，即每 token 每层 32768 个元素、61 层合计约 4 MB/token。这直接封顶了 batch size 和序列长度——decode 是访存瓶颈，KV cache 就是访存的大头。这条账本的完整推导见《MHA 的 Prefill 与 Decode 账本》，可调参数的交互计算见《Attention AI 计算器》，此处不重复。

压缩 KV cache 的谱系是一条「在 K/V 头之间做共享」的路：

方法KV cache / token / 层做法代价
MHA\(2 n_h d_h\)每头独立 K/V缓存最大
MQA（2019）\(2 d_h\)所有头共享 1 组 K/V质量损失明显
GQA（2023）\(2 n_g d_h\)折中：\(n_g\) 组共享仍有损失（V2 论文附录 D.1 的 7B 消融：MMLU 45.2 vs GQA-8 41.2 vs MQA 37.9）
MLA（V2）\((d_c + d^R_h)\approx \frac{9}{2} d_h\)不做头间共享，改做 K/V 联合低秩压缩：只缓存 latent \(c^{KV}_t\)，多头 K/V 从中恢复等效 GQA 2.25 组的缓存，但 V2 论文附录 D.2 消融显示强于 MHA（250B 级 MoE：MMLU 59.0 vs MHA 57.5）

2. 结构逐矩阵拆解

2.1 完整前向公式（V2 论文附录 C，式 37–47）

MLA 的所有细节都在这 11 条式子里。记号沿用论文：\(d\) 为 hidden size，\(n_h\) 为头数，\(d_h\) 为每头维度（= \(d^{nope}_h\)），\(d^R_h\) 为解耦 RoPE 通道的每头维度，\(d_c\) 为 KV 压缩维度，\(d'_c\) 为 Q 压缩维度：

Q 侧（低秩压缩，为省训练 activation，不省 KV cache）：

\[ c^Q_t = W_{DQ} h_t \tag{37} \] \[ [q^C_{t,1};\dots;q^C_{t,n_h}] = q^C_t = W_{UQ}\, c^Q_t \tag{38} \] \[ [q^R_{t,1};\dots;q^R_{t,n_h}] = q^R_t = \mathrm{RoPE}(W_{QR}\, c^Q_t) \tag{39} \]

KV 侧（联合低秩压缩，K 与 V 共享同一个 latent）：

\[ c^{KV}_t = W_{DKV} h_t \tag{41} \] \[ [k^C_{t,1};\dots;k^C_{t,n_h}] = k^C_t = W_{UK}\, c^{KV}_t \tag{42} \] \[ k^R_t = \mathrm{RoPE}(W_{KR}\, h_t) \tag{43} \] \[ v^C_t = W_{UV}\, c^{KV}_t \tag{45} \]

拼接与注意力（每头 concat 位置无关部分与 RoPE 部分）：

\[ q_{t,i} = [q^C_{t,i};\, q^R_{t,i}],\qquad k_{t,i} = [k^C_{t,i};\, k^R_t] \tag{40, 44} \] \[ o_{t,i} = \sum_j \mathrm{Softmax}_j\!\left(\frac{q^T_{t,i} k_{j,i}}{\sqrt{d_h + d^R_h}}\right) v^C_{j,i} \tag{46} \] \[ u_t = W_O [o_{t,1};\dots;o_{t,n_h}] \tag{47} \]

2.3 为什么 RoPE 与低秩压缩不兼容（数学原因）

RoPE 对 q 施加位置 \(t\) 的旋转 \(R_t\)、对 k 施加位置 \(j\) 的旋转 \(R_j\)，注意力分里的相对旋转 \(R^T_t R_j = R_{j-t}\) 只依赖相对位置。本节从「absorption 想要什么形式」出发，逐条推演把 RoPE 塞进压缩通道的两种方式为何都失败，最后落到解耦设计的必然性。

2.3.1 吸收的目标形式：缓存向量左边只许有常数

decode 每步只有 1 个 query，却要扫全部缓存 token \(j\)，瓶颈是读缓存的字节数。因此希望把每步注意力整理成：

\[ s_{t,j} = \tilde q_t^{\,T}\, \hat c_j, \qquad o_t = \tilde W \Big( \sum\nolimits_j \alpha_{t,j}\, \hat c_j \Big) \]

其中 \(\hat c_j\) 是缓存向量，\(\tilde q_t\)、\(\tilde W\) 只依赖 \(t\)、每步算一次；per-\(j\) 的全部工作只是与缓存向量做点积 / 加权累加。判据由此而来：缓存向量左边只允许出现与 \(j\) 无关的常数矩阵——常数可以沿点积搬到 query 侧或输出侧，任何随 \(j\) 变化的因子都不许夹在中间。

2.3.2 内容通道为什么畅通：常数矩阵可以自由搬家

\[ s^{C}_{t,i,j} = (q^C_{t,i})^T\, W_{UK}[i]\, c^{KV}_j = \big( W_{UK}[i]^T q^C_{t,i} \big)^T c^{KV}_j \] \[ o_{t,i} = \sum\nolimits_j \alpha_{t,j}\, W_{UV}[i]\, c^{KV}_j = W_{UV}[i] \Big( \sum\nolimits_j \alpha_{t,j}\, c^{KV}_j \Big) \]

key 链路上除了常数矩阵 \(W_{UK}[i]\) 与缓存向量 \(c^{KV}_j\) 别无他物，纯用结合律即可把矩阵搬到 query 侧；\(W_{UV}[i]\) 同理搬到输出侧（还可进一步并进 \(W_O\)，见 4.2 节）。「学到的矩阵 = 常数 ⇒ 可搬运」是 absorption 成立的全部原因。RoPE 的旋转矩阵不是常数——下面两小节推演把它塞进压缩通道的两种方式。

2.3.3 变体一：先上投影、再旋转——保住相对位置就保不住 absorption

要让内容 key 带位置，合规写法是旋转作为 key 链路的最后一步：

\[ s^{C}_{t,i,j} = (R_t\, q^C_{t,i})^T \big( R_j\, W_{UK}[i]\, c^{KV}_j \big) = (q^C_{t,i})^T\, R_{j-t}\, W_{UK}[i]\, c^{KV}_j \]

数学上这是完全合法的 RoPE 注意力（只出现 \(j-t\)，相对位置性质 ✓）。但按 2.3.1 的判据做 absorption 时，\(c^{KV}_j\) 左边的前缀是 \(W_{UK}[i]^T R_{j-t}^T q^C_{t,i}\)——含 \(R_{j-t}\)、随 \(j\) 变化，每来一个 key 位置都要重算一次 \(d_h \times d_c\) 的 GEMV，代价与现场物化 \(k^C_{j,i}\) 完全相同。V2 论文 §2.1.3 对同一事实的表述是（把式子从 \(c^Q\) 侧写起，\(W_{UQ}^T\) 与 \(W_{UK}\) 之间正好落着一个旋转矩阵）：「a RoPE matrix related to the currently generating token will lie between \(W_{UQ}\) and \(W_{UK}\) and matrix multiplication does not obey a commutative law」。于是只剩两条路，各牺牲一样东西：

  • 把 \(W_{UK}[i] R_j c^{KV}_j\)（= 带 RoPE 的 \(k^C_{j,i}\)）整体缓存——那就是每 token \(n_h \times d_h\) 个元素，压缩白做；
  • decode 每步对全部前缀 token 重算上投影——每步 \(O(L)\) 个 GEMM，推理效率崩塌。

2.3.4 变体二：把 RoPE 直接做在 latent 上——缓存里不能存「旋转后的 latent」

更激进的想法：既然 \(k^C = W_{UK}\, c^{KV}\)，不如缓存时就旋转，存 \(\tilde c_j = R_j\, c^{KV}_j\)（512 维、各头共享），顺便省掉解耦通道的 64 维开销。注意这把顺序锁死了：缓存里已是旋转后的向量，上投影只能发生在旋转之后，\(k^C_{j,i} = W_{UK}[i]\, R_j\, c^{KV}_j\)。query 侧只有三种配法，逐一推演：

  1. query 不旋转：\(s = (q^C_{t,i})^T W_{UK}[i] R_j c^{KV}_j = \big( W_{UK}[i]^T q^C_{t,i} \big)^T \tilde c_j\)——计算形式恰好是「吸收后的 query × 缓存向量」的理想 MQA 形态，但 score 只依赖 \(j\)、与 \(t-j\) 无关，RoPE 退化成绝对位置编码，外推性质全丢。✗
  2. 最终 query 旋转（\(d_h\) 维的 \(\hat R_t\)，即旋转放在 query 上投影之后）：\(s = (c^Q_t)^T W_{UQ}[i]^T \hat R_t^T\, W_{UK}[i]\, R_j\, c^{KV}_j\)——两个旋转作用在不同维度的坐标系上（\(d_h=128\) 维 vs \(d_c=512\) 维），中间隔着 \(W_{UK}[i]\)，连 \(j-t\) 的形式都凑不出来。✗
  3. query 的 latent 也旋转（\(d'_c\) 维的 \(R'_t\)，再上投影）：\(s = (c^Q_t)^T R'^{T}_t \big( W_{UQ}[i]^T W_{UK}[i] \big) R_j\, c^{KV}_j\)——学到的矩阵 \(W_{UQ}[i]^T W_{UK}[i]\) 又夹回两个旋转中间，回到变体一的困境。✗

症结在于：旋转发生在缓存时刻 ⇒ 上投影必然在旋转之后 ⇒ 「相对位置性质」与「缓存向量左边只有常数」不可兼得。反过来，唯一保相对性质的顺序（先投影、后旋转）又把旋转逼进 kernel 内部——那正是变体一，同样堵死 absorption。两条路合起来给出一个干净的结论：位置信息不能流经压缩通道。

变体二的三种 query 侧配法与「两条路合起来」的论证是本文的展开，论文未逐一讨论；结论与论文一致（位置不可流经压缩通道）。

2.3.5 解耦 RoPE：位置信息走一条「无矩阵」旁路

从上面的失败里提炼两条硬约束：① 缓存通道要能 absorption ⇒ \(c^{KV}\) 左边只能有常数矩阵，内容通道不许出现 \(R_j\)；② RoPE 要保相对性质 ⇒ \(R_t\) 与 \(R_j\) 之间不许有任何矩阵，旋转必须是 q、k 各自链路的最后一步。内容通道的最后一步必须留给常数矩阵 \(W_{UK}\)（否则吸收不了），它注定当不了位置载体——所以位置只能单独开一对向量，各自用小投影、最后一步旋转：\(q^R_{t,i}\in\mathbb{R}^{d^R_h}\)（每头一份）与 \(k^R_t\in\mathbb{R}^{d^R_h}\)（所有头共享一份，天然就是 MQA 形态）专司 RoPE，且 \(k^R_t = \mathrm{RoPE}(W_{KR}\, h_t)\) 直接从原始 \(h_t\) 取、绕过压缩通道。完整注意力分拆成两项，各自都满足 2.3.1 的目标形式：

\[ s_{t,i,j} = \big( W_{UK}[i]^T q^C_{t,i} \big)^T c^{KV}_j \;+\; \big( R_t^T q^R_{t,i} \big)^T k^R_j \]

第一项：常数矩阵已全部吸收，与 512 维 latent 做点积；第二项：两个旋转之间无任何矩阵，相对位置性质成立，\(k^R_j\) 旋转后可直接缓存（kernel 内连旋转都省了，只对 \(q^R\) 做一次 \(R_t^T\)）。缓存 = \(c^{KV}(512) + k^R(64) = 576\) 维，softmax 内积维度从 \(d_h\) 变 \(d_h + d^R_h\)（式 46 的 \(\sqrt{d_h+d^R_h}\) 缩放）。64 维（+12.5%）就是「位置绝不流经压缩通道」这条约束的定价。

一句话判据：在 \(q^T(\cdot)k\) 的双线性形式里，常数矩阵可以搬到任何一边（absorption 没问题）；旋转矩阵只有当它是两条链路各自的最后一步、且中间无矩阵时才合法。压缩通道的末步必须留给常数矩阵 \(W_{UK}\)，所以旋转只能自带旁路——解耦 RoPE（式 39、43）是必然设计，而非可选项。

「\(R_t\) 与 \(W_{UK}^T\) 不可交换」的具体论证（对偶旋转矩阵与稠密矩阵乘法交换的失败）是本文的展开，论文原文只给了「矩阵乘法不满足交换律」这一句结论性陈述；结论一致。

3. 训练侧：朴素形式怎么算

3.1 前向完整流程

训练时 MLA 就是式 (37)–(47) 的朴素实现：先按 head 切出 \(q_{t,i}, k_{t,i}, v^C_{t,i}\)（每头 \(128+64=192\) 维 QK、128 维 V），然后跑一个标准的因果 MHA——head_dim 192/128 的形状可直接用 FlashAttention。下面是可跑的参考实现（float32、缩比维度；完整脚本第 5 节有真实数值验证）：

import torch
# 训练形式（论文式 37–47 的朴素实现）
def mla_forward_train(h, pos, W):            # h: [B, T, d]
    c_Q  = h @ W['DQ']                                     # 式37  [B,T,d'_c]
    q_C  = (c_Q @ W['UQ']).view(B, T, n_h, d_h)            # 式38
    q_R  = rope((c_Q @ W['QR']).view(B, T, n_h, d_Rh), pos) # 式39
    c_KV = h @ W['DKV']                                    # 式41  [B,T,d_c]
    k_C  = (c_KV @ W['UK']).view(B, T, n_h, d_h)           # 式42
    k_R  = rope(h @ W['KR'], pos)                          # 式43  [B,T,d_Rh]，所有头共享
    v_C  = (c_KV @ W['UV']).view(B, T, n_h, d_v)           # 式45
    q = torch.cat([q_C, q_R], -1)                          # 式40  [B,T,n_h,d_h+d_Rh]
    k = torch.cat([k_C, k_R[:, :, None].expand(-1,-1,n_h,-1)], -1)  # 式44
    s = torch.einsum('bqhd,bkhd->bhqk', q, k) / (d_h + d_Rh) ** 0.5   # 式46
    p = s.masked_fill(~causal_mask, float('-inf')).softmax(-1)
    o = torch.einsum('bhqk,bkhd->bqhd', p, v_C)            # 式46
    return (o.reshape(B, T, n_h * d_v) @ W['O'])           # 式47

代码 1｜训练形式参考实现。与第 5 节验证脚本同构（脚本已验证与 absorbed 形式数值等价，相对误差 4.9e-7）。

生产实现里，\(\mathrm{RoPE}\) 用高效的 interleaved/half 实现（V3 config 的 YaRN 缩放 factor=40, original_max_position_embeddings=4096），\(q,k\) concat 后喂给支持 head_dim 192/128 的 attention kernel；V3 全程用 FP8 混合精度训练（V3 论文 §3.3），MLA 的各投影都是普通 GEMM，照常量化。

3.2 反向传播

没有特殊处理。MLA 的全部新东西（\(W_{DKV}, W_{UK}, W_{UV}, W_{KR}, W_{DQ}, W_{UQ}, W_{QR}\)）在训练前向里都是普通线性层，\(c^{KV}\) 是普通中间激活，autograd 照常求导；「absorption」是推理期的权重重参数化视角，训练里根本不发生。唯一值得注意的是压缩让反向的多头 attention 不再是最大的 activation 消耗点之一。

「反向无特殊处理」是从论文（附录 C 只给前向公式、正文无 backward 描述）与官方实现（FlashMLA 训练侧只有 dense prefill fwd/bwd 的标准 CUTLASS FMHA，见 csrc/cuda_kernels/sm100/prefill/dense/fmha_cutlass_bwd_sm100.cu，main@0f11e17）共同推出的结论，非论文明文陈述。

3.3 训练显存账：activation 与 KV

  • KV cache 不存在：训练是全序列一次前向，\(c^{KV}\) 只当一层中间激活，反向算完就丢，不做跨层缓存——MLA 的 KV cache 收益是纯推理收益。
  • Q 侧低秩压缩省 activation：论文 §2.1.2 末尾明说「in order to reduce the activation memory during training, we also perform low-rank compression for the queries」。省的量是 \(W_{UQ}\) 输入端：不压缩时该处 activation 为 \(T \times d \times n_h d_h \times 2\) 字节量级，压缩后为 \(T \times d'_c\)（1536）中间量 + 上投影输出。按式 (12)–(13) 的两段式，Q 通道的中间激活从 \(n_h d_h = 16384\) 维降到 \(d'_c = 1536\) 维，约 \(\times 10\)。
  • 代价：MLA 每层比 MHA 多出 \(W_{UK}+W_{UV}+W_{DKV}+W_{KR}\approx 21\)M 的投影 FLOPs/层/token，在 V2/V3 的 21B/37B 激活参数里占比很小。

3.4 与 MoE 主干的配合（简述）

MLA 与 DeepSeekMoE 是正交的两件事：MLA 管注意力的推理效率（KV cache 与 decode 访存），DeepSeekMoE 管 FFN 的参数效率（细粒度专家 + 共享专家隔离）。V2 摘要给出的组合收益：相对 DeepSeek 67B（MHA + 稠密 FFN），训练成本省 42.5%、KV cache 减 93.3%、最大生成吞吐 5.76×（V2 论文 §1）。MoE 细节见MoE 零基础系列。

4.2 Weight absorption 完整推导

naive 形式 decode 时，对每个新 query 都要先把全部前缀的 \(c^{KV}\) 上投影成 \(k^C, v^C\)——这部分计算与 \(n_h\) 和 \(L\) 成正比，且是纯粹的开销。利用矩阵乘法结合律可以把投影挪到另一侧，让缓存条目「存的是什么就用什么算」：

第一步：\(W_{UK}\) 吸收进 query 侧。naive 形式的 nope 打分（式 38×42）：

\[ s^C_{t,i,j} = (q^C_{t,i})^T k^C_{j,i} = \big(W_{UQ}[i]\,c^Q_t\big)^T \big(W_{UK}[i]\,c^{KV}_j\big) = \big(\underbrace{W_{UK}[i]^T\, q^C_{t,i}}_{\textstyle q^{\mathrm{lat}}_{t,i}\in\mathbb{R}^{d_c}}\big)^T c^{KV}_j \]

\(q^{\mathrm{lat}}_{t,i}\) 是 512 维的「latent 空间 query」。K 不再需要上投影：缓存里的 \(c^{KV}_j\) 直接当 K 用。注意被吸收的是 \(q^C\)（\(W_{UQ}\) 的输出）之后那段；\(W_{UQ}\) 本身留在 q_b_proj 里不显式合并（见 4.5 节源码）。

第二步：RoPE 通道天然是 MQA。\(s^R_{t,i,j} = (q^R_{t,i})^T k^R_j\) 中 \(k^R_j\) 本来就与头无关。把两路打分拼起来：

\[ s_{t,i,j} = \big[q^{\mathrm{lat}}_{t,i};\, q^R_{t,i}\big]^T \big[c^{KV}_j;\, k^R_j\big],\qquad \text{除以 } \sqrt{d_h + d^R_h} \tag{46'} \]

这就是一个 MQA：每头 576 维 query 对同一份 576 维共享 KV。

第三步：\(W_{UV}\) 吸收进输出侧。naive 的加权求和（式 45×46）：\(o_{t,i} = \sum_j p_{t,j}\, W_{UV}[i]\, c^{KV}_j\)。把求和与投影交换：

\[ o_{t,i} = W_{UV}[i]\, \underbrace{\sum_j p_{t,j}\, c^{KV}_j}_{\textstyle \hat{c}_{t,i}\in\mathbb{R}^{d_c}},\qquad u_t = W_O\big[W_{UV}[1]\hat{c}_{t,1};\dots;W_{UV}[n_h]\hat{c}_{t,n_h}\big] \]

V 也不需要上投影：缓存的 \(c^{KV}_j\) 直接当 V 用，MQA 输出是每头一个 512 维的「latent 空间加权和」\(\hat c_{t,i}\)，再经每头独立的 \(W_{UV}[i]\)（512→128）回到 \(d_v\) 维。三步之后，decode 的 attention 主体变成：

# absorbed 推理形式：KV cache 每条目 = [c_KV(512) ; k_R(64)]，全头共享
q_lat = torch.einsum('bqhd,hde->bqhe', q_C, W_UK_h)        # W_UK 吸收进 query
q_mqa = torch.cat([q_lat, q_R], -1)                        # [B,Sq,n_h,576]
k_mqa = torch.cat([c_KV, k_R], -1).expand heads            # [B,T,576] 共享
p2   = softmax(q_mqa @ k_mqa.T / sqrt(d_h+d_Rh))           # MQA attention
chat = p2 @ c_KV                                           # V=c_KV，输出 latent 和
o    = torch.einsum('bhql,hel->bqhe', chat, W_UV_h)        # W_UV 吸收进输出
u    = o.reshape(B, Sq, n_h * d_v) @ W_O

代码 2｜absorbed 形式骨架（可运行完整版见第 5 节代码 5，与代码 1 的训练形式数值等价）。

4.3 数值等价验证：训练形式 = 吸收形式

absorption 只用了矩阵乘法结合律，输出必须逐元素一致。下面是实际运行过的完整验证脚本（CPU、float32、缩比维度 \(d=256, n_h=8, d_h=32, d^R_h=16, d_c=64, d'_c=96\)；缩放因子与 RoPE 同 V3 口径）：

import torch; torch.manual_seed(0)
# 维度（缩比版 V3 口径）：d=256, n_h=8, d_h=32(P), d_Rh=16(R), d_c=64, d_cq=96, d_v=32
B, Sq = 2, 10
scale = 1.0 / ((d_h + d_Rh) ** 0.5)
# ... 权重 W_DQ/W_UQ/W_QR/W_DKV/W_UK/W_UV/W_KR/W_O 随机初始化（见附注脚本） ...

# ---------- 训练 / naive 形式（式 37-47） ----------
c_Q  = h @ W_DQ;  q_C = (c_Q @ W_UQ).view(B,Sq,n_h,d_h)
q_R  = rope((c_Q @ W_QR).view(B,Sq,n_h,d_Rh), pos)
c_KV = h @ W_DKV; k_C = (c_KV @ W_UK).view(B,Sq,n_h,d_h)
k_R  = rope(h @ W_KR, pos)                    # 全头共享
v_C  = (c_KV @ W_UV).view(B,Sq,n_h,d_v)
s = torch.einsum('bqhd,bkhd->bhqk',
        torch.cat([q_C,q_R],-1),
        torch.cat([k_C, k_R[:,:,None].expand(-1,-1,n_h,-1)],-1)) * scale
p  = s.masked_fill(~mask, float('-inf')).softmax(-1)
o  = torch.einsum('bhqk,bkhd->bqhd', p, v_C)
u_naive = o.reshape(B,Sq,n_h*d_v) @ W_O

# ---------- absorbed 推理形式 ----------
W_UK_h = W_UK.view(d_c,n_h,d_h).permute(1,2,0)     # 每头 W_UK[i]^T: (n_h,d_h,d_c)
W_UV_h = W_UV.view(d_c,n_h,d_v).permute(1,2,0)     # 每头 W_UV[i]^T: (n_h,d_v,d_c)
q_lat  = torch.einsum('bqhd,hde->bqhe', q_C, W_UK_h)          # 吸收1: W_UK 进 query
q_mqa  = torch.cat([q_lat, q_R], -1)                          # [B,Sq,n_h,d_c+d_Rh]
k_mqa  = torch.cat([c_KV[:,:,None,:].expand(-1,-1,n_h,-1),
                    k_R[:,:,None,:].expand(-1,-1,n_h,-1)],-1) # 共享 KV
p2  = torch.einsum('bqhd,bkhd->bhqk', q_mqa, k_mqa).mul(scale).masked_fill(~mask, float('-inf')).softmax(-1)
chat = torch.einsum('bhqk,bkl->bhql', p2, c_KV)               # V=c_KV（latent 空间加权和）
o_abs = torch.einsum('bhql,hel->bqhe', chat, W_UV_h)          # 吸收2: W_UV 进输出
u_abs = o_abs.reshape(B,Sq,n_h*d_v) @ W_O

diff = (u_naive - u_abs).abs().max()
print(f"max|naive-absorbed| = {diff:.3e}, rel = {(diff/u_naive.abs().max()):.3e}")
# 实测输出：max|naive-absorbed| = 2.980e-06   rel = 4.913e-07   → PASS (< 1e-4)

代码 3｜数值等价验证（本机 Python 3.9 + PyTorch 2.8.0 CPU 实跑，2026-10-19）。float32 下 1e-6 量级的差异来自 einsum 的归约顺序不同，属数值噪声；softmax 与 concat 的位置都核对过：\(q^R/k^R\) 在 absorbed 形式里不经过任何投影，直接拼接。

同一脚本顺带给出 prefill FLOPs 账：每 (head, q, k) 对的 attention 内积+加权和 FLOPs，naive 形式 \(2[(128+64)+128]=640\)，absorbed 形式 \(2[(512+64)+512]=2176\)，3.4×——这就是 prefill 不用吸收形式的原因，见下节。

4.4 为什么 decode 用 absorbed、prefill 往往不用

两种形式是「访存友好 vs 算力友好」的取舍（vLLM mla_attention.py:12-16 的文档注释原话：compute friendly for prefill（\(S_q/S_{kv}\) 接近 1），data-movement friendly for decode（\(S_q/S_{kv}\) 接近 0））：

decode（\(S_q=1\)）prefill（\(S_q\approx S_{kv}\)）
瓶颈访存：每步要把前缀 KV 从 HBM 读一遍算力：\(O(S_q S_{kv})\) 的 attention 矩阵乘是大头
absorbed 的影响KV 读取从 \(n_h(d_h+d_v)=32768\) 元素/token 降到 576/token（56.9×）；上投影 GEMM 与 \(L\) 解耦QK^T 在 576 维上做、PV 在 512 维上做，每对 FLOPs 3.4×；\(\hat c\) 的 \(W_{UV}\) 后处理从「每 token 一次」变成「每 (token, head) 一次」，乘上 \(S_q\)
结论用 absorbed：MLA 的 MQA 形态 = 免费拿到 MQA 的访存优势而无损质量不用 absorbed：先用 kv_b_proj 把 latent 上投影成标准 MHA（QK 192 维 / V 128 维），喂 FlashAttention 等高效 kernel

表 4｜两条路径的取舍。另有一个算力视角的佐证：FlashMLA 官方 deep-dive（docs/20250422-new-kernel-deep-dive.md:9-15，ba89a34）算出 absorbed decode 的 FLOPs/byte ≈ \(2 h_q s_q\)，H800 上 \(h_q s_q \ge 128\) 就进入 compute-bound 区——DeepSeek decode 部署 \(h_q=128\)（decode 实例不做 TP），恰好压线，所以 decode kernel 也要按 compute-bound 优化（见 4.5 节）。MTP/投机解码把 \(s_q\) 抬到 >1，进一步推向 compute-bound。

「prefill 用 non-absorbed 是因为 3.4× 的 FLOPs 差与 \(W_{UV}\) 后处理复杂度」中，3.4× 是本文按张量形状算的账（代码 3 尾部），论文未给此数；「\(S_q/S_{kv}\) 分界由调度器的 prefill/decode 标签决定、尚可调优」是 vLLM 文档注释（mla_attention.py:18-19）的原文陈述。

4.5 FlashMLA 的 kernel 设计要点（以仓库源码为准）

FlashMLA（deepseek-ai/FlashMLA）是 DeepSeek 官方的注意力 kernel 库，承载 V3/V3.2 的推理。其 dense MLA decode kernel（Hopper sm90，经典 MLA 形态）实现要点：

(1) 输入就是 absorbed MQA + 页表。Python 接口声明 Q 为 576 维、V 输出 512 维、KV cache 形如 (num_blocks, page_block_size, num_heads_k, head_dim) 且 num_heads_k must be 1（flash_mla/flash_mla_interface.py:73-95，快照 ba89a34）——「只有 MQA」正是吸收后的形态。内核常量钉死形状（csrc/kernels/sm90/decode/dense/config.h:5-11）：

namespace Config {
static constexpr int BLOCK_SIZE_M   = 64;    // 每 CTA 处理 64 个 q（多请求 q 打包）
static constexpr int PAGE_BLOCK_SIZE = 64;   // KV 页大小（与 PagedAttention 对齐）
static constexpr int HEAD_DIM_K = 576;       // = 512 c_KV + 64 k_RoPE
static constexpr int HEAD_DIM_V = 512;       // 输出 = latent 空间加权和
}

代码 4｜FlashMLA decode 内核的形状常量。K、V 在这里同源：前 512 维读进来既参与 QK^T（配 \(q^{lat}\)）又当 V（式 46'）——官方 deep-dive 原话「in MLA, K and V are the same with different names」。

(2) 一个 KV tile 服务所有 128 个 q 头。kernel 网格是 (num_m_blocks, h_k, num_sm_parts)，其中 \(h_k=1\)（MQA），每个 q 头只是 Q 打包维里的一行（splitkv_mla.cuh:962-967 的网格注释）。TMA 一次搬 64×576 的 KV 页（拆成 9 个 64×64 tile，见下），128 个头的 QK^T/ItPV 全部复用这一份 shared memory 数据——这是「shared KV」的硬件意义，也是 MHA kernel 做不到的。

(3) 「seesaw」调度：一份输出寄存器文件上的双 warpgroup 乒乓。64×512 的输出累加器占 32768 个 32-bit 寄存器，一个 SM 只有 65536 个，无法像 FA3 那样双缓冲两份输出做 ping-pong。FlashMLA 的解法是把输出竖切成 \(O_L/O_R\) 两个 64×256 分属两个 warpgroup，拿两个 KV 块 \(K_0,K_1\) 按固定 11 步交错：一个 warpgroup 在 Tensor Core 上算 GEMM 时，另一个在 CUDA Core 上做 online softmax 的 max/exp/缩放，同时 TM&A 搬下一块（deep-dive 文档 docs/20250422-new-kernel-deep-dive.md:19-42，称为「mathematically equivalent to FlashAttention's online softmax」的 seesaw scheduling）。源码里对应 wg0_subroutine/wg1_subroutine 的成对编排与 NamedBarrier 同步（splitkv_mla.cuh:742-945）。

(4) 细粒度 TMA 流水与 L2 提示。每块 64×576 的 K 拆成 9 个 64×64 的 TMA 拷贝，「GEMM 等一个 tile 到一个」，并给 TMA 加 EVICT_FIRST 缓存提示提升 L2 命中（deep-dive :54-55；源码 launch_kv_tiles_copy_tma，splitkv_mla.cuh:36-52）。

(5) split-KV + combine + PDL。长序列时 KV 维切给多个 SM part 各算部分（oaccum 路径，splitkv_mla.cuh:1240-1261），由独立 combine kernel 按/log-sum-exp 合并（csrc/cuda_kernels/smxx/decode/combine/combine.cu，main@0f11e17）；两个 kernel 之间用 Programmatic Dependent Launch 重叠启动（splitkv_mla.cuh:1226 的 cudaTriggerProgrammaticLaunchCompletion 与 :1340-1351 的 cudaLaunchAttributeProgrammaticStreamSerialization）。tile scheduler（get_decoding_sched_meta）负责把 (请求, 块) 均衡分配到 SM。Q tile 也按 64×576 进 shared memory（:708 的 arrive_and_expect_tx(64*576*2)）。

性能口径：dense decode kernel 在 H800 SXM5 + CUDA 12.8 上，memory-bound 配置最高 3000 GB/s、compute-bound 配置最高 660 TFLOPS（README.md:36，ba89a34）。

两框架的工程注意点总结（从源码读出）：absorbed 路径在 FP8 下要额外维护 \(W_{UK}\) 的量化 bmm（vLLM 的 fp8/aiter/amx 分支、SGLang 的 bmm_fp8），这是 MLA 相比 MHA 多出来的算子链条；投机解码/目标验证时 \(s_q>1\)，vLLM 有 reshape_query_for_spec_decode（flashmla.py:277 附近）把多 token q 打平成 MQA 的额外 q 维。

6. 事实与推断的边界

论文/官方源码证实的事实：全部公式 (37)–(47) 与 Table 1/Table 8/Table 9 数字（V2 论文）；V3 超参（官方 config.json）；缓存内容 576 维、MQA-only 接口与 576/512 形状常量（FlashMLA 接口文档与 config.h）；seesaw/TMA/PDL/tile scheduler 与 3000 GB/s、660 TFLOPS（FlashMLA README 与 deep-dive）；vLLM/SGLang 的双路径分流与 absorption 算子位置（上述源码行号）；数值等价（本文实测）。

推断（均已在上文就地标注）：① 反向传播无特殊处理（论文未述 + FlashMLA 只有标准 FMHA bwd）；② RoPE 与 \(W_{UK}^T\) 不可交换的逐条论证（论文只给结论句）；③ prefill absorbed 3.4× FLOPs 账（自算）；④ \(W_{UQ}\) 在生产实现中不显式吸收、只吸收 \(q^C\) 之后的 \(W_{UK}\)（由 vLLM/SGLang 源码归纳的实现惯例）。

7. 局限与后续演进

  • 双路径工程税：absorbed（decode）/non-absorbed（prefill）两套实现、两套 FP8 量化路径要同时维护（vLLM/SGLang 里大量分支代码的来源），prefill 下 \(W_{UK}\) 上投影的中间量还逼出 chunked context 机制。
  • head_dim 576 超出生态假设：主流 flash kernel 面向 128/256 维设计，MLA 需要 FA3 的 MLA 分支或 FlashMLA 专用 kernel；页大小、布局也有专属约束（FlashMLA 要求页表连续有效、MQA-only）。
  • 缓存仍随序列长度线性：576 元素/token/层是常数下界，长上下文下绝对量仍在涨；且 absorbed 形式要求缓存「压缩即用」的完整 latent，无法再对 entry 内部做无损再压缩。
  • 算子链条更长：decode 每步多出 \(W_{UK}\)、\(W_{UV}\) 两个 bmm，在极小 batch 时占比可观；这也是 MLA 部署对 kernel 融合（如 FP8 bmm、Q 拼接量化）敏感的原因。
  • 演进：V3.2 在 MLA 之上加 Lightning Indexer + top-k 稀疏（DSA），缓存元素量不变、省算力；V4 转向 CSA/HCA——把「缓存即所需」推到极致，免去 decode 时的上投影与双路径，并首次压缩序列维。《DeepSeek-V4 Attention 设计解读（CSA/HCA）》有完整对比，其中的三维框架（entry 大小 / KV 头数 / 序列长度）正好把本文的 MLA 定位在「只压 entry」这一格。
