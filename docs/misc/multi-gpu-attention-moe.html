一句话：多卡部署 = 挑一个维度把张量切开（batch / 层 / 矩阵内部 / 序列 / 专家），再用一个通信原语把切开后的结果拼回来。切开省显存，拼回来花带宽——所有并行策略的差别，只是「切哪里」和「拼的代价多大、多久拼一次」。

五个维度一句话记住：DP切 batch，各卡模型全复制，吞吐 ×n；PP切层，只在 stage 边界传激活，通信最省但有气泡；TP切矩阵内部（attention 按 head 切），每层 2 次 all-reduce，必须待在机内 NVLink；CP/SP切序列，长上下文专用，KV cache 也 ÷n；EP切专家，每层 2 次 all-to-all，MoE 的默认选择。

通信量速记（每层、每卡、前向一次）：TP all-reduce ≈ \(2\cdot\frac{n-1}{n}\cdot B S H\cdot b\)，约 百 MiB 量级；EP all-to-all ≈ \(2\cdot T\cdot k\cdot H\cdot b\)，prefill 时可到 ~900 MiB（比专家计算还慢）；Ring-CP 传 KV ≈ \(4 S d_{kv}\cdot b\)，与卡数无关、可被计算掩盖；PP 只传 \(BSH\cdot b\)，最省。

显存速记：推理每卡 ≈ 权重字节/切片数 + KV cache/切片数 + 激活与框架开销；训练每个参数要 16 字节（bf16 权重 2 + bf16 梯度 2 + fp32 主权重与 Adam 动量 12），ZeRO-1 把后 12 字节摊到 DP 组上。

1.3 训练时激活有多大

训练要多存反向传播用的中间结果。以 Transformer 一层为例（\(s\)=序列长、\(b\)=batch、\(h\)=hidden、\(a\)=head 数、字节数按 bf16=2）：

\[ \text{每层激活} \approx sbh\left(34 + 5\frac{as}{h}\right)\ \text{字节} \]

前一项是各种线性层的输入输出（34·sbh），后一项是 attention 里那个 \(s\times s\) 的分数矩阵（5·as²b）。第二项随序列长平方增长——这正是 FlashAttention（把 \(s^2\) 矩阵不落显存）和 CP（把 \(s\) 切开）存在的理由。

举个数：\(s=4096,\ b=1,\ h=8192,\ a=64\)，每层激活 ≈ \(4096\times8192\times(34 + 5\times64\times4096/8192)\) ≈ 33.6M × 50 ≈ 1.6 GiB，80 层就是 130 GiB——比 70B 的权重还大。所以长上下文训练里，激活才是显存的第一杀手，而切激活的手段正是 SP（÷n）、CP（÷n）、重计算（V3 论文里明确重算所有 RMSNorm 与 MLA up-projection）。

3.2 TP：按 head 切（Megatron 风格，最常用）

核心技巧只有一句：\(W_q,W_k,W_v\) 按输出列切（列并行），\(W_o\) 按输入行切（行并行）。这样每卡拿到若干完整的 head，从投影到 attention 到输出投影全程不需要通信——因为每个 head 的 \(\mathrm{softmax}(Q_iK_i^\top)V_i\) 本来就只依赖自己；只在最后 \(W_o\) 出来时，每卡手里是一个「部分和」，需要一次 all-reduce 相加。

图 3-1｜TP 的精妙之处：列并行 + 行并行成对出现，中间那一大段（含 \(S^2\) 的 attention 计算）完全本地化，一层只付一次 all-reduce。同样的模式复制到 MLP（gate/up 列并行 + down 行并行），所以「每层 2 次 all-reduce」。

decode 阶段：通信量变小，但延迟变重要

decode 时每步只有「batch 里每条请求 1 个 token」，\(T\) = 并发数。batch=32 时 \(M = 32\times8192\times2 = 512\) KiB，带宽上完全不值一提；但 all-reduce 的次数没变（80 层 × 2 = 160 次），每次都有 kernel 启动 + 同步的固定开销（几 µs 到几十 µs）。160 次 × 30 µs ≈ 5 ms，而 decode 一个 token 本身可能只要 15 ms——TP 在 decode 阶段的成本主要是「次数 × 延迟」，不是字节数。这也是小模型、小 batch 的 decode 不建议开大 TP 的原因。

3.3 SP：Megatron 序列并行，TP 的免费补丁

纯 TP 有个浪费：在 TP 区域之外（LayerNorm、Dropout、残差），每卡都持有完整的 \([T,H]\) 激活，4 卡就是 4 份重复。SP 的做法是把这些区域的激活沿序列维切开，每卡只存 \(T/n\)；进 TP 区前用 all-gather 拼回完整序列，出 TP 区后用 reduce-scatter 直接散开。

  • 通信量不变：all-gather \((n{-}1)/n\cdot M\) + reduce-scatter \((n{-}1)/n\cdot M\) = all-reduce \(2(n{-}1)/n\cdot M\)，只是把一个原语换成两个；
  • 激活 ÷n：训练时按 §1.3 的公式，34·sbh 那一项直接省 n 倍，长序列训练里这是几十 GiB 的差别；
  • 推理时收益很小：推理只存当前 step 的激活，本来就不大。所以你会看到 DeepSeek-V3 的部署写「TP4 with SP」——训练/长 prefill 场景才需要它。

Ring 的通信为什么能被计算掩盖（一行推导）

设每张卡拿到 \(c = S/n\) 个 token 的 Q 和 KV，hidden 维 \(d\)。环上每步：计算两个 \(c\times d\) 与 \(d\times c\) 的矩阵乘 ≈ \(4c^2d\) FLOPs，通信把一块 KV 发给邻居 ≈ \(4cd\) 字节（K 和 V 各 \(c\cdot d\) 个数、bf16 各 2 字节）。要让通信藏进计算里：

\[ \frac{4cd}{\text{带宽}} \le \frac{4c^2 d}{\text{算力}} \quad\Longrightarrow\quad \boxed{c \ge \frac{\text{算力}}{\text{带宽}}} \]

结论很干净：掩盖通信只要求每块的 token 数超过「算力/带宽」这个比值，与卡数无关。代入数字（bf16 稠密峰值按 500 TFLOPS，实测有效算力打 5 折）：

MLA 的并行陷阱：KV 切不动

TP 能切 KV，靠的是「KV head 数 ≥ TP」——每卡分几个 head 的 KV。但 MLA 的 KV 是所有 128 个 head 共享的一份潜向量，没有 head 维可切。结果是：

  • 纯 TP 下，每张卡都要存整份 MLA KV cache（vLLM 官方明确说明：没有 DCP 时 MLA 的 KV 在每个 TP rank 上是完整复制的）——KV 完全不省，TP 越大浪费越多；
  • 出路一：DP-attention。每张卡跑自己的请求，KV 天然分开、零复制。DeepSeek-V3 官方部署正是这个思路（attention 侧 DP8/DP80）；
  • 出路二：DCP（decode context parallel）。把 KV 按序列切到 DCP 组，代价是每层要 AllGather Q、ReduceScatter 输出与 LSE。vLLM 报告在长上下文 decode 上吞吐约 3×；
  • 顺带的好处：MLA 的 attention 权重很小（V3 是每层 187 M 参数、61 层共 11.4 B → bf16 仅 21 GiB），小到可以每卡整份复制，于是 DP-attention 变得完全可行。这是 MLA 与 MoE 的一个隐藏协同。

三个结论，直接决定部署方案：
① prefill 的 all-to-all 是「带宽问题」：896 MiB/层 与专家计算（\(4096\times8\times6\times7168\times2048 \approx 2.89\) TFLOP ≈ 5.8 ms @500 TFLOPS，机内通信约 2.1 ms）同量级 → 机内可掩盖，跨机（18.8 ms/层）就盖不住了。DeepSeek-V3 论文实测跨机 EP 的「计算:通信 ≈ 1:1」，靠 DualPipe 让前向与反向互相掩盖、并用两个 micro-batch 交错才把这 1:1 藏掉。
② decode 的 all-to-all 是「延迟问题」：字节数很小，但每层两次全员同步的固定延迟会直接叠到 token 间隔上 → 要用低延迟 kernel（V3 decode 走 IB 点对点 + IBGDA，DeepEP 的 low-latency 模式）。
③ 降精度是最便宜的一刀：V3 训练时把 dispatch 的激活量化成 FP8、combine 保留 BF16（论文 §3.3.3），通信量直接减半，且与 FP8 的 up-projection GEMM 天然兼容。

跨机 all-to-all 的工程做法（V3 论文的实现细节）

  • 分层转发：先跨节点用 IB 把 token 发到目标节点的一张卡，再由这张卡在节点内用 NVLink 转发给同节点的其它卡——避免每张卡都单独占一条 IB 连接；
  • 专用 SM + warp specialization：划出 20 个 SM（H800 共 132 个）分成 10 个通信通道，dispatch 阶段三类 warp 分别负责「IB 发送」「IB→NVLink 转发」「NVLink 接收」，按实际负载动态调整 warp 数；
  • combine 侧顺手做规约：NVLink→IB 转发时就地累加，减少回程字节；
  • 少占 L2：用定制 PTX 指令 + 自动调优的 chunk size，降低对计算 kernel 的干扰。

这些优化后来被抽成开源库 DeepEP，提供两类 kernel：高吞吐（NVLink 机内 + IB 跨机，用于 prefill/训练）与低延迟（纯 IBGDA RDMA，用于 decode），dispatch 支持 BF16 与 FP8。vLLM / SGLang 都已把它作为可选后端。

5. 补齐另外两维：PP 与 DP / ZeRO

Attention 用 TP/CP、MoE 用 EP，这两维已经覆盖"层内"的全部故事。但一台真机还要回答两个问题：模型太长一张卡（一组卡）放不下怎么办（PP），以及怎么把吞吐扩到几百上千卡（DP）。

5.1 PP：通信最省的切法，代价是气泡

PP（pipeline parallel，流水线并行）按层切：把 \(L\) 层分成 \(p\) 段（stage），第 \(i\) 段放在第 \(i\) 组卡上，只有段与段的边界需要传数据。

\[ \text{一次边界传输} = B\cdot S\cdot H\cdot b \ \text{字节（单向）} \qquad\qquad \text{气泡率} = \frac{p-1}{m+p-1} \]

\(m\) = micro-batch 数（把一个大 batch 拆成 \(m\) 份依次灌进流水线）。拿 Llama-3-70B、\(S=4096\)、bf16 代入：一次边界传输 = \(4096\times8192\times2 = \) 64 MiB。对比 TP=8 时每层就要 all-reduce 两次共 224 MiB、80 层合计 17.5 GiB——这就是"PP 通信最省"的量化含义，差了两个数量级，也是为什么 PP 是唯一可以放心跨机的"模型内"切分。

DP-attention：MLA + MoE 时代的"新 DP"

§3.5 提过的一个关键组合，值得单独强调：MLA 的 KV cache 无法按 head 切分，TP 只会让每卡都存一份完整的 KV。而 MLA 的 attention 权重又特别小（V3 是 21 GiB bf16，除以 TP=4 只剩 5.3 GiB）。于是最优解变成：attention 侧走 DP（每卡处理自己那批请求，KV 天然分开、零复制、零通信），MoE 侧走大 EP（专家摊到几百张卡上）。

\[ \text{V3 decode：}320\ \text{卡} = \underbrace{\text{DP}80 \times \text{TP}4}_{\text{attention}} \quad+\quad \underbrace{\text{EP}320}_{\text{MoE}} \]

这也解释了一个看起来矛盾的现象：同一批卡在不同层里扮演不同角色。attention 层里，4 张卡是一个 TP 组、共同处理同一批 token；到了 MoE 层，这 4 张卡变成 EP 组里的 4 个独立节点、各自把 token 发给别的卡上的专家。框架里这体现为"通信组的重新划分"（详见 vLLM 分布式第 5 讲里 initialize_model_parallel 那张 rank 网格）。

5.3 把五个维度放回真实的机架上

图 5-1｜2 节点 16 卡的典型配置：TP=8（机内） × PP=2（跨机） × DP=N（最外层）。三个要点：① TP 永远关在机内——它每层通信两次，跨机 IB 撑不住；② PP 放跨机——每个 micro-batch 只传一次 64 MiB；③ 同一批 8 张卡在 attention 层是 TP 组、在 MoE 层是 EP 组，物理卡不变，只是通信组和权重切法变了（图中第 ② 行只对 MoE 模型成立，Llama-3-70B 这类稠密模型只有第 ① 行）。

7. 六个场景配方

下面每个配方都给出具体数字，可以直接照着算自己的场景。所有显存按"单卡 80 GiB、预留 3 GiB 给 CUDA/NCCL/碎片"计。

配方 1｜单机 8×H100/H800（80 GiB），Llama-3-70B bf16，在线服务

基线方案 TP=8：权重 131.5 ÷ 8 = 16.4 GiB/卡 → 剩 60.6 GiB 给 KV → 每卡存 \(320/8 = 40\) KiB/token → 全系统 159 万 token ≈ 12 条 128K 或 388 条 4K 请求。

替代方案 TP=4 × DP=2：权重 32.9 GiB/卡 → 每副本剩 44.1 GiB → 每副本 58 万 token、两副本合计 116 万 token（比 TP=8 少 27%，因为权重被复制了两份）。

怎么选：长上下文或高并发（>200 路）→ TP=8（KV 池更大）；短请求高 QPS、追求低首 token 延迟 → TP=4×DP=2（每层通信减半、两条独立队列互不阻塞）。不要用 PP：80 层切两段会让 decode 阶段每卡闲一半时间。

配方 2｜单机 8 卡，DeepSeek-V3 / R1（671B MoE）

bf16 不可能：1249.8 GiB ÷ 8 = 156 GiB/卡 > 80 GiB。

FP8 也放不下：624.9 ÷ 8 = 78.1 GiB/卡，80 GiB 的卡只剩 1.9 GiB（连 CUDA context 都不够）→ OOM。

可行解：① 换 8×H200（141 GiB）：78.1 GiB 权重 + 剩 62.9 GiB 给 KV；② 换 W4A16：312.4 ÷ 8 = 39 GiB/卡，80 GiB 卡可行，但要接受量化精度损失；③ 上 2 节点（见配方 3）。

并行：EP=8（256 只专家 → 每卡 32 只）+ attention 侧 TP=8 或 DP=8（MLA 的话强烈建议 DP，否则 KV 复制 8 份）。

配方 3｜2 节点 16 卡，671B FP8，中等并发在线服务

显存：624.9 ÷ 16 = 39.1 GiB/卡 → 剩 37.9 GiB。attention 走 DP=16、KV 不复制 → 每卡 37.9 GiB ÷ 68.6 KiB = 58 万 token，全系统 928 万 token。

通信是唯一的问题：EP=16 跨机 all-to-all = 896 MiB/层 @ IB 50 GB/s = 18.8 ms/层，58 个 MoE 层 = 1.09 s/step（完全不掩盖的话）。必须上：FP8 dispatch（减半到 9.4 ms）+ DeepEP 高吞吐 kernel + 与专家 GEMM 重叠。

更稳的替代：PP=2 × EP=8——把 all-to-all 全部关进机内 NVLink（2.09 ms/层），跨机只传 64 MiB 激活。代价是 PP 气泡和"两套专家分布"的运维复杂度。跨机带宽弱（HDR 200Gb/s 或纯以太网）时，这是唯一靠谱的选择。

配方 4｜128K 长上下文的单请求 prefill（RAG / 长文档总结）

瓶颈不是显存而是 \(O(S^2)\) 算力：128K 的 attention 是 4K 的 \(32^2 = 1024\) 倍计算量。单卡几十秒起步。

方案：CP=8（每卡只处理 16K 的 Q）+ TP=4。机内优先 Ulysses（70B 有 64 个 Q head，够切 8 份）；跨机只能 Ring（Ulysses 的 all-to-all 跨机太贵）。

能不能掩盖？用 §3.4 的判据 \(c \ge \frac{\text{算力}}{\text{带宽}}\)：H100 是 500 TFLOPS ÷ 450 GB/s ≈ 1100 token；这里每卡 chunk \(c = 131072/8 = 16384\) token，超阈值 15 倍 → Ring 通信完全被计算掩盖，跨机（阈值 ~10000）也刚好够。

KV 显存：70B @128K = 40 GiB，CP=8 → 每卡 5 GiB，很轻松。MLA 模型（V3）@128K 只要 8.6 GiB，但记得它不随 TP 切分，要用 DCP 或 DP-attention。

配方 5｜高并发 decode（V3 官方生产配置，40 节点 320 卡）

配置：attention TP=4 + SP，DP=80；MoE EP=320（每卡只托管 1 只专家，另用 64 卡放冗余专家和共享专家）；dispatch/combine 走 IB 点对点 + IBGDA。

每卡显存：attention 权重 11.4 B bf16 ÷ 4 = 5.3 GiB + 1 只专家 FP8 ≈ 42 MiB → 约 5.4 GiB，扣掉 3 GiB 预留后剩 ~71 GiB 全给 KV → 每卡约 108 万 token（\(71\,\text{GiB} / 68.6\,\text{KiB}\)）。

瓶颈是延迟不是带宽：每层 all-to-all 只有 31.5 MiB（batch=128、k=9），但 58 层 × 2 次全员同步的固定延迟会直接叠进 token 间隔。所以官方只给通信分配少量 SM，并用低延迟 kernel 绕开 CPU 代理。

注意：每专家 batch 通常 ≤256 token → 专家 GEMM 是访存受限的，加大 EP 反而提高了每卡的利用率（权重更少、KV 更多）。

配方 6｜训练（V3 官方：2048 卡）

配置：PP=16 + EP=64（8 节点） + ZeRO-1（DP=2），完全没有 TP。

为什么不用 TP：TP 每层两次 all-reduce 无法跨机，而 2048 卡必须跨机；H800 的 NVLink 还被限到 ~400 GB/s 双向。官方选择"把跨机通信全部交给 PP（低频）和 EP（可用 DualPipe 掩盖）"。

每卡显存：671 B × \((4 + 12/2) = 10\) 字节/参数 = 6249 GiB，÷ (16×64=1024 路切分) = 6.1 GiB/卡，剩下的全给激活。

省激活的两招：① 重计算所有 RMSNorm 和 MLA 的 up-projection（这俩便宜但占内存）；② DualPipe + 两个 micro-batch 交错，把跨机 EP 那 1:1 的计算/通信比藏掉。

8. 常见误区与自检清单

误区事实出处
"TP 开大一点吞吐更高"TP 是把同一批 token 拆给多卡算，吞吐上限仍受单份 batch 限制；它降延迟、不降单请求成本。提吞吐要靠 DP/EP§3.2
"MoE 激活 37B，所以显存只要 37B"激活参数决定算力和带宽，显存要装全部 671B 专家权重。算得像 37B，存得像 671B§4.1
"PP 能降单请求延迟"层是串行依赖的，PP 只增加同步点。推理 decode 时 \(m=1\)，气泡率 \((p-1)/p\)§5.1
"EP 越大越好，最好等于专家数"EP 越大，all-to-all 越可能跨机；每卡专家越少，专家 GEMM 的 batch 越小、越访存受限。V3 decode 才用到 EP=320，prefill 只用 EP=32§4.3
"DP 能解决装不下"DP 是整份复制，只会更放不下。装不下要用 TP/PP/EP/ZeRO/量化§1
"all-reduce 通信量随卡数线性增长"ring all-reduce 每卡是 \(2\frac{n-1}{n}M \approx 2M\)，与卡数几乎无关。变的是延迟项（\(2(n-1)\) 次同步）§3.2
"MLA 的 KV cache 会自动随 TP 切分"MLA 的 KV 是所有 head 共享的一份潜向量，没有 head 维可切；纯 TP 下每卡存整份。要用 DCP 或 DP-attention§3.5
"带宽够就没问题了"decode 阶段字节数很小，瓶颈是每次集合通信的固定延迟 × 层数 × 2。这时候要换低延迟 kernel（IBGDA），加带宽没用§4.3
"量化 KV 和量化权重是一回事"权重量化省的是固定开销，KV 量化省的是随并发线性增长的部分。高并发长上下文场景，KV 量化的收益远大于权重量化§3.5
"专家负载均衡是训练的事，部署不用管"部署侧的不均衡直接变成尾延迟和"按最坏情况开缓冲区"的显存浪费。V3 线上跑 32（prefill）/64（decode）只冗余专家，每 10 分钟重排一次§4.4

上线前的十条自检

  1. 权重字节数 ÷ 切分因子 + KV + 3 GiB 预留 ≤ 单卡显存？（先算这个，别的都是空谈）
  2. KV cache 用的是哪个公式？GQA 是 \(2Ln_{kv}d_h b\)，MLA 是 \(L(d_c+d_R)b\)（没有那个 2）。
  3. 如果是 MLA + TP，我确认过 KV 是复制的还是切分的吗？（vLLM 需要显式开 DCP 或用 DP-attention）
  4. TP 组是否完整落在同一台机器内？nvidia-smi topo -m 看过 NVLink 连接了吗？
  5. \(n_{kv} \ge\) TP 吗？不满足的话 KV head 会被复制，KV 省不下来。
  6. MoE 用的是 EP 还是 ETP？EP 才能线性扩吞吐；ETP 只在单只专家装不下时才需要。
  7. 跨机的 all-to-all 每层多少毫秒？和专家 GEMM 的时间比是多少？超过 1:1 就要考虑 PP 替代或 DeepEP。
  8. prefill 和 decode 用的是同一套并行配置吗？成熟部署应该是两套（甚至 PD 分离）。
  9. 训练的话：micro-batch 数 \(m\) 够不够把 PP 气泡压到 10% 以下（\(m \ge 5\text{–}10p\)）？
  10. 专家负载统计接上了吗？冗余专家 / EPLB 有没有开？
