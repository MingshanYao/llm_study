一句话：集合通信 = 一组进程（rank）按约定好的语义交换数据。所有原语都是三件事的组合——搬数据（gather / scatter / all-to-all）、做归约（reduce）、发副本（broadcast）。

八个原语一句话记住：Broadcast一份发给所有人；Scatter一份切开分给所有人；Gather每人交一片汇总到一人；All-Gather每人交一片、人人都拿到全套；Reduce所有人的数据求和给一人；All-Reduce求和后人人都有；Reduce-Scatter求和后每人只拿自己那一片；All-to-All每人给每人发不同的一块（分布式转置）。

最重要的一条恒等式：All-Reduce = Reduce-Scatter + All-Gather。Ring All-Reduce 就是这么实现的；Megatron 序列并行、ZeRO、FSDP 都是把这条恒等式反过来用。

通信量速记（\(N\) 卡、每卡消息 \(S\) 字节）：All-Reduce 每卡线上量 \(W=2\frac{N-1}{N}S\)（与卡数几乎无关，渐近 \(2S\)）；All-Gather / Reduce-Scatter / All-to-All 各 \(W=\frac{N-1}{N}S\)；Broadcast / Reduce 受 root 出口限制，\(W=S\) 且无法用满所有链路。

时间公式：\(T = \text{步数}\times\alpha + W\times\beta\)。小消息看 \(\alpha\)（步数越少越好 → Tree）；大消息看 \(\beta\)（每卡线上量越小越好 → Ring 最优）。机内 8 卡的分界点约在 5 MiB。

1. 先把「通信量」说清楚：三个口径与记号约定

1.1 点对点 vs 集合

最原始的通信只有两个动作：send(dst, buf) 和 recv(src, buf)——点对点（P2P）。流水线并行（PP）用的就是它：第 40 层的激活从 GPU 1 发给 GPU 2，一次一条消息。

但一旦是「\(N\) 张卡都要参与同一件事」——比如把 8 张卡上的梯度加起来——用 P2P 手写就会变成 \(O(N^2)\) 条消息和一堆死锁风险。集合通信（collective communication）就是把这类「全员参与、语义固定」的模式封装成一个调用，由库（NCCL / MPI / Gloo / RCCL）负责选拓扑、排调度、做流水线。你只说「all-reduce 这个张量」，库来决定谁在第几步发给谁。

点对点（send / recv）集合通信（collective）
参与者2 个 rank通信组（communicator）内全部 rank，缺一个就挂死
语义只搬数据搬数据 + 可选归约（sum / max / prod…）
典型用途PP 传激活、Ring Attention 传 KVTP 的 all-reduce、DP 的梯度归约、EP 的 all-to-all
性能由谁决定单条链路带宽算法（ring / tree / …）+ 拓扑 + 消息大小
「集合」指的是参与者的集合，不是数据结构。一个 communicator 就是一份 rank 名单（外加它们协商好的连接）。同一次调用必须由名单里所有 rank 以相同顺序发起，否则先到的会一直等——这是分布式训练「卡住不动」最常见的原因。

1.3 「通信量」有三个口径，混用就会算错

这是本篇最想先钉死的一件事。同一句「all-reduce 的通信量是多少」，可能指三件完全不同的东西：

口径说的是什么All-Reduce 的值谁在用
① 语义量 \(S\)应用层看到的张量有多大\(S\)写模型的人：「我这层要 all-reduce 一个 64 MiB 的激活」
② 线上量 \(W\)每卡 NVLink / 网卡端口实际吐出多少字节\(2\frac{N-1}{N}S \approx 2S\)算带宽占用、算耗时、算成本的人
③ 时间 \(T\)这次调用花多久\(2(N-1)\alpha + W\beta\)判断能不能被计算掩盖、要不要换算法的人

三者关系：① 决定 ②（差一个算法系数），② 和步数决定 ③（差一个带宽和延迟）。很多「我算出来通信量对不上」的困惑，都是因为一方说的是 ① 而另一方说的是 ②，或者把 algbw（用 ① 算）当成了 busBw（用 ② 算）——§3.4 专门讲这件事。

2.1 原语之间的等价关系（记这几条就够了）

\[ \underbrace{\text{All-Reduce}}_{\text{人人有和}} \;=\; \underbrace{\text{Reduce-Scatter}}_{\text{各拿一片的和}} \;+\; \underbrace{\text{All-Gather}}_{\text{把片段拼给所有人}} \] \[ \text{All-Gather} = \text{All-to-All 的特例（每行都发同一块）},\qquad \text{Broadcast} = \text{All-Gather 的特例（只有 root 有数据）} \] \[ \text{Reduce} = \text{Reduce-Scatter} + \text{Gather},\qquad \text{All-Reduce} = \text{Reduce} + \text{Broadcast}\ (\text{但 root 是瓶颈，没人这么实现}) \]

第一条恒等式是全部现代分布式训练的地基：

  • Megatron 序列并行（SP）：把 TP 里的 all-reduce 拆成 reduce-scatter + all-gather，总线上量一模一样（\(2\frac{N-1}{N}S\)），但中间的 LayerNorm / Dropout 激活可以只存 \(1/N\)，白省显存。
  • ZeRO-1/2、FSDP：梯度不再 all-reduce，而是 reduce-scatter（每卡只留自己那 \(1/N\) 的梯度去更新优化器状态），更新完再 all-gather 参数。通信量与普通 DP 相同。
  • Ring All-Reduce：本身就是按这条恒等式实现的两阶段算法（§4）。

2.2 用 PyTorch 写出来：shape 是唯一容易错的地方

把上面八张卡片翻译成代码。注意每个 API 里的张量是「每卡的」还是「总量的」——这是最容易写错、也最容易导致通信量算错的地方：

import torch, torch.distributed as dist

N = dist.get_world_size()          # rank 数
r = dist.get_rank()                # 我是谁

# ① broadcast：所有 rank 都要传同一个 tensor，root 的值覆盖其他人
t = torch.full((1024,), float(r), device="cuda")   # 每卡 shape [1024]
dist.broadcast(t, src=0)                           # 之后所有卡的 t 都等于 r0 的值

# ② / ③ scatter / gather：list 版本只在 root 上需要
in_list = [torch.full((256,), float(i), device="cuda") for i in range(N)] if r == 0 else None
out     = torch.empty(256, device="cuda")
dist.scatter(out, in_list, src=0)                  # root 的 N×256 -> 每卡 256
g_list  = [torch.empty(256, device="cuda") for _ in range(N)] if r == 0 else None
dist.gather(out, g_list, dst=0)

# ④ all-gather：**输出是输入的 N 倍**
local = torch.randn(256, device="cuda")            # 每卡 [256]
full  = torch.empty(N * 256, device="cuda")        # 每卡 [N*256]  <- 别写成 256
dist.all_gather_into_tensor(full, local)

# ⑤ / ⑥ reduce / all-reduce：shape 完全不变，只有值变了
g = torch.randn(4096, device="cuda")
dist.all_reduce(g, op=dist.ReduceOp.SUM)           # 每卡 [4096] -> [4096]
g /= N                                             # 求平均要自己除

# ⑦ reduce-scatter：**输入是输出的 N 倍**（与 all-gather 相反）
src = torch.randn(N * 256, device="cuda")          # 每卡 [N*256]
dst = torch.empty(256, device="cuda")              # 每卡 [256]
dist.reduce_scatter_tensor(dst, src, op=dist.ReduceOp.SUM)

# ⑧ all-to-all：输入输出同 shape，但按 rank 维重新分配
send = torch.randn(N, 256, device="cuda")          # send[j] 是要发给 rank j 的
recv = torch.empty(N, 256, device="cuda")          # recv[i] 是 rank i 发来的
dist.all_to_all_single(recv, send)

# 异步 + 与计算重叠：几乎所有真实性能优化都靠这两个参数
work = dist.all_reduce(g, async_op=True)           # 立刻返回句柄
do_something_else()                                # 计算与通信重叠
work.wait()                                        # 需要结果时才阻塞

all_gather_into_tensor / reduce_scatter_tensor / all_to_all_single 是「单张量」版本，比 list 版本少一次显存拷贝，实际框架里用的都是它们，底层直接对应 NCCL 的 ncclAllGather / ncclReduceScatter / ncclSend+Recv。

PyTorch 的 all_gather(tensor_list, tensor)（list 版本）在 NCCL 后端上是用 \(N\) 组 send/recv 模拟的，比 all_gather_into_tensor 慢；后者才走真正的 ncclAllGather。写性能敏感代码时一律用单张量版本。

3. 通信量怎么算：α-β 模型、八个原语的推导与速查表

3.1 α-β 模型：一次集合通信花多久

业界通用的成本模型只有两项。设一次调用被拆成 \(k\) 步点对点传输、每卡累计发出 \(W\) 字节：

\[ T \;=\; \underbrace{k\cdot\alpha}_{\text{延迟项：与消息大小无关}} \;+\; \underbrace{W\cdot\beta}_{\text{带宽项}=\,W/B} \]

模型假设链路全双工（收发同时）、每卡各有一条带宽 \(B\) 的链路、且所有链路同速。它不精确，但足够回答两类问题：

  • \(W \ll \alpha B\)（小消息）：\(T \approx k\alpha\)，只看步数。这正是 decode 阶段 TP all-reduce 的处境——512 KiB 的消息，时间全花在 14 次传输的启动与同步上。
  • \(W \gg \alpha B\)（大消息）：\(T \approx W/B\)，只看每卡线上量。这正是 prefill 激活和梯度 all-reduce 的处境。

两段的分界点 \(S^\ast\) 满足「延迟项 = 带宽项」。以机内 8 卡、\(\alpha=1.5\,\mu s\)、\(B=450\) GB/s 代入 All-Reduce（\(k=2(N-1)\)、\(W=2\frac{N-1}{N}S\)）：

\[ 2(N-1)\alpha = 2\tfrac{N-1}{N}S^\ast\beta \;\Longrightarrow\; S^\ast = N\alpha B = 8 \times 1.5\,\mu s \times 450\,\text{GB/s} \approx \mathbf{5.2\ MiB} \]
\(S^\ast\approx 5\) MiB 是个很有用的经验值：机内 all-reduce 的消息小于 5 MiB 就属于延迟主导——此时加带宽毫无帮助，该做的是减少调用次数（融合）、减少步数（换 Tree / one-shot）；大于 5 MiB 才轮到「压线上量」出场。注意 \(S^\ast\) 与 \(N\) 成正比、与 \(\alpha B\) 成正比：跨机（\(\alpha\) 大 10 倍、\(B\) 小 9 倍）时 \(S^\ast\) 会涨到几百 MiB，也就是跨机场景下几乎所有 LLM 通信都是延迟主导的。

3.1.1 \(k\)（步数）到底是什么：串行的时间深度

\(k\) 不是「一共发生了多少次 send」，而是无法并行掉的那部分时间深度。把它想成接力赛：同时进行的传递算一棒，必须等上一棒跑完才能开始的传递算下一棒。

用 Ring Reduce-Scatter（§4 详解）看这条界线在哪：

  • 第 1 步里，\(N\) 张卡同时各发一个 \(S/N\) 的块给下游。这是 \(N\) 次 send，但只算 1 步——因为它们互不依赖，占的是同一段时间。
  • 第 2 步必须等第 1 步的接收方把数据加完才能发，所以它是新的一棒，要多付一个 \(\alpha\)。
  • 一个块要集齐 \(N\) 份数据，必须依次经过 \(N-1\) 张卡 → \(N-1\) 步。加上 All-Gather 那 \(N-1\) 步，All-Reduce 共 \(k=2(N-1)\)。

\(W\) 则是同一张卡在整个过程中累计发出的字节，与并行无关：Ring Reduce-Scatter 里每卡每步发 \(S/N\)、发 \(N-1\) 步，所以 \(W=(N-1)\cdot\frac{S}{N}=\frac{N-1}{N}S\)。

\(\alpha\) 项数的是「串行深度」，\(\beta\) 项数的是「单卡累计字节」——两者的口径根本不同，这是最容易搞混的地方。 所以「星型 all-reduce」的 \(k\) 只有 2（收一轮、发一轮，看起来步数极少），但根节点的 \(W=2(N-1)S\) 是别人的 \(N\) 倍，时间照样被它拖死。反过来 Ring 的 \(k=2(N-1)\) 很大，但每卡 \(W\) 与 \(N\) 无关。判断一个算法好不好，必须两项一起看，而且 \(W\) 要看最忙那张卡： \[ T \;=\; k\cdot\alpha \;+\; \max_r W(r)\cdot\beta \qquad(\text{用 } \max_r W(r)\text{，不是平均值 }\overline{W}) \]

两类算法因此各占一头：树 / 递归折半把 \(k\) 压到 \(O(\log N)\) 而 \(W\) 一分不变（小消息赢）；环把 \(W\) 压到下界而 \(k\) 是 \(O(N)\)（大消息赢）。§3.2 逐个原语把这两笔账算出来，§5.2 给出选型表。

3.2 通信量推导：All-Reduce 下界与八个原语的 \(W\)

3.2.1 先证 All-Reduce 的下界

这不是 ring 算法的特性，而是任何用 send/recv 实现的 all-reduce 的共同下界。nccl-tests 官方文档给的论证非常干净：

  1. 对每一个元素，最终要得到 \(o_0 = o_1 = \cdots = o_{N-1} = i_0 + i_1 + \cdots + i_{N-1}\)。
  2. 这需要 \(N-1\) 次加法（把 \(N\) 个输入合成一个）和 \(N\) 次赋值（把结果放到 \(N\) 个 rank 上）。
  3. 除了「最后一个输入恰好与第一个输出在同一个 rank」这一处能省掉，其余每次加法 / 赋值都发生在不同的 rank 上，必须靠一次跨 rank 传输完成 → 每个元素至少 \(2(N-1)\) 次传输。
  4. \(N\) 个 rank 各有一条带宽 \(B\) 的对外链路，\(S\) 个元素 × \(2(N-1)\) 次传输分摊到 \(N\) 条链路上：
\[ t \;\ge\; \frac{S\cdot 2(N-1)}{N\cdot B} \;=\; \frac{S}{B}\cdot 2\frac{N-1}{N} \qquad\Longrightarrow\qquad W_{\min} = 2\frac{N-1}{N}S \]

Ring All-Reduce 正好达到这个下界（§4 逐步验证），所以被称为「带宽最优」。下面把同样的算法套到其余七个原语上，逐个把 \(W\) 算出来。

\(2\frac{N-1}{N}\) 随 \(N\) 的变化：\(N=2\) → 1.0，\(N=4\) → 1.5，\(N=8\) → 1.75，\(N=64\) → 1.97，\(N\to\infty\) → 2。 即 All-Reduce 的每卡线上量与卡数几乎无关——这正是数据并行能扩到上千卡的原因：卡越多，每卡要传的字节数不变（永远约等于 2× 梯度大小）。但延迟项 \(2(N-1)\alpha\) 是随 \(N\) 线性增长的，所以小消息场景下卡数依然会要命（见 §3.5 图与 §5）。

3.2.2 推导前先分清三个量

「通信量」这个词在资料里至少有三种口径，混用会得出完全相反的结论。本节统一记号：

记号含义用在哪
\(W(r)\)rank \(r\) 全程累计发出的字节数逐卡算账；接收量在全双工下与之对称，不额外花时间
\(W_{\max}=\max_r W(r)\)最忙那张卡的量决定时间：\(T = k\alpha + W_{\max}\beta\)（§3.1.1）

Ring、递归折半、双二叉树的 \(W(r)\) 对所有 \(r\) 都相同，所以 \(W_{\max}=\overline{W}\)，账很好算。星型和朴素二项树不是——它们的 \(W_{\max}\) 可以是 \(\overline{W}\) 的好几倍，这正是它们输掉的原因。§3.3 表里的 \(W\) 一律指 \(W_{\max}\)。

3.2.3 Broadcast 与 Reduce：一对镜像

Broadcast：root 有 \(S\)，其余为 0；结束时人人有 \(S\)。

  1. 下界：\(N-1\) 个节点各要收到 \(S\)，所以 \(\sum_r W(r) \ge (N-1)S\)。摊到 \(N\) 条链路上，每卡的理想值是 \(\frac{N-1}{N}S \approx S\)。
  2. 线性 / 星型：root 依次发给 \(N-1\) 个节点 → \(W(\text{root})=(N-1)S\)、其余为 0。\(W_{\max}\) 是理想值的 \(N\) 倍，\(k=N-1\)。（若交换机允许 root 同时发 \(N-1\) 份，\(k\) 可以记 1，但 root 的 NIC 仍要吐 \((N-1)S\) 字节，\(\beta\) 项一分没省。）
  3. 二项树（倍增树）：第 \(i\) 步由所有已拿到数据的 \(2^i\) 个节点同时转发给 \(r+2^i\)，故 \(k=\log_2 N\)。但每卡的发送次数极不均匀——\(N=8\) 时逐卡发送份数是 [3,2,1,1,0,0,0,0]（单位 \(S\)），root 发 \(\log_2 N\cdot S = 3S\)，而 \(\sum_r W(r)=7S=(N-1)S\)，与线性实现完全相同。
  4. 分块流水线：把 \(S\) 切成 \(P\) 块，收到一块就立刻转发。\(k=\log_2 N + P\)，而每卡累计转发量降到 \(\approx\frac{N-1}{N}S\)。这才是 §3.3 表里 Broadcast 记 \(W=S\) 的由来，也是 NCCL 双二叉树 + 分块的实际形态。
「树状广播的通信量是 \(\log_2 N\cdot S\)」——这个流传很广的说法是错的，或至少严重误导。 \(\log_2 N\) 是步数（\(\alpha\) 项），不是通信量的改善。朴素二项树里 \(\log_2 N\cdot S\) 只是 root 一张卡的发送量，全网总量仍是 \((N-1)S\)，和线性实现一模一样；而且 \(\log_2 N\cdot S > S\)，比起流水线的 \(\approx S\) 反而更差。 树买到的是「\(N-1\) 步 → \(\log_2 N\) 步」，即延迟项缩小 \(\frac{N-1}{\log_2 N}\) 倍（\(N=8\) 时 2.3×，\(N=1024\) 时 102×）。小消息用树是因为步数，不是因为字节变少了。

图 3-1：二项树（倍增树）广播，\(N=8\)。第 \(i\) 步由所有已拿到数据的 \(2^i\) 个节点同时转发给 \(r+2^i\)，所以 3 步就覆盖 8 卡（\(k=\log_2 N\)）——图上四列就是四个时刻，时间从左往右流。但看右列「发几份」：r0 发了 3 次、r1 两次、r2/r3 各一次、r4–r7 一次都没发。\(W_{\max}=3S=\log_2 N\cdot S\)，而 \(\sum_r W(r)=7S=(N-1)S\) —— 总字节和线性实现一模一样，只是压在了左边几张卡上。这就是 §3.2.2 里「朴素二项树的 \(W_{\max}\) 是 \(\overline W\) 的好几倍」的图像版。

Reduce 是 Broadcast 的镜像（人人有 \(S\)，结束时只有 root 有归约结果）：

  1. 星型：每个非根发 \(S\) → 发送侧很均匀（\(W_{\max}=S\)），但 root 要收 \((N-1)S\)，接收侧成了瓶颈，且 \(k=N-1\)。
  2. 二项树：\(k=\log_2 N\)。每个非根只向父节点发 1 份已归约的 \(S\)（子树的数据在上行途中就被合并了），所以 \(W_{\max}=S\)；root 从 \(\log_2 N\) 个孩子各收 \(S\)，收 \(\log_2 N\cdot S\)。
  3. 结论：Reduce 的发送侧本来就近乎最优，树改善的是步数和 root 的接收侧。§3.3 表里记 \(W=S\)。

Scatter / Gather 是上面两者的「切块版」：root 的 \(S\) 切成 \(N\) 份，第 \(i\) 份归 rank \(i\)。

  • Scatter：root 发 \(\frac{N-1}{N}S\)（自己那份不用发），其余为 0 → \(W_{\max}=\frac{N-1}{N}S\)；每个非根收 \(S/N\)。\(k=N-1\)（线性）或 \(\log_2 N\)（树）。
  • Gather：每个非根发 \(S/N\) → \(W_{\max}=S/N\)；root 收 \(\frac{N-1}{N}S\)。与 Scatter 镜像。

3.2.4 Reduce-Scatter：两种算法，同一个 \(W\)

定义：每卡输入 \(S\)；结束后 rank \(r\) 只持有「第 \(r\) 块的总和」，大小 \(S/N\)。

\[ W \;\ge\; (N-1)\cdot\frac{S}{N} \;=\; \frac{N-1}{N}S \qquad\text{（每卡必须把自己那份数据中属于其余 } N-1 \text{ 块的部分送出去）} \]

\(\displaystyle W=\sum_{j=1}^{d}\frac{S}{2^{j}} = S\Big(1-\frac{1}{2^{d}}\Big)=\Big(1-\frac{1}{N}\Big)S=\frac{N-1}{N}S\)
这是全篇最重要的一条推导：步数从 \(N-1\) 降到 \(\log_2 N\)，\(W\) 一个字节都没多。 递归折半每步交换的量指数衰减（\(S/2, S/4, S/8,\dots\)），几何级数求和刚好收敛到 \((1-\frac1N)S\)；而 Ring 每步交换的量恒定（\(S/N\)），要 \(N-1\) 步才凑齐同一个总数。「树/递归类算法必然多花流量」是错觉——它们只是把同样的字节压缩进了更少的轮次。这就是 NCCL 在小消息上切到 Tree / PAT 而不损失带宽的数学基础。

3.2.5 All-Gather：镜像的递归加倍

定义：每卡输入 \(S/N\)；结束后人人持有拼接好的 \(S\)。

\(S\) 的口径在这里会翻 \(N\) 倍，是最常见的算错点。本节和 §3.3 表一律取 \(S=\) 输出总长（即拼接后的完整张量）。若你习惯用「本地分片 \(s\)」，则 \(W=(N-1)s=\frac{N-1}{N}S\)，看着像差 \(N\) 倍其实是同一个数。nccl-tests 的 size 列、all_gather_into_tensor 的输出张量都按输出总长算；而 PyTorch 的 all_gather(list, tensor) 里你传进去的 tensor 是分片。对不上时先查口径。

3.2.6 All-Reduce = Reduce-Scatter + All-Gather

\[ W = \underbrace{\tfrac{N-1}{N}S}_{\text{RS}} + \underbrace{\tfrac{N-1}{N}S}_{\text{AG}} = 2\tfrac{N-1}{N}S, \qquad k = \underbrace{(N-1)}_{\text{RS}} + \underbrace{(N-1)}_{\text{AG}} = 2(N-1)\ \text{（Ring）}\ \text{或}\ 2\log_2 N\ \text{（递归）} \]

与 §3.2.1 的下界证明完全吻合。对照星型（参数服务器）：root 收 \((N-1)S\) 再发 \((N-1)S\) → \(W_{\max}=2(N-1)S\)，是 Ring 的 \(N\) 倍。\(N=8\) 时同一份梯度，星型要 14× 的时间——这就是「参数服务器撑不过 8 卡」的算术原因，也是 Horovod 当年换成 ring 的全部理由。

3.2.7 All-to-All：唯一无法优化的原语

定义：每卡输入 \(S\)，切成 \(N\) 块，第 \(j\) 块发给 rank \(j\)（纯置换，无归约、无复制）。

\[ W = S - \underbrace{\frac{S}{N}}_{\text{发给自己的那块不上网}} = \frac{N-1}{N}S \qquad(\text{既是下界，也是实际值}) \]
  • 没有可聚合的结构 → 树、环、递归都帮不上忙，\(W\) 无从再降。\(k=N-1\)（逐对串行）或 \(1\)（全连接直发，NVSwitch / 单跳 IB 内可行）。
  • 所以 MoE 专家并行（§7.4）和 DeepSpeed-Ulysses 式的上下文并行（§7.1 表的 CP 行）的通信优化只能从另外两个方向下手：少发（FP8 dispatch、top-\(k\) 截断、token 丢弃）和藏起来（DeepEP 用 IBGDA 让 all-to-all 与专家计算重叠）。

3.4 algbw 与 busBw：读懂 benchmark 的钥匙

nccl-tests 对每次调用报两个带宽：

\[ \text{algbw} = \frac{S}{t}\qquad\qquad \text{busBw} = \text{algbw} \times \text{系数（见 §3.3 表）} \]
  • algbw（algorithm bandwidth）：最朴素的「数据量 ÷ 时间」。用途是估算——知道 algbw，就能用 \(t = S/\text{algbw}\) 预测任意大小调用的耗时。缺点是它随 \(N\) 变化（\(N\) 越大越小），不能直接和硬件峰值比。
  • busBw（bus bandwidth）：乘上系数，把「算法必然产生的额外倍数」除掉，得到硬件链路的实际利用率。它与 \(N\) 基本无关，可以直接与 NVLink / IB 的标称带宽对比——这才是判断「我的集群网络正常吗」的指标。

举例：机内 8 卡 all-reduce，\(S=64\) MiB，实测 \(t=282\,\mu s\)。algbw \(=64\text{ MiB}/282\,\mu s=238\) GB/s——看着只有 NVLink4（450 GB/s）的一半，容易误判成有问题；busBw \(=238\times2\times\frac{7}{8}=416\) GB/s，已达单向峰值的 93%，完全正常。

nccl-tests 输出的 size 列，对 all-gather 是「输出总数组大小」= 每卡输入 × N，对 reduce-scatter 是「输入总数组大小」= 每卡输出 × N，而对 all-reduce 就是每卡张量大小。官方文档明确写了这两处的 S 指 total array（sendcount*sizeof*n / recvcount*sizeof*n）。若拿 all-gather 的 size 当成「每卡输入」去套公式，结果会差整整 \(N\) 倍。本篇所有公式里的 \(S\) 统一是「每卡输入缓冲区大小」，代 nccl-tests 数字前请先换算。

3.5 从公式到曲线：延迟主导区与带宽主导区

三条结论直接从图上读出来：① 水平段的高度 = 步数 × α：机内 ring 是 \(2\times7\times1.5\,\mu s=21\,\mu s\)，跨机 64 卡 ring 是 \(2\times63\times10\,\mu s=1.26\) ms——同一条 4 KiB 的小消息，跨机 ring 慢 60 倍，这就是「TP 不能跨机」的量化解释。② 换 Tree 只压低水平段（步数 \(2\log_2 N\)：8 卡 6 步、64 卡 12 步），斜线段几乎不动——因为两种算法的线上量 \(W\) 相同。③ 斜率只由带宽决定：跨机曲线陡 9 倍，因为 IB 比 NVLink 慢 9 倍。参数：\(\alpha\) 机内 1.5 µs（ring 每步）/ 2 µs（tree 每步），跨机 10 µs / 12 µs；曲线按纯 α-β 模型画，未计 NCCL 的分块流水线与实测抖动。

4. Ring 算法逐步走

4.1 为什么要「切成 N 份转圈」

最朴素的做法是「所有人都把数据发给 r0，r0 加完再发回去」（root-based）。它有两个致命问题：r0 的出入口链路要承载 \(N\cdot S\) 的流量（其他 \(N-1\) 条链路闲着），而且 r0 要存下 \(N\) 份数据。

Ring 的思路是把数据切成 \(N\) 块，让 \(N\) 张卡排成一个环，每步每卡只发一块给下家。这样每一步所有链路同时满载、没有任何热点——这就是它能达到 §3.2 下界的原因。代价是步数多：\(N-1\) 步（all-reduce 是 \(2(N-1)\) 步）。

4.4 Ring 的两个隐藏前提

  • 链路必须同构。环上任何一条慢链路都会拖死整个算法（每一步都要等它）。机内 8 卡如果混了 NVLink 和 PCIe，或跨机环里有一条 100 GbE 而其余是 400 Gb IB，实测带宽会掉到最慢那条的水平。
  • \(S\) 最好能被 \(N\) 整除。NCCL 对不能整除的情况会切成不等长的块，尾部略慢；写框架时把张量 pad 到 \(N\) 的倍数通常能白捡几个百分点。

5. Ring 不是万灵药：Tree、双二叉树、多维环、NVLS 与 one-shot

5.1 Ring 的软肋：步数是 \(O(N)\)

把 §3.1 的 α-β 模型套到 Ring All-Reduce 上：

\[ T_{\text{ring}} = \underbrace{2(N-1)}_{\text{步数}}\cdot \alpha \;+\; \underbrace{\frac{2(N-1)}{N}S}_{\text{每卡线上量}}\cdot \beta \]

两项的命运完全不同。带宽项几乎与 \(N\) 无关（\(2(N-1)/N \to 2\)，N=8 时 1.75，N=64 时 1.97）——这是 Ring 的伟大之处。但延迟项随 \(N\) 线性增长：\(\alpha = 1.5\,\mu s\) 时，N=64 要 126 步 = 189 µs 纯等待，一个字节都还没开始搬。

decode 阶段每次 all-reduce 的消息可能只有几十 KB（batch=1、H=8192、bf16 → 16 KiB），搬完只要 0.04 µs，而 189 µs 的延迟开销是它的 4700 倍。这就是为什么大规模推理不能无脑用 Ring。

选型第一原则：看 \(\alpha\) 项和 \(\beta\) 项谁大。消息大（\(S \gg S^* \approx 5\) MiB）→ 要带宽最优 → Ring / NVLS；消息小（\(S \ll S^*\)）→ 要步数最少 → Tree / one-shot。NCCL 自己就在做这个判断（NCCL_ALGO 的默认值由 tuning model 决定），理解它是为了在结果不对时能手动干预。

5.2.1 多维环：把 \(O(N)\) 的步数压到 \(O(\sqrt N)\)，而 \(W\) 一分不变

Ring 唯一的毛病是 \(k=2(N-1)\) 随 \(N\) 线性涨。如果集群本身是分层的（\(N=N_1\times N_2\)：\(N_2\) 张卡一个节点、共 \(N_1\) 个节点），就不必拉一个覆盖全部 \(N\) 卡的大环，而是沿两个维度各做一轮 ring all-reduce——这就是 2D torus，也是 §6 分层通信的抽象形式：

\[ \begin{aligned} W &= \underbrace{2\frac{N_2-1}{N_2}S}_{\text{维度 2：节点内环，全量 }S} + \underbrace{2\frac{N_1-1}{N_1}\cdot\frac{S}{N_2}}_{\text{维度 1：节点间环，只搬 }S/N_2} \\[4pt] &= 2S\left[\frac{N_2-1}{N_2} + \frac{N_1-1}{N_1N_2}\right] = 2S\cdot\frac{N_1N_2-N_1+N_1-1}{N} = \mathbf{2\frac{N-1}{N}S} \end{aligned} \qquad k = 2(N_2-1) + 2(N_1-1) \]

\(W\) 化简后与 1D Ring 逐字相同——分层没有减少一个字节，只是把同样的字节分到了两个维度上。而步数从 \(2(N-1)\) 降到 \(2(N_1-1)+2(N_2-1)\)；取方阵 \(N_1=N_2=\sqrt N\) 时是 \(4(\sqrt N-1)\)，即 \(O(N)\to O(\sqrt N)\)：

代入真实数字（\(N=1024=32\times32\)、\(S=64\) MiB、节点内 NVLink 450 GB/s & \(\alpha=1.5\,\mu s\)、节点间 IB 50 GB/s & \(\alpha=10\,\mu s\)）：2D torus ≈ 3.32 ms，flat 1D ring ≈ 23.14 ms，7.0× 加速。推广到 3D（机柜内 / 机架上 / 机架间）就是 \(2(N_1-1)+2(N_2-1)+2(N_3-1)\)，\(N=10^6\) 时步数只有 \(\approx 6\times100=600\)，而 1D ring 要 200 万步——这就是为什么万卡集群必须做成多维 torus，而不是拉一个大环。

三种「减少步数」的手段，代价完全不同，别混为一谈：
  • 树 / 递归折半：\(k: 2(N-1)\to 2\log_2 N\)，\(W\) 不变。靠指数衰减的交换量（§3.2.4），几何级数收敛到同一个总数。免费的。
  • 多维环：\(k: 2(N-1)\to 2\sum_i(N_i-1)\)，\(W\) 不变（上面刚证）。靠拓扑本来就是分层的这一事实。也是免费的，但要求物理拓扑匹配。
  • one-shot：\(k: 2(N-1)\to 1\)，但 \(W: 2\frac{N-1}{N}S \to (N-1)S\)，涨 \(N/2\) 倍。这是唯一真正拿流量换延迟的做法，所以只在 \(S\) 极小时划算（阈值 \(S^\dagger\)，§5.4）。

6. 分层通信：机内 NVLink + 机间 IB 的流量账

6.1 为什么必须分层：flat ring 浪费了 7/8 的网卡

真实集群的带宽是异构的：机内 NVLink 单向 450 GB/s，机间每张 400 Gb IB 网卡约 50 GB/s，差 9 倍。前面所有公式都假设「所有链路一样快」，一旦不成立，慢链路就是唯一的答案。

考虑一个看起来最自然的方案：把 64 张卡拉成一个大环（flat ring），环在节点边界处穿过 IB。分析一下每张网卡承担多少：

  • 环上每一步，每条链路都同时搬 \(S/N\)。跨机链路一共 \(m=8\) 条，每条搬 \(2(N-1)\cdot \frac{S}{N} = 126\) MiB。
  • 但每个节点在这条环上只有一进一出两个跨机端口——也就是说 8 张 NIC 里只有 1~2 张在干活，其余 6~7 张全程闲置。
  • 时间由最慢链路决定：\(126\ \text{MiB} \div 50\ \text{GB/s} = \mathbf{2.64\ ms}\)，再加上 126 步 × 10 µs 的跨机延迟 ≈ 1.26 ms，合计 ≈ 3.9 ms。

分层（hierarchical / 2-level）方案的做法是：让每张卡都独立跑自己的跨机通信，8 张 NIC 同时开工。

同样的原则贯穿 DeepSeek-V3 §3 的基础设施设计：跨机 MoE 的 all-to-all 被刻意安排成「每张 GPU 只跟远端同 rail 的 GPU 通信」，并给不同的 SM 分组以独占各自的 NIC，避免多卡抢一张网卡的 PCIe 通道。凡是「汇聚到一个代表再通信」的写法，在多网卡机器上都是反模式。

6.4 Rail-optimized 网络与 PXN

大规模集群的物理布线通常是 rail-optimized：所有节点的 GPU 0 接到同一台交换机（rail 0），GPU 1 接到 rail 1……这样同 rail 通信只需一跳，跨 rail 必须上 spine，既慢又容易拥塞。

问题来了：all-to-all（MoE 的 EP 通信）天生要跨 rail。PXN（PCI × NVLink） 是 NCCL 的解法：本卡要发给远端 rail \(k\) 的数据，先通过机内 NVLink 转给本地那张属于 rail \(k\) 的 GPU，再由它走 IB 一跳直达。代价是多一次机内传输（便宜，450 GB/s），收益是避开 spine 的拥塞与额外跳数。

7.2 TP：一层里那两次 All-Reduce 从哪来

图 7-1：列并行把权重按输出维切开，每张卡算出部分结果（不需要通信）；行并行把权重按输入维切开，每张卡算出一个不完整的求和项，必须 All-Reduce 才能拼回正确答案。「列并行 → 行并行」的配对是 Megatron 的核心设计，正好让每个子层只需要一次通信。

算例 A：Llama-3-70B，TP=8，prefill chunk = 4096 token，bf16。

  • \(S = T\cdot H\cdot b = 4096\times 8192\times 2 = \mathbf{64\ MiB}\)
  • 每次 All-Reduce 每卡线上量 \(= \frac{2\times 7}{8}\times 64 = \mathbf{112\ MiB}\)
  • 耗时 \(= 112\,\text{MiB}/450\,\text{GB/s} + 14\times1.5\,\mu s = 261 + 21 = \mathbf{282\ \mu s}\)
  • 一层 2 次 → 0.56 ms；80 层前向合计 45 ms，每卡搬 17.5 GiB

45 ms 是什么概念？70B 在 TP=8 上算 4096 token 前向约需 \(2\times 70.5\text{G}\times 4096 / (8\times 500\ \text{TFLOPS}) \approx 144\) ms（不算 attention 的 \(S^2\) 项）。通信占前向的 31%——而且这 45 ms 无法与计算重叠（All-Reduce 在关键路径上，后面的算子必须等它）。这就是 TP 只能放机内、且 TP=16 跨机会崩掉的量化理由。

7.3 decode：同一个 All-Reduce，完全不同的性格

算例 B：Llama-3-70B，TP=8，decode，batch=32，H=8192，bf16。

  • \(S = 32\times 8192\times 2 = \mathbf{512\ KiB}\)（比 prefill 小 128 倍）
  • Ring：\(14\times1.5\,\mu s + 896\,\text{KiB}/450\,\text{GB/s} = 21 + 2.1 = \mathbf{23.0\ \mu s}\) —— 91% 是纯延迟
  • custom two-shot（全连接 P2P，2 轮）：\(2\times1.5 + 2.1 = \mathbf{5.0\ \mu s}\)
  • one-shot：\(1\times1.5 + 3.5\,\text{MiB}/450 = \mathbf{9.7\ \mu s}\)（512 KiB 已超过 §5.4 算出的 126 KiB 上限，所以输给 two-shot）
  • batch=1 时 \(S=16\) KiB：one-shot 1.8 µs < two-shot 3.1 µs < Ring 21.1 µs —— 完全反过来
  • 每层 2 次 × 80 层 = 160 次/step：Ring 3.69 ms vs two-shot 0.81 ms

同一个原语，prefill 是带宽问题、decode 是延迟问题。prefill 的 64 MiB 消息把 21 µs 的步数开销稀释到看不见；decode 的 512 KiB 消息里，21 µs 延迟占了 91%。所以推理框架宁可自己写 kernel 绕过 NCCL——省的不是字节，是步数。

7.4 MoE 的 All-to-All：最贵的一次通信

算例 C：Qwen3-235B-A22B，EP=8，top-k=8，H=4096，bf16，T=4096，94 个 MoE 层。

  • dispatch 每卡线上量 \(= T\cdot k\cdot H\cdot b\cdot\left(1-\frac1{\text{EP}}\right) = 4096\times8\times4096\times2\times\frac78 = \mathbf{224\ MiB}\)
  • combine 对称，再来 224 MiB → 每层 448 MiB
  • 机内（450 GB/s）：1.04 ms/层；跨机（50 GB/s）：9.4 ms/层
  • 94 层前向：机内 41 GiB / 98 ms；跨机 41 GiB / 0.88 s
  • 换 FP8 dispatch：每层降到 224 MiB，跨机 0.44 s

对比 §7.2 的 TP：70B 稠密模型 80 层前向通信 45 ms，而 235B MoE 光是跨机 EP 就要 880 ms。这就是「EP 尽量关在机内」「跨机必须上 FP8 dispatch」「DeepEP 要用 IBGDA 绕过 CPU proxy」这些工程决策的全部动机。

All-to-All 的 \(1-\frac1{\text{EP}}\) 因子来自「发给自己的那一份不用上网」：EP=8 时是 0.875，EP=64 时是 0.984——再加大 EP 也省不下流量，它只是把同样的字节摊到更多链路上。真正能减字节的只有三条路：减小 \(k\)、量化激活、或者用分组/分层 all-to-all（先在机内做一次 local dispatch 聚合，再跨机）。

7.5 DP / ZeRO：梯度那一次 All-Reduce

算例 D：70.55B 参数，TP=8 机内、DP=8 跨机，bf16 梯度。

  • 每卡梯度分片 \(G = 70.55\text{G}\times 2 / 8 = \mathbf{17.6\ GB}\)
  • DDP / ZeRO-1：\(W \approx 2G = \mathbf{35.3\ GB}\)，跨机 50 GB/s → 0.71 s/step（ZeRO 论文的 \(2\Psi\) 是取整上界；按 §3.2 的精确 Ring 因子 \(2\frac{N-1}{N}=1.75\) 算是 30.8 GB → 0.62 s，本页计算器 preset「DP 梯度」给的就是后者）
  • ZeRO-3 / FSDP：\(\approx 3G = \mathbf{52.9\ GB}\)（前向 AG + 反向 AG + 梯度 RS），→ 1.06 s/step

0.71 s 听起来灾难，但 DP 的通信有个别的并行都没有的奢侈：它可以和反向传播重叠。梯度是分桶（bucket，PyTorch DDP 默认 25 MB）产生的，一个桶算完就立刻发，等到反向结束时最后几个桶也发完了。判断标准是：

\[ T_{\text{comm}}^{\text{grad}} \;\le\; T_{\text{backward}} \quad\Longleftrightarrow\quad \text{通信被完全隐藏} \]

反向大约是前向的 2 倍时长。如果一次 step 的前向是 1.5 s，反向 3 s，那 0.71 s 的梯度通信完全藏得住——DP 的通信量最大，却通常不是瓶颈。反过来 TP 的 45 ms 虽然小得多，却因为在关键路径上而完全暴露。这是理解「为什么 TP 放机内、DP 跨机」的最后一块拼图。

8.3 八个坑

  1. 拿 algbw 去比硬件标称带宽。8 卡 all-reduce 的 algbw 天生只有 busBw 的 \(1/1.75 = 57\%\)。这是算法下界（§3.2），不是故障。看到「450 GB/s 的卡只跑出 240」先去查 busBw 那一列。
  2. 只测小消息就下结论。\(S \le 1\) MiB 时 time 几乎是常数（延迟地板），algbw 随 size 线性上升，画出来的「带宽曲线」毫无诊断价值。必须扫到 ≥ 512 MiB 才进入带宽主导区。
  3. GPUDirect RDMA 没生效。日志里应看到 NET/IB : ... GDRDMA；如果是 via shared memory 或走了 host bounce buffer，跨机带宽直接腰斩甚至掉到 1/5。检查 nvidia-peermem / nv_peer_mem 模块是否加载。
  4. NCCL_SOCKET_IFNAME 选错网卡。日志 NET/Socket : Using [0]eth0:10.0.0.5 而 eth0 是 1 GbE 管理网 → 全部流量走管理网。用 NCCL_SOCKET_IFNAME=^docker0,lo 排除，或直接指定 IB 设备。
  5. NUMA / PCIe 亲和错配。GPU 0 的 NIC 挂在 NUMA 0，而进程被调度到 NUMA 1，数据要跨 socket 的 UPI 走一趟。nvidia-smi topo -m 看 GPU↔NIC 是不是 PIX/PXB（同 switch）；用 numactl --cpunodebind 或 --map-by ppr:8:socket 绑核。
  6. P2P 被 ACS / IOMMU 关掉。nvidia-smi topo -m 里 GPU 之间显示 PIX/PHB/SYS 而不是 NV12 之类，或者日志出现 P2P is disabled → 机内退到 shared memory，带宽掉 5–10 倍。BIOS 关 ACS、开 IOMMU passthrough。
  7. 残留的 NCCL_ALGO / NCCL_PROTO。某次为了排查手工设了 NCCL_ALGO=Ring 忘了删，之后跨机训练就一直慢 3–5 倍。诊断时先 env | grep NCCL 清场，再逐项加回来做 A/B。
  8. 用 nccl-tests 的 time 乘层数去估训练通信占比。nccl-tests 是空载上限：没有计算抢 SM、没有别的集合通信抢带宽、没有重叠。真实训练里 DP 的梯度通信大部分被反向藏掉，而 TP 的 all-reduce 一点也藏不住。要估占比必须用 torch.profiler / nsys 抓真实时间线。

三条能带走的判断力：①任何通信问题先拆成 \(k\alpha + W\beta\)，看哪一项大；②看 W 永远要看「每卡线上量」而不是「语义量」，否则会把 1.75× 的算法下界误判成故障；③在异构集群里，决定时间的不是总字节数，而是最忙那条链路上的字节数——所以「让更多链路同时干活」往往比「减少字节」更有效。
